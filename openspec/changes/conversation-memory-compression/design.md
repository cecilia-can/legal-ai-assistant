## Context

当前 `POST /api/chat` 从数据库读取会话的全部 user/assistant 消息，并由 `lib/ai/context.ts` 在 token 超预算时从最早消息开始裁剪。此方式实现简单，但会丢失法律咨询中可能决定结论的早期事实；数据库保留原文并不代表模型在下一轮仍能看到这些内容。

项目已具备 PostgreSQL、Prisma、pgvector、按用户隔离的会话、知识库 RAG 与 token 计数能力。新设计必须保持原始 Message 不可替代、服务端决定上下文、会话与用户权限隔离，以及聊天 SSE 的现有请求格式。

## Goals / Non-Goals

**Goals:**

- 在不传入完整历史的情况下保持长期会话的事实连续性。
- 将普通法律问答与逐步形成的案件咨询同时纳入一份通用、可校验的会话记忆。
- 在摘要缺失细节时，能从当前用户有权访问的同一会话早期原文中找回少量证据片段。
- 为普通聊天配置可预测的输入、输出与压缩成本，并保留审计和重建能力。

**Non-Goals:**

- 不建立跨会话或跨用户的个人记忆。
- 不将用户陈述自动认定为客观事实或法律结论。
- 不改变浏览器调用聊天接口的格式，不将内部摘要、检索结果或工具轨迹暴露到 SSE。
- 不在本 Change 实现案件工作空间、Agent 规划、外部网络搜索或文档知识库的重构。

## Decisions

### 1. 采用单一通用摘要，案件信息为可选块

每个 Conversation 最多有一条当前 `ConversationMemory`，`content` 为版本化 JSON：通用字段包含 `summary`、`topics`、`conclusions`、`openQuestions`；可选 `case` 块包含当事人、时间线、事实、证据和争点。事实项必须标记 `user_stated`、`document_supported` 或 `uncertain`，并携带来源 Message ID。

选择它而不是互斥的 `general | case` 类型：用户可从一般法律问答自然过渡到个案，且无需迁移或错误分类。选择它而不是纯自然语言摘要：服务端可用 Zod 校验，并可明确处理事实状态与来源。

### 2. 原始消息是事实来源，摘要是可重建派生数据

`ConversationMemory` 保存 `coveredUntilMessageId`、`sourceMessageIds`、`schemaVersion`、`revision`、更新时间和失败状态。每次更新使用乐观并发控制；若摘要输出不合法、来源范围变化或写入冲突，保留上一有效版本。删除消息或会话时，关联记忆和回溯片段必须失效或级联删除。

选择持久化摘要而不是每轮临时生成：可降低重复 token 成本并提供稳定上下文。选择保留全部 Message 而不是用摘要覆盖 Message：用户纠正、问题排查和摘要重建都依赖原文。

### 3. 使用增量摘要，而非全量重总结

压缩输入为“上一有效摘要 + 已覆盖范围之后、即将退出近期原文区的连续消息”；其输出取代旧摘要，并推进覆盖游标。摘要调用使用专用 prompt、低创造性参数和结构化 JSON 输出；模型不得生成法律结论、补全缺失事实或把助手推测升级为事实。

压缩在输入占应用输入预算约 65% 时创建持久化任务。若本轮已经无法在硬预算内保留所需消息，则先同步完成压缩；其余任务由持久化任务表和 worker 执行，不能依赖 Route Handler 结束后的悬空 Promise。

### 4. 上下文以预算驱动的分层组合

聊天输入按以下顺序分配预算：固定系统规则、授权知识库 RAG、会话记忆、按需回溯的历史原文、近期原文与本轮用户消息。系统必须先保留最新用户消息，随后从低优先级的回溯片段和最旧近期消息收缩，绝不静默删除会话记忆中的来源信息。

应用配置 `CHAT_MAX_CONTEXT_TOKENS` 和 `CHAT_MAX_OUTPUT_TOKENS` 定义产品级总预算，而非用尽供应商最大上下文。AI 客户端将输出配置传入上游 `max_tokens`，使本地预算与实际调用一致。

### 5. 第二期使用独立会话回溯索引

为较早消息构建 `ConversationRecallChunk`：它按连续消息形成短片段，记录 `conversationId`、消息范围、内容哈希、embedding 模型/维度和向量。检索只能在当前 `conversationId` 与当前 `userId` 的授权范围内进行，并与知识库 RAG 分别标识。回答模型收到的回溯内容须注明“会话历史原文”，不得作为法律资料引用。

选择独立索引而不是复用 DocumentChunk：两者的权限、生命周期、来源语义和引用方式不同。第一期不依赖该索引；第二期可按开关渐进启用。

## Risks / Trade-offs

- [摘要遗漏或扭曲事实] → 保留原始消息、记录来源 ID 与状态；用户纠正时优先重建，并在必要时从原文回溯。
- [摘要模型输出非法 JSON] → Zod 校验、失败不覆盖旧记忆、持久化失败状态并重试。
- [流式响应后的后台任务丢失] → 使用数据库任务记录与独立 worker/受控触发器，不使用不可靠的 fire-and-forget。
- [会话回溯泄露其他用户内容] → 查询必须以 `(conversationId, userId)` 授权，数据库索引和服务层均强制限制。
- [长上下文成本与延迟升高] → 应用级上限、软阈值、预算优先级和用量日志；普通聊天不默认使用模型 1M 上限。
- [摘要与消息删除不一致] → 删除后标记或删除受影响记忆/片段，下次对话从可用原文重建。

## Migration Plan

1. 先增加记忆、压缩任务与回溯片段表及索引，不修改或删除既有 Message。
2. 部署摘要 schema、服务与迁移后，历史会话的记忆初始为空；首次触发压缩时按原文懒构建。
3. 上线第一期后监控摘要成功率、token 用量、压缩延迟与用户纠正率。
4. 在回溯索引完成回填和权限测试后，通过特性开关启用第二期检索。
5. 回滚时停用特性开关并继续使用现有最近历史裁剪；保留派生记忆/索引数据，禁止删除原始消息。

## Open Questions

- 当前部署是否具备常驻 worker 或计划任务能力；若没有，需要选择与部署环境兼容的队列执行器。
- 生产使用的 DeepSeek 模型是否支持所需的结构化 JSON 响应与 `max_tokens` 语义；需要在接入前进行 provider spike。
- 用户是否需要查看、编辑、清除会话摘要；第一期默认不展示，但数据模型需保留后续可视化空间。
