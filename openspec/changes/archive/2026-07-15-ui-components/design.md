## 背景

项目已完成 Change 1.1：Prisma/PostgreSQL 基础设施、`Conversation`/`Message` 模型、`lib/db.ts`、基础目录和共享聊天类型已经就绪。当前 `components/chat/`、`components/layout/`、`components/ui/` 仍为空目录，`app/page.tsx` 仍是默认 Next.js 模板页面。

Change 1.2 是 Phase 1 ChatBot 的前端基础阶段，需要提供一个可验收的聊天界面骨架，并为后续 Change 1.3 会话管理、Change 1.4 AI 流式输出、Change 1.5 消息持久化留下稳定组件接口。

## 目标 / 非目标

**目标：**

- 将首页替换为法律 AI 助手的 ChatBot UI 骨架。
- 提供桌面端侧边栏 + 主聊天区布局，并在移动端保持可用。
- 创建基础聊天组件：会话列表、消息列表、消息气泡、聊天输入框。
- 创建少量基础 UI 原语：按钮、文本区域、空状态。
- 在 `app/globals.css` 中定义适合本项目的基础颜色、背景和主题 token。
- 组件使用静态/mock 数据或 props 驱动，便于后续接入真实 API。

**非目标：**

- 不实现会话 CRUD API、数据库查询或 React 状态管理。
- 不接入 AI API、流式输出、请求取消或重试机制。
- 不实现消息持久化、分页、删除或历史加载。
- 不实现 Markdown 渲染、代码高亮或复制代码功能。
- 不引入认证、多用户、案件工作空间或知识库能力。

## 设计决策

### 1. 采用组件分层而不是单页堆叠

**决策：** 页面入口 `app/page.tsx` 只组合布局和聊天组件；具体 UI 拆分到 `components/layout/`、`components/chat/` 和 `components/ui/`。

**理由：** Change 1.3 以后会逐步接入真实会话、消息、流式响应和服务层逻辑。提前把布局、聊天组件和基础 UI 原语拆开，可以减少后续重写成本。

**备选方案：**

- 直接在 `app/page.tsx` 实现完整 UI：实现快，但会让后续状态管理和 API 接入变得混乱。
- 引入完整 UI 组件库：当前阶段需求较小，会增加依赖和样式约束。

### 2. 组件先使用 props 驱动和静态数据

**决策：** 会话列表、消息列表和输入框组件先定义清晰 props，并在页面层使用静态示例数据展示。

**理由：** Change 1.2 的目标是 UI 基础，不应提前实现 API 或数据库调用。Props 驱动能让后续 Change 1.3/1.4 用真实数据替换 mock 数据。

### 3. 聊天布局采用桌面固定侧边栏、移动端左侧滑出抽屉

**决策：** 桌面端使用左侧 sidebar（固定宽度 `w-80` / 320px）+ 右侧 main chat 区域；桌面端支持通过「收起 / 侧栏」按钮展开与收起侧栏，收起时侧栏宽度动画过渡为 0，主聊天区占满剩余空间。移动端默认全屏展示主聊天区，会话导航通过主区头部的「会话」按钮打开，以**左侧滑出抽屉**形式展示侧边栏内容。用户选中会话、点击关闭按钮或点击遮罩后，抽屉自动关闭并回到主聊天区。

**理由：** ChatGPT 类产品的主使用场景需要稳定的会话导航和聊天内容区。桌面端固定侧栏宽度可避免侧栏被内容挤压过窄、主区比例失衡；收起能力则让用户在宽屏下优先专注对话内容。移动端空间有限，若将会话列表与主区纵向堆叠，会挤压消息区域；改为默认主区 + 按需抽屉，可保证消息列表和输入框始终可用。

**备选方案：**

- 移动端纵向堆叠 sidebar 与 main：实现简单，但会话列表会占据过多高度，消息区几乎不可读。
- 全屏切换式会话列表：可用，但切换成本高于抽屉，且与桌面侧栏心智差异更大。
- 桌面端侧栏仅固定宽度、不可收起：实现更简单，但宽屏下无法让主聊天区独占视口。

### 4. 桌面侧栏展开与收起

**决策：** 桌面端侧栏默认展开；侧栏头部提供「收起」入口，主聊天区头部在侧栏收起后提供「侧栏」入口重新展开。收起/展开状态由页面层本地 state 管理，本阶段不持久化到 localStorage。

**理由：** 满足用户在桌面端按需放大主聊天区的需求，同时保持实现轻量，不引入额外存储或图标库依赖。

**备选方案：**

- 收起后保留窄条（icon rail）：信息密度更高，但当前阶段未引入图标库，文本按钮方案更一致。
- 收起状态持久化：体验更好，但 Change 1.2 非目标，留待后续 UX 优化。

### 5. 使用 Tailwind CSS 和 CSS variables 定义主题

**决策：** 延续当前 Tailwind CSS 配置，在 `app/globals.css` 中补充 CSS variables，例如 background、foreground、surface、muted、border、primary。

**理由：** 当前项目已使用 Tailwind CSS 4，不需要新增主题库。CSS variables 便于后续支持深色模式和品牌色调整。

### 6. 输入框只提供本地交互，不提交到后端

**决策：** `ChatInput` 提供输入、提交回调、禁用状态和基础键盘交互，但不调用 API。

**理由：** API 和流式输出属于后续 Change。此阶段只保证组件行为和视觉结构，为后续接入保留 `onSubmit` 接口。

### 7. 先不引入图标库

**决策：** 默认使用文本符号、纯 CSS 或简单内联元素完成按钮和状态展示；除非实现阶段确认必要，否则不新增图标依赖。

**理由：** 降低依赖面，避免基础 UI 阶段引入与设计系统绑定过深的库。

## 风险 / 权衡

- [风险] 静态 UI 与后续真实数据结构不完全一致 → 使用 `types/chat.ts` 中已有类型作为参考，props 命名贴近 `Conversation` 和 `ChatMessage`。
- [风险] 响应式布局过早复杂化 → 移动端仅实现基础左侧滑出抽屉和遮罩关闭；桌面端仅实现固定宽度侧栏与收起/展开，不引入手势库或复杂动画依赖。
- [风险] 视觉风格后续可能调整 → 通过 CSS variables 集中定义颜色 token，降低后续改动成本。
- [风险] 输入框行为与未来流式提交有差异 → 仅约束 `onSubmit(content)`、disabled、placeholder 等稳定接口，不绑定具体请求实现。

## 实施计划

1. 创建基础 UI 原语组件。
2. 创建 layout 和 chat 组件。
3. 用静态示例数据替换 `app/page.tsx` 默认模板。
4. 更新 `app/globals.css` 的主题 token 和基础页面样式。
5. 运行 `npm run lint` 和 `npm run build` 验证。

**回滚：** 如果 UI 实现出现问题，可恢复 `app/page.tsx` 和相关组件文件；本变更不修改数据库和持久化数据。
