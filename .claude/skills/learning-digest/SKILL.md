# 学习复盘与知识沉淀（learning-digest）

把当前聊天窗口里的技术问答，复盘成**结构化知识点**，去重后**追加/合并**进项目知识库 `docs/learning/`，并为每个知识点补充**可向外延伸**的相关内容。知识库按 roadmap 的 **Change** 分文件组织，呼应 `docs/roadmap.md` 中“学习优先：重点记录每个阶段的学习心得和架构决策，形成知识库”。

触发示例：

- “复盘一下”
- “总结/沉淀知识点”
- “做个学习复盘”
- “digest”

---

## 核心规则

- 面向用户的说明和知识库正文使用**中文**；文件名、标签、代码标识符使用英文。
- 只复盘**当前对话上下文**里真实出现过的问答，不凭空虚构问题。
- **来源问题**必须来自本对话中用户的原话或忠实 paraphrase；**禁止**读代码/文档后反推并伪造用户问题；**禁止**为凑条目硬造新知识点。
- 每次沉淀**仅写入当前 Change** 的学习文档；**禁止跨 Change** 读取、合并、更新其他 Change 文件——即使主题与历史 Change 重合，也在当前 Change 文档中**新建或本文件内合并**，不去改旧文件。
- 去重/合并/补充的检索范围**仅限**当前 Change 的 `docs/learning/<change-number>-<slug>.md`。
- 知识点分为「✅ 确定」「⚠️ 需查证」两档；关键结论用 `WebSearch` 联网核实后再标注 🔗 来源。
- 再次触发时**必须去重**：在同一 Change 文档内，同标题知识点做合并更新，而不是重复追加。
- 不修改 `docs/learning/` 以外的项目代码。
- 不提交 `.env`、凭证或密钥。

---

## 总流程

```text
识别当前 Change（唯一写入目标）
→ 提取问题与知识点（仅来自对话）
→ 结构化 + 联网核实延伸内容
→ 读取当前 Change 知识库文件、本文件内去重合并
→ 更新 INDEX.md（仅登记当前 Change）
→ 报告增量 + 来源追溯 + 列出“我的疑问”
```

---

## 1. 识别当前 Change（决定唯一写入目标）

按优先级判断当前处于哪个开发阶段：

1. 读 git 分支名：`git branch --show-current`，形如 `feature_<slug>_<YYMMDD>` → 取 `<slug>`。
2. 看 `openspec/changes/` 下未归档（非 `archive/`）的 active change 目录名。
3. 对照 `docs/roadmap.md` 找到对应的 Change 编号与标题。

得到**唯一**目标文件：`docs/learning/<change-number>-<slug>.md`，例如 `docs/learning/1.3-conversation-management.md`。

**本节只决定写入哪个文件，不按对话主题改投其他 Change 文件。** 即使知识点在其他 Change 文档中已有同名/同主题条目，也**只在当前 Change 文件**中新建或本文件内合并，**不得**打开或修改其他 Change 的学习文档。

**无法唯一确定目标文件时，一律先用 `AskQuestion` 询问用户，不要静默写入。** 具体：

- **有歧义**（分支与 active change 指向不同 Change、或匹配到多个）→ 列出候选 Change 让用户选。
- **完全无信息**（不在 feature 分支、也没有 active change）→ 询问用户写入哪个 Change，并提供「写入 `docs/learning/general.md`」作为其中一个选项。

只有在用户明确选择后才写入；用户选 `general.md` 时才落到通用文件。

---

## 2. 提取问题与知识点

通读当前对话，提取：

- 用户**真实问过的问题**（合并重复/追问，保留核心疑问）。
- 每个问题对应的**结论**与**原理**（限于回答该问题时的解释）。
- 对话过程中暴露的**易错点 / 踩过的坑 / 纠正过的误解**。
- 明确**还没搞懂或存疑**的点 → 进入“我的疑问”清单。

只保留有沉淀价值的技术点；寒暄、纯操作指令不入库。

### 来源边界（硬约束）

**结论 / 原理 / 易错点**必须来自本对话中的问答；**延伸**另有放宽规则（见下）。

| 字段 | 可写入 | 不可写入 |
|------|--------|----------|
| 来源问题、结论、原理、易错点 | 用户在本对话中的提问；回答该问题时的解释；对话中出现的纠正/误解 | 用户未问、从代码/文档读出的架构结论；凭空推断的「来源问题」；代码审查式易错点 |
| **延伸** | 与**本次提问**强相关的概念、方法、工具或后续 Change 衔接（**含当前代码中未出现的**）；每条**简要提及**，不在延伸里展开成教程 | 与本次提问弱相关的发散；从读代码推断、用户未问的新主题；在延伸里写详细教程或另开 `###` 条目 |

**「延伸」**只扩展**同一条问答**下的 1 层强相关内容，写在**该条知识点的「延伸」字段**内；**不得**从读文件拆出新的独立 `###` 知识点条目。

## 3. 结构化每条知识点

每条知识点使用统一模板（写入知识库文件）：

```markdown
### [知识点标题]

- **来源问题**：<当时的核心问题，一句话>
- **结论**：<一句话核心答案>
- **原理 / 为什么**：<简要解释，2-4 句>
- **易错点 / 坑**：<可选，没有则省略>
- **延伸**：
  - <相关可拓展方向 1> ✅
  - <相关可拓展方向 2> ⚠️需查证
  - 🔗 <参考来源链接>
- **标签**：#<tag1> #<tag2>
- **状态**：#待复习
- **日期**：YYYY-MM-DD
```

标注约定：`✅` 确定、`⚠️需查证` 不确定、`🔗` 来源链接、`#待复习` / `#已掌握` 复习状态。

### 关于“延伸”

- 只延伸**强相关**的 1 层内容，不要漫无边际发散。
- 延伸写在**同一条知识点**的「延伸」字段里，**不是**再开一条新 `###` 知识点。
- **延伸可包含与本次提问相关、但未必出现在当前代码中的概念、方法或工具**（如替代写法、配套 API、同类对比、后续 Change 衔接）；**仅简要提及**（通常每条 1 句），不在延伸里展开成教程。
- 关键结论（尤其是版本相关、API 相关）先用 `WebSearch` 核实，再写入并附 🔗 来源；未核实的标 `⚠️需查证`。
- 延伸方向可优先服务于后续 Change，但仍须挂在本条问答下，不能单独成条。
- **禁止**借延伸引入：用户未问且与问题弱相关的主题；从读代码推断的架构叙事（应作为独立知识点时，用户必须先在本对话中问到）。

### 填好的示例（对照这个颗粒度）

```markdown
### App Router 下用 ReadableStream 实现流式响应

- **来源问题**：Next.js 的 Route Handler 里怎么把 AI 的流式输出返回给前端？
- **结论**：在 Route Handler 中返回一个 `Response(stream)`，其中 `stream` 是 `ReadableStream`，前端用 `response.body.getReader()` 逐块读取。
- **原理 / 为什么**：App Router 的 Route Handler 基于 Web 标准的 `Request`/`Response`，原生支持流式 body；无需像旧版 API Routes 那样手动 `res.write()`。
- **易错点 / 坑**：别忘了设 `Content-Type: text/event-stream` 并禁用缓冲；`export const dynamic = "force-dynamic"` 避免被静态化。
- **延伸**：
  - Vercel AI SDK 的 `streamText` 已封装好这套流程，可直接用 ✅
  - 前端可用 `EventSource`（SSE）替代手动 reader，但不支持 POST ⚠️需查证
  - 🔗 https://nextjs.org/docs/app/building-your-application/routing/route-handlers#streaming
- **标签**：#nextjs #streaming #app-router
- **状态**：#待复习
- **日期**：2026-07-15
```

**延伸含「代码外相关概念」的示例**（问 TypeScript 类型，延伸可提 Map、后续 Change，不必出现在当前文件里）：

```markdown
### TypeScript `Record<string, ChatMessage[]>` 含义

- **来源问题**：`Record<string, ChatMessage[]>` 这是什么意思？
- **结论**：以 `string` 为键、`ChatMessage[]` 为值的对象类型，等价于 `{ [key: string]: ChatMessage[] }`。
- **原理 / 为什么**：`Record<K, V>` 是内置泛型；`<>` 内是键值类型，不是数组语法。
- **延伸**：
  - 同类写法还有索引签名 `{ [id: string]: ChatMessage[] }` ✅
  - `Map<string, ChatMessage[]>` 语义类似，但不便 JSON 序列化 ✅
  - Change 1.5 消息持久化后，可从 API 填入同样结构 ✅
- **标签**：#typescript #generics
- **状态**：#待复习
- **日期**：2026-07-22
```

## 4. 去重合并进知识库

同一个 Change 可以分多次沉淀，写入同一个文件。**每次触发都新建一个带日期的「沉淀批次」小节，追加到文件末尾**，本次的新知识点归入该批次，保证"下一次接在上一次后面"的时间顺序。

**检索与写入范围仅限当前 Change 的目标文件，禁止跨 Change 操作。**

1. **只读取**当前 Change 的目标文件 `docs/learning/<change-number>-<slug>.md`：
   - 文件**不存在**，且本批次**至少有 1 条**可沉淀知识点 → 用第 6 节模板**新建**。
   - 文件**不存在**，且本批次**无**可沉淀知识点 → **不新建**空文档。
2. 对每条待写入的知识点，**仅在该文件内**按 `###` 标题匹配已有条目：
   - **标题为新** → 归入本次批次小节。
   - **标题相同（含语义等价，措辞略有出入也算同一条）** → **在原位合并更新**：补充新的延伸/来源/易错点、更新日期；不在新批次里重复整条。
3. 在文件末尾追加本次批次小节 `## 沉淀 YYYY-MM-DD（第 N 次）`（N 为该文件已有批次数 +1），把本次的**新**条目放进去（原位合并更新的条目不重复放入新批次）。
4. **不要为了归类而移动或重排已有条目**，历史批次保持原有顺序不动。
5. **不得**打开、读取、修改其他 Change 的学习文档——即使主题与旧 Change 完全重合。

---

## 5. 更新 INDEX.md

更新 `docs/learning/INDEX.md`：**仅**登记/刷新**本次写入的当前 Change** 文件的条目数、最近更新日期。

- 不因跨 Change 操作修改其他 Change 的计数（禁止跨 Change 写入，故不应发生）。
- 本批次无可沉淀内容、未新建/未修改当前 Change 文档时，**不更新** INDEX。

---

## 6. 文件模板

新建单个 Change 知识库文件时的结构（`##` 为沉淀批次，`###` 为知识点）：

```markdown
# 学习知识库：<Change 编号> <Change 标题>

> Phase：<Phase 编号与名称>　|　分支：`feature_<slug>_<YYMMDD>`

## 沉淀 <YYYY-MM-DD>（第 1 次）

### <知识点标题>
<知识点条目，见第 3 节模板>

## 我的疑问（待解决）

- [ ] <存疑问题>
```

后续每次沉淀，在「我的疑问」小节**之前**追加新的 `## 沉淀 <日期>（第 N 次）` 批次；「我的疑问」始终保持在文件末尾。

**注意**：「新建文件」指当前 Change 尚无学习文档且本批次有内容时创建；**不可**为凑数创建空壳文档。

## 7. 报告增量

复盘完成后，向用户报告：

```text
本次复盘写入 docs/learning/<当前-change-file>.md（沉淀第 N 次）：
- 当前 Change：<编号> <标题>
- 本批次新增 X 条；本 Change 文档内原位合并更新 Y 条
- 来源追溯：
  - 「<用户原话摘要>」→ #<知识点标题>（新增|合并）
- 跳过：<无沉淀内容时的说明，例如未新建文档>
- 未修改其他 Change 的学习文档
- 联网核实 M 条关键结论
- 我的疑问（待解决）：
  1. ...
  2. ...
```

---

## 暂停 / 询问条件

- 无法唯一确定当前 Change 时（含完全无信息的情况），一律用 `AskQuestion` 确认写入哪个文件，不静默兜底。
- 当前对话没有可沉淀的技术知识点时，如实说明、不硬凑、不建空文档。
- 即使判定与某旧 Change 主题重复，仍只写当前 Change 文档；**禁止**去改旧 Change 的学习文件。
