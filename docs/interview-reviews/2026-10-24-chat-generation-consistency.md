## 本阶段做了什么

原聊天链路由浏览器先接收 SSE，再另发消息保存请求。这会在刷新、断流、保存失败或重复提交时留下消息丢失和重复落库窗口。本阶段把“一次 AI 回复”改造成由服务端管理、可追踪的生成任务。

核心调用链如下：

```text
浏览器发送 conversationId + content + clientRequestId
  → POST /api/chat 校验会话归属、请求参数和限流
  → Prisma 事务创建 user Message、空 assistant Message、ChatRun(generating)
  → 读取会话历史并调用 DeepSeek 兼容接口
  → SSE 发送 token / done / error / cancelled
  → 服务端事务写入 assistant 最终文本，并将 ChatRun 更新为终态
  → 前端根据 runId、SSE 终态刷新已持久化消息或提供重试
```

具体完成内容：

1. 新增 `ChatRun` 模型，关联会话、用户消息和助手消息，保存 `clientRequestId`、状态、失败原因、开始及结束时间。
2. 通过 `(conversationId, clientRequestId)` 唯一约束实现幂等；同一会话增加 PostgreSQL 部分唯一索引，确保只有一个 `generating` 任务。
3. 将 user 消息、assistant 空占位和生成任务放入同一个 Prisma 事务，避免初始写入留下半条记录。
4. 在服务端保存 `completed`、`cancelled`、`failed` 终态和已接收文本，浏览器不再承担本轮聊天消息落库。
5. 统一 SSE JSON 事件为 `token`、`done`、`error`、`cancelled`；只有收到 `done` 才算成功，意外断流不会被误判为成功。
6. 将 `AbortSignal` 传入 OpenAI SDK 兼容调用，配置首 token、流空闲和整轮生成超时；当前默认模型为 DeepSeek 兼容接口。
7. 前端保存每个会话的 `runId`、生成状态、失败原因和重试内容。失败或取消后，重试会重新发起原问题，不再只是重新加载历史。
8. 重新生成不再先删除旧回复，而是保留原历史后创建新候选轮次，避免候选生成失败造成内容丢失。
9. 新增 SSE 终态单元测试，并修复虚拟列表测试环境中 `requestAnimationFrame` 同步回调导致的临时死区错误。

## 关键决策与取舍

### 用 ChatRun 表承载运行态，而不是给 Message 堆叠状态字段

`Message` 负责展示对话内容；请求 ID、取消、超时、失败原因和耗时属于一次模型调用。独立的 `ChatRun` 让消息数据保持简单，也为后续增加回复版本、运行统计和恢复能力保留位置。

### 在调用模型前创建占位消息

服务端先持久化 user 消息、空 assistant 消息和 `generating` 任务，再调用上游。这样即使浏览器断开或服务端随后遇到错误，也能查询到本轮任务并记录终态。代价是历史查询需要正确处理空 assistant 占位，不能把它显示成已完成回复。

### 不逐 token 写数据库

token 流速高，逐 token 更新会造成大量短事务和写放大。当前策略是在内存累积文本，正常结束、取消或异常时一次性更新助手消息和任务状态。代价是服务进程异常终止时，最后尚未落库的少量 token 可能丢失。

### 幂等和会话并发控制交给数据库兜底

前端禁用发送只能覆盖单页面；多标签页、网络重试或直接调 API 时仍会并发。代码先检查已有任务，迁移再用唯一约束处理并发竞态：重复请求返回已有任务；不同请求同时争抢同一会话时，部分唯一索引阻止第二条 `generating` 记录。

### 只把 done 视为成功

网络连接结束不等于模型正常完成。SSE 消费器会记录是否收到 `done`；未收到时前端进入失败/取消处理，服务端将任务写入对应终态。这样可以避免截断内容被当作完整回答保存为成功。

## 面试重点

### 一次 AI 流式对话为什么需要生成任务表

- **面试官提问**：你为什么没有只用 `Message` 表，而是增加了 `ChatRun`？
- **难度 / 考察意图**：必须掌握；考察数据建模与业务边界。
- **实现证据**：`prisma/schema.prisma`、`lib/services/chatRunService.ts`。
- **回答要点**：消息是静态对话内容；一次调用还需要请求 ID、状态、失败原因和时间。把运行态单独建模后，可以追踪生成中、成功、取消、失败，也能避免把调用信息污染展示消息。
- **参考回答**：原先浏览器在流结束后一次性保存消息，服务端不知道一轮调用是否已经创建、是否被取消。`ChatRun` 将一次回复建成独立实体，并关联 user 和 assistant 两条消息。这样服务端可以在模型调用前原子创建记录，在结束时用状态机更新；未来做回复版本或运行统计也不需要改动 `Message` 的基础语义。
- **追问路径**：为什么 assistant 要先创建空占位？为什么不把每个 token 存库？服务进程重启时如何处理 generating 任务？
- **失分点**：只回答“方便管理”，没有说明 Message 与调用运行态的边界。

### 事务具体保证了什么

- **面试官提问**：你这里的事务包含哪些写操作，失败时解决了什么问题？
- **难度 / 考察意图**：必须掌握；考察事务原子性及其边界。
- **实现证据**：`createChatRunRecord` 与 `createOrGetChatRun`。
- **回答要点**：同一个事务创建 user Message、assistant Message、ChatRun，并更新 Conversation 时间。任一操作失败，初始记录整体回滚，模型调用不会启动。
- **参考回答**：事务保证的是“本轮初始化”要么完整存在，要么完全不存在，避免只落 user 消息或只落任务记录。生成过程跨越网络调用，不能放在长事务中；模型返回后的 assistant 内容和任务终态通过一个新的短事务更新，避免长期占用数据库资源。
- **追问路径**：为什么不把上游模型调用也放进事务？终态更新如何保证一致？如果终态落库失败怎么办？
- **失分点**：把事务说成“能保证整个网络请求绝不失败”。

### 幂等请求和并发请求如何区分

- **面试官提问**：重复点击、网络重试、多标签页同时发送，分别如何处理？
- **难度 / 考察意图**：必须掌握；考察幂等、约束和并发竞态。
- **实现证据**：`ChatRun_conversationId_clientRequestId_key`、`ChatRun_one_generating_per_conversation`、`createOrGetChatRun`。
- **回答要点**：相同 `clientRequestId` 是同一请求，应复用已有任务；不同请求 ID 但同一会话同时生成，是会话并发冲突，应拒绝第二条；不同会话可并行。
- **参考回答**：客户端每轮生成产生稳定 `clientRequestId`。数据库用会话 ID 与请求 ID 的复合唯一约束防止同一次请求重复落库。对于两个不同请求同时进入同一会话，数据库部分唯一索引只允许一条 `generating` 任务；代码捕获唯一约束异常后返回“会话正在生成”。这样前端状态只是体验优化，数据库才是最终正确性保障。
- **追问路径**：为什么仅靠先查询再插入不够？部分唯一索引为什么比普通索引合适？多实例部署后该方案是否仍然有效？
- **失分点**：把“重复请求”和“不同内容的并发请求”混为一谈。

### 如何定义 SSE 的成功、失败与取消

- **面试官提问**：浏览器读到流结束时，为什么不能直接认为生成成功？
- **难度 / 考察意图**：必须掌握；考察流式协议和异常处理。
- **实现证据**：`types/chat.ts`、`lib/api/sse.ts`、`app/api/chat/route.ts`、`lib/api/sse.test.ts`。
- **回答要点**：TCP/HTTP 流结束可能来自断网、代理断开、上游异常。协议要求收到 `done` 才代表完整成功；`cancelled` 代表用户主动停止；`error` 传递受控错误码。
- **参考回答**：我将上游输出统一封装成 JSON SSE 事件。前端 `consumeSseStream` 显式记录 `receivedDone` 和 `receivedCancelled`。没有 `done` 时不会把内容当成成功；服务端根据取消、超时和异常更新 `ChatRun`。这避免了半截回复在刷新后被误标为完整结果。
- **追问路径**：SSE 帧被拆分时如何解析？`done` 已发出但浏览器没收到怎么办？错误码为什么不能直接透传上游异常文本？
- **失分点**：只谈前端流式展示，不谈服务端终态和数据持久化。

### 超时与取消如何真正传到 DeepSeek

- **面试官提问**：点击“停止生成”后，怎么保证模型调用也停止？超时分几类？
- **难度 / 考察意图**：应当理解；考察 SDK、AbortSignal 和可靠性。
- **实现证据**：`lib/ai/client.ts`、`app/api/chat/route.ts`。
- **回答要点**：HTTP request 的 `AbortSignal` 传给上游 `createChatCompletionStream`；服务端分别设置首 token、空闲流和总时长超时；SDK 有默认 90 秒 timeout 与一次重试。
- **参考回答**：前端中止 fetch 后，服务端监听 `request.signal`，再中止上游控制器，SDK 调用接收相同的 signal。首 token 超时用于发现模型迟迟未开始响应，空闲超时用于发现流卡住，总超时限制一轮资源占用。取消时保存已收到的文本并标记 cancelled；超时和上游错误写为 failed，并记录受控原因。
- **追问路径**：客户端断开能否保证云端模型一定停止？SDK 重试和业务超时会怎样叠加？如何从日志和指标评估 timeout 数值？
- **失分点**：声称 AbortSignal 能百分之百终止第三方服务端生成。

### 重新生成为什么不先删除旧回复

- **面试官提问**：重新生成时，如何避免新回答失败后旧回答也丢失？
- **难度 / 考察意图**：应当理解；考察失败恢复与产品数据安全。
- **实现证据**：`lib/stores/chatStore.ts` 的 `regenerateMessage`。
- **回答要点**：先保留原回复，创建新的候选生成轮次；只有后续确认产品要替换时，才应由服务端事务处理旧分支替换或截断。
- **参考回答**：旧实现先删旧回答和后续消息，再请求模型，失败会造成不可恢复的数据损失。现在重新生成复用原 user 内容，但不删除既有历史，候选失败时旧内容仍保留。当前版本以新增轮次表示候选结果，尚未实现回复版本切换界面；这是明确的产品边界。
- **追问路径**：如果要做到“替换旧回复”而不是新增轮次，数据库怎么设计？如何事务删除后续分支？怎样支持多个候选版本？
- **失分点**：说“已经实现了完整版本历史界面”；当前代码没有该界面。

## 面试风险与待补强

- OpenSpec 中仍有验证任务未完成：缺少 ChatRun 的事务、幂等唯一约束、同会话并发拒绝的集成测试。
- 当前 SSE 单元测试覆盖 `done`、`cancelled`、`error` 和未收到 `done`；路由层的超时、上游 SDK 异常及真正取消传播仍需 mock 上游流来测试。
- 前端缺少发送重复点击、失败重试、重新生成失败保留旧回复的组件测试。
- 当前并发控制依赖 PostgreSQL 约束，在多实例下仍能保证数据库写入正确，但进程内 `Map` 限流不具备跨实例一致性。生产环境应迁移到 Redis 或网关限流。
- `ChatRun` 处于 generating 时若服务进程被强制终止，当前没有后台恢复器；可通过定时扫描超时 generating 任务并标记 failed 来演进。
- `clientRequestId` 的重复请求当前服务层可复用已有任务；路由层对已有任务的返回体验仍可继续优化为可查询的任务状态或恢复入口。

## 一分钟项目讲解

这一阶段我解决的是 AI 流式聊天“能回复但不够可靠”的问题。以前浏览器接收完模型流再保存消息，所以刷新、断流或重复提交会造成丢失和重复。我的做法是把每次回复抽象成 `ChatRun`：服务端先用事务创建 user 消息、assistant 占位和 generating 任务，再调用 DeepSeek。请求使用 `clientRequestId` 做幂等，同一会话用数据库部分唯一索引限制并发生成。流协议上只有 SSE `done` 表示成功；取消、超时和异常都会持久化成对应终态，并保留已接收文本。前端保存 runId 和失败恢复信息，重试不再只是刷新页面。构建已通过，SSE 事件和既有消息列表测试已覆盖；下一步是补数据库并发集成测试和前端失败恢复测试。
