# 项目面试复盘：Embedding、向量检索与 RAG

> 日期：2026-10-13
> 分析范围：当前 Change 2.4 实现
> 岗位：AI 全栈
> 场景：轻量复盘 / 秋招技术一面

## 证据与边界

- 已阅读：`lib/rag/config.ts`、`lib/rag/embeddings.ts`、`lib/rag/service.ts`、`lib/rag/retrieval.ts`、`lib/rag/context.ts`、`app/api/chat/route.ts`、`scripts/embed-documents.ts`、`prisma/migrations/20261012153000_embedding_tasks_and_vector_index/migration.sql`、`docs/embedding-retrieval-rag.md`。
- 已验证事实：`npm run verify:embedding-rag`、`npx prisma validate`、`npm run lint` 与 `npm run build` 均通过；本地 pgvector 数据库已确认创建 `EmbeddingTask` 和 HNSW 索引。
- 待确认：暂无真实用户检索质量、吞吐量、Embedding 成本或线上延迟指标，面试中不要虚构这些数据。

## 实现概览

调用链为：受控 CLI 从已授权且已激活的 `DocumentChunkSet` 读取缺失向量的 `DocumentChunk` → `createEmbeddings()` 批量调用 Embedding API、校验维度、有限重试 → 参数化 SQL 写入 `Embedding.vector`，并记录 `EmbeddingTask` 进度和失败项。聊天端在 `RAG_ENABLED=true` 时，以已认证用户和最新问题调用 `retrieveRelevantChunks()`；检索 SQL 在数据库中同时施加知识库权限、活动切片集、模型/维度与相似度过滤；`buildRagContext()` 再将结果裁剪成带 `[来源N]` 标签的证据包，注入模型 system message。

## 关键决策与取舍

- 使用 `chunkId + model + contentHash` 的唯一约束完成向量化幂等，避免重复计费；内容或模型变化才重新生成。
- 把用户权限条件写入检索 SQL，而不是只在上层做判断；私有知识库仅匹配 `ownerId`，系统知识库可被已认证用户读取。
- 采用 pgvector 的余弦距离和默认模型 `text-embedding-3-small` 的 1536 维 HNSW 部分索引；模型升级须新增对应索引/迁移，不能混用维度。
- RAG 默认关闭。未配置独立 Embedding 密钥时，原有聊天功能继续可用；启用后检索失败返回 503，而不伪造来源或静默用客户端资料降级。
- 当前是同步 CLI 批处理，而非队列系统，适合小范围导入和可验证开发阶段；大规模任务需演进为后台队列和更细粒度的失败重试。

## 面试重点

### 1. 你为什么要在法律知识库中引入 RAG？

- **面试官提问**：现有聊天已经能调用大模型，为什么还要加 Embedding、向量检索和 RAG？
- **难度 / 考察意图**：必须掌握；考察是否理解 RAG 的问题边界，而不是只会调用 SDK。
- **实现证据**：`lib/rag/retrieval.ts`、`lib/rag/context.ts`、`app/api/chat/route.ts`。
- **回答要点**：法律资料长且有版本、来源和权限边界；不能把全部文档塞进 Prompt；先召回少量相关切片可降低上下文成本并保留页码/章节；RAG 不能保证事实正确，仍需来源约束与质量评估。
- **参考回答**：我把 RAG 当作“给模型提供受控证据”的能力，而不是单纯让回答更长。法律文档如果整体塞入上下文，成本高、容易超窗口，也无法说明依据。这个实现先对结构化切片做向量检索，只选 Top-K 的已授权片段，再把文档标题、页码、章节和 `[来源N]` 一起放进 system message。这样模型有可引用依据；如果没有足够资料，Prompt 要求它明确说明不能从知识库确认。它不能消除幻觉，所以后续还需要用测试集评估召回和引用准确性。
- **追问路径**：
  1. RAG 和微调分别适合解决什么问题？
  2. 向量召回错误时，生成模型会有什么风险？
  3. 你如何为法律场景评估 Top-K 召回与引用准确率？
- **评价与失分点**：不要回答“RAG 可以让模型知道私有知识”就结束；需讲清来源、权限、上下文成本和幻觉限制。

### 2. 向量化任务为什么能安全重跑？

- **面试官提问**：Embedding API 有成本也会失败。你如何避免重复生成，并让任务从失败处恢复？
- **难度 / 考察意图**：必须掌握；考察幂等、重试和任务状态设计。
- **实现证据**：`prisma/schema.prisma` 的 `Embedding` 唯一约束与 `EmbeddingTask`；`lib/rag/service.ts`；`lib/rag/embeddings.ts`。
- **回答要点**：以切片 ID、模型和内容哈希作为唯一身份；查询时跳过当前模型、维度和哈希都匹配的记录；429/5xx 有有限重试；每个批次更新成功数、失败数和失败切片；重跑只补缺失项。
- **参考回答**：我没有把“文档已向量化”当成一个布尔值，而是将向量绑定到具体切片、模型和内容版本。数据库对 `(chunkId, model, contentHash)` 做唯一约束，批处理前会过滤掉已有相同内容哈希的向量，因此重跑不会重复付费。模型调用对 429 和 5xx 做有限重试；最终失败的批次会在 `EmbeddingTask` 保存失败切片和错误信息，已成功批次保留。再次运行时仍从缺失向量开始处理。当前实现的限制是任务在 CLI 同步运行，没有单切片级队列，需要大规模化时再拆成后台任务。
- **追问路径**：
  1. 内容变了但 `chunkId` 没变，为什么还要重新生成？
  2. 为什么模型名和维度也要纳入版本判断？
  3. 如果两个任务同时处理同一切片，如何避免竞态？
  4. 如何给重试加入退避和限流？
- **评价与失分点**：不要说“捕获异常再重试”即可；须交代幂等键、部分成功和失败后的可恢复性。

### 3. 你如何做多租户知识库的权限隔离？

- **面试官提问**：攻击者把别人的 `knowledgeBaseId` 传到检索接口，你如何保证不会泄露文档或向量？
- **难度 / 考察意图**：必须掌握；考察鉴权位置和数据层防御。
- **实现证据**：`lib/rag/access.ts`、`lib/rag/retrieval.ts`、`lib/rag/service.ts`、`app/api/chat/route.ts`。
- **回答要点**：先由 `requireApiSession()` 取得服务端身份；指定知识库时 `assertKnowledgeBaseAccess()` 校验；检索 SQL 仍包含 `(scope = system OR ownerId = userId)`；客户端不提供可信的向量、资料正文或来源标签；不返回资源存在性信息。
- **参考回答**：我把知识库当作权限边界，而不是相信前端筛选条件。聊天接口首先从 Auth.js session 取得 `userId`，再在检索 SQL 中限制为系统知识库或 `ownerId` 等于当前用户的私有库。即使客户端伪造 `knowledgeBaseId`，它也只能进一步缩小已经授权的集合，不能扩大范围。对于指定知识库还会先做访问校验；客户端提交的来源正文和向量都没有被用于构建 RAG 上下文。这样服务端身份和数据库条件形成双层约束。
- **追问路径**：
  1. 为什么只在 Route Handler 中校验不够？
  2. 系统知识库与私有知识库的授权模型有什么不同？
  3. 如何防止“无权”和“资源不存在”产生可枚举差异？
  4. 如果未来有团队知识库和 RBAC，查询如何演进？
- **评价与失分点**：不能只说“前端隐藏入口”或“传 userId”；真实边界必须由 session 和服务端查询决定。

### 4. pgvector、余弦距离和 HNSW 是怎么选的？

- **面试官提问**：为什么向量放 PostgreSQL？为什么选余弦距离和 HNSW 索引？
- **难度 / 考察意图**：应当理解；考察数据库/检索基础与工程取舍。
- **实现证据**：`Embedding.vector`、`lib/rag/retrieval.ts` 的 `<=>` 查询、迁移中的 `vector_cosine_ops` 和 HNSW 索引。
- **回答要点**：项目已有 PostgreSQL 和知识库关系数据；pgvector 减少新系统与同步成本；`<=>` 是余弦距离，`1 - distance` 转为相似度；HNSW 是近似最近邻索引，牺牲建索引/存储换低延迟；索引固定为 1536 维且对模型做部分过滤。
- **参考回答**：当前阶段优先选择 pgvector，是因为元数据、权限关系、文档和切片本来就在 PostgreSQL 中，可以在一次参数化查询中同时做权限过滤和向量排序，降低维护独立向量库的复杂度。检索使用余弦距离 `<=>`，再转成相似度阈值。HNSW 的优势是大规模近邻查询快，但它是近似索引，也有更多内存和建索引成本。因为索引要求统一向量维度，我为 `text-embedding-3-small` 的 1536 维建立了部分表达式索引；模型升级不能直接混用，需要单独迁移。
- **追问路径**：
  1. HNSW 与 IVFFlat 的主要取舍是什么？
  2. 近似检索怎样影响召回率，如何测量？
  3. 为什么索引要与模型维度绑定？
  4. 什么时候考虑迁移到专用向量数据库？
- **评价与失分点**：不要把 HNSW 说成“绝对最快”；应主动说明近似性、内存/构建成本和评估需要。

### 5. RAG 上下文如何控制长度并防止伪造引用？

- **面试官提问**：拿到检索结果后，为什么还要做上下文裁剪和来源标签？
- **难度 / 考察意图**：应当理解；考察 Prompt 编排与安全边界。
- **实现证据**：`lib/rag/context.ts`、`lib/ai/context.ts`、`app/api/chat/route.ts`、`.env.example` 的 RAG 参数。
- **回答要点**：限制 Top-K、单切片字符数和总字符数，避免挤占聊天历史/输出预算；来源标签由服务端连续生成，包含标题、章节、页码；Prompt 要求只依据资料回答、引用标签或表达不确定；客户端字段不被信任。
- **参考回答**：检索结果不应该原样全部拼接，否则长片段会耗尽上下文并淹没用户问题。当前实现通过 `RAG_TOP_K`、单片段和总上下文字符上限，把资料裁剪成有限证据包。每段由服务端生成 `[来源N]`，并携带文档标题、章节和页码，然后和法律助手的 system prompt 一起注入模型。客户端不能直接提交可信来源或正文，因此它无法伪造被模型引用的资料。这里的局限是字符数只是近似预算，后续可用 tokenizer 做更精确的 token 控制。
- **追问路径**：
  1. 为什么 system prompt 仍然不能保证模型不幻觉？
  2. 如何防止文档正文中的 Prompt Injection？
  3. RAG 上下文与聊天历史该如何分配 token 预算？
  4. 用户要求“不要引用资料”时，系统应如何处理？
- **评价与失分点**：不要把来源标签说成安全证明；它只是可追溯设计，需要结合检索质量和输出评估。

## 面试风险与待补强

- 当前验证覆盖向量格式和 RAG 上下文构建；尚未用真实 Embedding API、真实语料和端到端聊天请求测出召回、延迟、成本或引用正确率。
- `EmbeddingTask` 记录批次状态，但不是分布式队列；进程中断后的自动调度、并发互斥和任务抢占仍是后续演进点。
- `RAG_ENABLED` 默认关闭，真实启用前需要配置独立 `EMBEDDING_API_KEY` 并先为活动切片执行向量化。
- 数据库存在一条已回滚的历史 Prisma 迁移记录，导致 Prisma 7 schema engine 自动迁移报空错误；本阶段迁移已被事务执行并校验，但这应如实说明为工程遗留问题。
