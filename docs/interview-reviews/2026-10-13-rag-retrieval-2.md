## 高概率跨模块问题

### 1. 从用户发起聊天到模型输出，整条调用链是什么？

- **面试官提问**：请从前端发一个问题开始，讲清楚后端如何鉴权、检索、调用模型和返回流式结果。
- **难度 / 考察意图**：必须掌握；验证候选人是否真正理解自己项目的端到端链路。
- **实现证据**：`app/api/chat/route.ts`、`lib/auth/require-api-session.ts`、`lib/services/messageService.ts`、`lib/rag/retrieval.ts`。
- **参考回答**：请求进入 `POST /api/chat` 后，先通过 `requireApiSession()` 获取服务端 session 的 `userId`。随后按 `conversationId + userId` 从数据库加载会话历史，因此客户端不能冒充别人的会话。系统从历史与本轮内容找出最新用户问题，并先进行 jailbreak 检测和限流。若 `RAG_ENABLED=true`，才用用户身份生成问题向量，在授权知识库范围内检索，构造有来源的上下文。最后把 system prompt、RAG 证据和裁剪后的聊天历史交给 OpenAI 兼容流式接口，并把上游增量重新编码为 SSE `token` / `done` 事件返回。
- **追问路径**：
  1. 流开始前和流开始后错误分别如何处理？
  2. 为什么聊天历史必须从服务端读？
  3. RAG 检索失败时为什么返回 503，而不是继续假装带知识库回答？
  4. 如果浏览器中断连接，如何进一步支持取消上游请求？

### 2. RAG 与会话鉴权为什么必须组合设计？

- **面试官提问**：会话已经按用户隔离了，为什么检索还要再次做知识库权限过滤？
- **难度 / 考察意图**：必须掌握；考察纵深防御与资源边界理解。
- **实现证据**：`listConversationMessagesForChat()` 的会话归属校验；`retrieveRelevantChunks()` 的 `knowledge_base.scope / ownerId` 条件。
- **参考回答**：两者保护的资源不同。会话鉴权防止读到别人的聊天记录；知识库鉴权防止模型拿到别人的文档内容。即使攻击者有自己的合法会话，也不应该借检索查询到其他用户的私有资料。所以 RAG 查询不能继承“会话合法就默认可查所有文档”的假设，而要把当前 userId 写入数据库过滤条件。这是分层授权：入口验证身份，数据查询验证资源归属。
- **追问路径**：
  1. 为什么不只校验前端传来的 knowledgeBaseId？
  2. 如果新增组织、团队与角色，SQL 条件会怎么演进？
  3. 应如何设计越权测试？

### 3. 你的 Prompt Injection 防护做到了什么、没做到什么？

- **面试官提问**：用户或知识库文档中出现“忽略系统指令”时，系统如何防护？
- **难度 / 考察意图**：应当理解；考察 AI 安全边界与诚实表达。
- **实现证据**：`lib/ai/prompts.ts` 的角色约束、`lib/ai/jailbreak.ts` 的请求检测、`lib/rag/context.ts` 的资料边界提示。
- **参考回答**：现有防护分三层：system prompt 固定法律助手角色和边界；对最新用户消息做已知 jailbreak 模式检测；RAG 资料由服务端构造，并明确标成“仅供参考的资料”，要求模型不把资料当作更高优先级指令。但这不是绝对防护：规则检测会漏掉变体，也可能误伤正常表达；文档正文仍可能含有恶意指令。因此生产演进要增加文档清洗/隔离、结构化引用、输出审核和红队测试，而不是声称 Prompt 已经完全安全。
- **追问路径**：
  1. 为什么仅靠关键词黑名单不可靠？
  2. 如何降低文档内指令对模型的影响？
  3. 安全策略与正常法律问答的可用性如何平衡？

### 4. 流式 SSE 为什么需要“重打包”，而不是直接透传供应商响应？

- **面试官提问**：为什么不直接把 OpenAI/DeepSeek 的 SSE 原样返回给浏览器？
- **难度 / 考察意图**：应当理解；考察 API 边界、供应商解耦和错误处理。
- **实现证据**：`app/api/chat/route.ts` 的 `extractDeltaText()`、`encodeSseEvent()` 与 SSE `token/done/error` 事件。
- **参考回答**：供应商的 SSE 协议、字段和错误格式可能不同，浏览器直接依赖会让前端与具体模型供应商耦合。当前路由在服务端只取文本增量，重打包为稳定的 `token`、`done` 和 `error` 事件。这样替换模型供应商时前端协议不变，也避免把上游原始元数据或异常直接暴露出去。代价是我们要在服务端维护事件转换和使用量记录。
- **追问路径**：
  1. HTTP 流开始前与开始后如何返回错误？
  2. 如何处理 backpressure 和客户端取消？
  3. 怎样避免代理层缓冲 SSE？

### 5. 为什么 RAG 还需要限流、Token 预算和成本控制？

- **面试官提问**：RAG 只多了一次检索，为什么要关注限流和 Token？
- **难度 / 考察意图**：应当理解；考察 AI 应用的成本与可靠性意识。
- **实现证据**：`lib/ai/rateLimit.ts`、`lib/ai/tokenizer.ts`、`app/api/chat/route.ts`、`lib/rag/config.ts`。
- **参考回答**：RAG 至少增加问题向量化调用和检索上下文；召回片段过多还会增加输入 Token，影响模型调用成本、延迟和上下文质量。当前系统已有按用户的请求频率和日 Token 配额，聊天历史按输入预算裁剪；RAG 进一步限制 Top-K、每片字符数和总上下文字符数。当前字符上限只是近似预算，后续应将 RAG 证据和聊天历史一起按 tokenizer 精确分配，并分别记录 embedding 与 completion 的成本和延迟。
- **追问路径**：
  1. 为什么字符数不能完全等价于 token 数？
  2. 检索结果多时，优先裁剪历史还是证据？
  3. 如何设计按用户、知识库和模型维度的成本指标？

### 6. 你如何处理 Prisma 迁移失败这一真实工程问题？

- **面试官提问**：你提到迁移工具报错，最后是怎么排查和处理的？
- **难度 / 考察意图**：加分深挖；考察排障过程、数据安全意识和是否掩盖问题。
- **实现证据**：`docs/embedding-retrieval-rag.md` 的验证记录；数据库 `_prisma_migrations` 中存在已回滚的历史切片迁移记录。
- **参考回答**：我先确认数据库容器健康，再通过迁移记录定位到一条历史迁移失败后已回滚的记录。Prisma 7 schema engine 因这个遗留状态返回空错误，无法继续自动部署。由于本阶段迁移是新增表、外键和索引，没有删除或重写业务数据，我使用 PostgreSQL 单一事务执行已版本化的 SQL，并核对 `EmbeddingTask`、HNSW 索引和迁移追踪记录。这个方案只是在开发环境解除阻塞，不能把它包装成最佳实践；真正的后续工作是修复历史迁移记录并恢复标准 `prisma migrate deploy` 流程。
- **追问路径**：
  1. 为什么不能直接删除 `_prisma_migrations` 的记录？
  2. 什么情况下绝不能手动执行 migration SQL？
  3. 如何在生产环境降低迁移风险？
- **评价与失分点**：回答重点是先诊断、最小影响、事务和验证；不要说“工具报错就手动跑 SQL”而不说明边界。

### 7. 如果系统有十万份法律文档，当前方案哪里会先成为瓶颈？

- **面试官提问**：不要求你已经做到十万文档；如果规模上去，你会怎么评估和演进？
- **难度 / 考察意图**：加分深挖；考察扩展性思维，避免虚构现有能力。
- **实现证据**：当前 `embedAvailableChunks()` 通过同步 CLI 分批处理；检索使用 pgvector HNSW；没有生产规模指标。
- **参考回答**：当前同步 CLI 适合开发和小规模受控导入，规模增大后首先要测量 Embedding API 吞吐、队列积压、数据库索引大小/构建时间、检索 P95、召回率和每份文档成本。演进上会把批处理放进持久化队列，按文档或切片分片并支持断点续跑；对索引参数做压测；引入混合检索、重排序和缓存。是否迁移专用向量库取决于测量结果、过滤复杂度和运维成本，而不是预先假设 PostgreSQL 一定不够用。
- **追问路径**：
  1. 为什么先测量再选专用向量库？
  2. 如何避免批量重嵌入影响在线检索？
  3. 如何实现新旧 Embedding 模型的平滑切换？

## 面试风险与待补强

- 面试官常从“RAG 原理”跳到“端到端安全、流式协议、限流和数据库迁移”；要能用具体调用链回答，而非重复概念。
- 不要声称当前已有异步队列、混合检索、重排序、真实召回指标或生产级容量；它们尚未实现。
- 对手工迁移处理要诚实：它是对历史 Prisma 迁移记录异常的开发环境补救，不应取代标准迁移流程。
