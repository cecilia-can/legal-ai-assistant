# 知识库管理（Change 2.5）

## 启动与入口

聊天侧栏点击「知识库管理」，或登录后访问 `/knowledge-bases`。

```powershell
# 部署或新环境先应用已有增量迁移，再生成客户端；不需要重置数据库。
npx prisma migrate deploy
npx prisma generate

# 终端一：应用（也会沿用既有的会话记忆 worker 启动逻辑）
npm run dev

# 终端二：知识库文档处理 worker
npm run knowledge:worker

# 只领取并执行一个任务，适合调试
node node_modules/tsx/dist/cli.mjs scripts/run-knowledge-worker.ts --once
```

生成 Prisma Client 或应用 migration 后，重启已运行的 Next.js 服务，避免开发进程缓存旧模型。生产环境由进程管理器分别维护应用与 worker。它们需要相同数据库配置、同一套解析/模型配置以及可共享读写的持久化目录。

当前 worker 使用项目已有的 `tsx`（位于 devDependencies）。部署 worker 环境时须包含该工具，或先单独打包 worker，不能直接省略开发依赖后假定此命令仍可执行。

## 一次完整操作

1. 创建私有知识库。系统知识库只读，网页端不能修改 scope 或替其他用户建库。
2. 上传一份 PDF、DOCX、DOC、HTML 或 UTF-8 TXT。默认单文件最大 20 MiB，文件接收后即排队解析。
3. 打开文档详情，等待解析完成，检查「规范化正文」。来源没有物理页码时明确显示无物理页码，不生成假页码。OCR 文档进入双栏审核工作区：原始 PDF 只加载一次，页码控制同步切换原图与识别文本；可逐页修改并保存，全文检查完毕后只需点击一次「确认全文审核完成」。
4. 点击「生成 / 复用切片」，在「切片与质量」查看章节、页码、质量提示与历史集。相同内容和策略会复用既有切片。
5. 点击「补齐当前模型索引」，按当前模型、维度和内容哈希补齐有效向量，已有正确向量不会重复调用模型。
6. 查看「处理记录」与阶段状态。索引 `N / M` 表示当前合格活动切片中有效向量的覆盖数，不代表检索效果评测已经通过。

上传只自动解析，切片与索引手动触发。解析、切片、索引是独立阶段，解析完成不等于可以 RAG 检索。网页聊天是否实际启用 RAG 仍由既有 `RAG_ENABLED` 控制。

OCR 文档在确认全文审核前不能切片、建索引或参与聊天检索。每次修改保存为新的规范化产物，原始 OCR 版本保留；修改或重新解析会撤销审核并停用旧切片。审核确认只对当前正文哈希有效，过期页面提交会收到冲突提示，刷新后再操作。历史 OCR 文档也需先确认才能重新进入检索。PDF 原件仅通过登录且具有知识库读取权限的接口预览。

## 状态、重试与删除

- 页面有活动任务时每两秒刷新，任务终态或离开页面后停止轮询。
- 排队一直不变化：检查 `knowledge:worker` 是否运行、是否连接同一数据库。请求不会在 HTTP 响应后偷偷执行未持久化工作。
- 同一文档重复提交相同操作返回已有活动任务；冲突操作和处理期间删除返回 409。
- worker 通过 60 秒租约、10 秒心跳和最多三次中断恢复维护执行权，过期执行者不能提交结果。正常失败会保留错误，用户检查原因后手动重试。
- OCR / DOC 转换需要已有 OCRmyPDF、Tesseract、语言包和 LibreOffice；缺失时显示对应阶段错误。无需这些软件也可先用短 TXT 验证主链路。
- 索引缺少凭证、维度错误或供应商失败时，页面明确显示失败，保留成功向量。重试只处理缺失项，不伪装为全部成功。
- 重新解析先暂存新结果，成功后才发布。失败保留旧可用正文；规范化内容发生变化后旧切片变为历史，需要重新切片和索引。
- 历史 CLI 文档的 `originalFileUri` 允许为空，仍可查看已有正文与切片。网页不会根据 sourceUri 读取任意服务器路径。网页重复上传可恢复同来源同哈希文档缺失的受控原件。
- 删除会清除文档、切片、向量及文档级任务记录。**原件与派生文件保留**，不是物理擦除功能；确认框会明确说明。不会删除外部 CLI 原始文件。已经生成的聊天回答会保留当时的来源文本快照，供继续核对；删除文档不会清除这些历史会话内容。

## 配置与存储

| 变量 | 默认值 / 作用 |
| --- | --- |
| `DOCUMENT_UPLOAD_ROOT` | `data/document-originals`；受控上传原件目录 |
| `DOCUMENT_UPLOAD_MAX_BYTES` | `20971520`；应用允许的文件大小，最大可配置为 100 MiB |
| `DOCUMENT_ARTIFACT_ROOT` | 沿用 `data/document-artifacts`；OCR、渲染与规范化产物 |
| `EMBEDDING_*` | 沿用 2.4 的独立服务凭证、模型和固定向量维度 |

原件以随机存储键独占创建，展示文件名不参与服务器路径拼接；读取检查目录和符号链接真实边界。受控文件路径不通过 API 暴露。DOCX 校验 ZIP 目录和实际解压上限；PDF 限制为 2000 页和 30 Mi 字符，规范化产物上限为 80 MiB；大文件请拆分导入。HTML 以文本与结构呈现，不执行脚本或加载其远程资源。

Nginx 等入口还应限制请求体大小，例如默认文件上限时使用 `client_max_body_size 21m;` 留出 multipart 开销。应用也按实际流量限制请求体，不依赖客户端 Content-Length。服务器持久化挂载必须覆盖上述两个目录；构建不会把用户文档打入应用镜像。

现阶段按单机应用和独立 worker 使用，不提供多机共享文件存储、管理员网页写入或文件自动回收。未新增 npm 依赖与外部队列。

## 验证方法

```powershell
# 网络无关的安全、API 和向量响应测试
npx vitest run lib/knowledge/storage.test.ts lib/knowledge/api.test.ts lib/rag/embeddings.test.ts

# 使用本机开发数据库的隔离验收
npm run verify:knowledge-management

# 项目检查
npm run lint
npm run build
```

隔离验收创建本轮随机测试账号、知识库和文件，结束时只清理这些数据库记录和本轮目录；不清库、不处理其他人的任务。它验证权限、并发去重、版本递增、真实 TXT 解析与结构切片、覆盖统计、任务恢复、重解析失败保留以及删除。

批次部分失败与恢复使用 **127.0.0.1 的 HTTP 模型替身与人工向量**，验证服务接口、写入、幂等和恢复，不等于真实语义检索或真实 Embedding 服务已通过。真实服务验收仍需有效凭证与供应商网络连接。

`scripts/knowledge-browser-fixture.ts` 是本地网页验收辅助脚本，创建随机临时账号和示例资料，使用固定测试密码 `KnowledgeSmoke2026!`。仅用于本地；完成后执行同脚本的 `--cleanup` 清理账号与数据库资料，文件按保留策略处理。账号信息存在被 git 忽略的 `data/knowledge-browser-fixture.json`，不要部署或分享此文件。
