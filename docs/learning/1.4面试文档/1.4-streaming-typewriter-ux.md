# Change 1.4：流式输出观感优化（卡顿 / 打字机 / 展示队列）

> Phase：1 ChatBot　|　分支：`feature_ai_api_streaming_260724`  
> 来源会话：[2b6411f7-d173-49a2-ad35-1c1151c54483](2b6411f7-d173-49a2-ad35-1c1151c54483) 起  
> 涉及文件：`lib/stores/chatStore.ts`、`lib/streaming/displayQueue.ts`、`components/chat/MessageList.tsx`  
> 日期：2026-07-27

---

## 1. 背景与现象

Change 1.4 接入 SSE 流式 AI 回复后，功能正确（Network 里 `data: {"type":"token",...}` 连续到达），但用户反馈：

> 助手回答虽然一点点出来，但**视觉上有点卡顿**，像是**分几次、每次出来一部分**，不像打字机那样一个字一个字匀速出现。

这与「流式链路是否打通」是两类问题：**链路通了 ≠ 观感像 ChatGPT**。

---

## 2. 完整数据链路

```text
DeepSeek 模型（token 流）
    ↓ OpenAI SDK chunk
lib/ai/client.ts  extractDeltaText()
    ↓
app/api/chat/route.ts  encodeSseEvent({ type:"token", text })
    ↓ HTTP ReadableStream（字节边界 ≠ SSE 帧边界）
浏览器 fetch + reader.read()
    ↓
lib/api/sse.ts  parseSseChunk → ChatStreamEvent[]
    ↓
lib/stores/chatStore.ts  展示策略（本文重点）
    ↓
React 重渲染 MessageBubble
    ↓
MessageList 粘底滚动（rAF 节流）
```

**关键认知：** `token`（模型语义单位）、`SSE 事件`（协议帧）、`reader.read()` chunk（TCP/HTTP 字节块）、`React 渲染帧`（~16ms）——**四者没有 1:1 关系**。

---

## 3. 根因分析

### 3.1 初版实现（优化前）

```ts
// chatStore：每个 token 立即 set
if (event.type === "token") {
  set((state) => ({ ... content: message.content + event.text }));
}
```

问题：

- 同一 `reader.read()` 内可能解析出 **N 个 token** → N 次 `set` → N 次 React 渲染（或批量后仍是一帧内连跳多段）
- 两次 `read()` 之间可能有 **100～300ms 空档** → 屏幕停住 → 突然多出一段
- 每个 token 还可能触发 `MessageList` 的 `scrollToBottom` → 布局抖动

### 3.2 用真实 Network 数据验证（DeepSeek 回复示例）

用户贴出的 Response 显示 token **已经很小、很碎**：

```text
"我是" / " **" / "Deep" / "Se" / "ek" / "**" / "，" / "由" / "深度" / "求" / "索" ...
```

说明：

| 误解 | 事实 |
|------|------|
| API 每次只发一大块 | ❌ 每行 `data:` 往往只有 1～4 字符 |
| 问题在 BFF 没转发 | ❌ BFF 已是 1 delta → 1 SSE 事件 |
| 问题在 token 太大 | ❌ 英文 `DeepSeek` 被拆成 `Deep`+`Se`+`ek` |

**真正原因：**

1. **`reader.read()` 批量到达** — 多行 `data:` 同批进前端，批次之间有间隔  
2. **UI 原样跟随网络 burst** — 无展示层平滑  
3. **Token 切分不规则** — 英文拆音节，合并显示时不像「逐字」  
4. **（次要）** 每 token 滚动 + 重渲染加剧跳动感

## 4. 优化演进（三阶段）

```mermaid
flowchart LR
  A[阶段 0<br/>每 token 立即 set] --> B[阶段 1<br/>rAF tokenFlush]
  B --> C[阶段 2<br/>displayQueue 展示队列]
```

### 阶段 0：每 token 立即更新 UI

| 项 | 说明 |
|----|------|
| 做法 | SSE `token` → 直接 `set()` 追加 `content` |
| 优点 | 实现最简单 |
| 缺点 | 跟随网络 burst；渲染/滚动次数过多 |
| 观感 | 顿一下、蹦一段 |

### 阶段 1：rAF 合并更新（`tokenFlush`，已移除）

**新增：** `lib/streaming/tokenFlush.ts`（后删除）

| 项 | 说明 |
|----|------|
| 做法 | token 写入 `pending`；`requestAnimationFrame` **每帧最多 flush 一次** 到 `set()` |
| 优点 | 渲染次数 ≤ 60/s；减轻 React 压力 |
| 缺点 | **同一 read 批次内的 token 合成一次 UI 更新** → 仍「一段段」出现 |
| 观感 | 卡顿减轻，但不像打字机 |

**同时：** `MessageList` 增加 `scrollToBottomOnFrame`，流式期间 **每帧最多 scroll 一次**（保留至今）。

### 阶段 2：展示层打字机队列（当前方案）

**新增：** `lib/streaming/displayQueue.ts`  
**替换：** `tokenFlush` → `createDisplayQueue`

| 项 | 说明 |
|----|------|
| 做法 | 网络层 `enqueue(text)` 尽快收进 buffer；展示层 rAF **按 ~22ms/字** 从 buffer `reveal` 到 UI |
| 优点 | **网络与展示解耦**；匀速打字机；积压时自适应加速 |
| 缺点 | 实现更复杂；`streamingConversationId` 需等队列排空才结束 |
| 观感 | 最接近 ChatGPT |

**默认参数（`displayQueue.ts`）：**

| 参数 | 默认值 | 含义 |
|------|--------|------|
| `msPerChar` | 22 | 每字展示间隔（ms） |
| `catchUpThreshold` | 36 | buffer 超过此长度开始加速 |
| 加速 | >36 字 → 2 字/ tick；>72 字 → 4 字/tick | 避免网络远快于展示时越积越多 |
| 收尾 | 网络结束且剩余 ≤12 字 | 一次性显示完毕 |

## 5. 方案对比总表

| 方案 | 网络→UI 关系 | 渲染频率 | 打字机观感 | 复杂度 | 本项目 |
|------|--------------|----------|------------|--------|--------|
| 每 token 立即 set | 1:1 跟随 burst | 极高 | ❌ 分段蹦 | 低 | 阶段 0（已弃） |
| rAF 合并（tokenFlush） | 每帧合并一批 | ≤60/s | ⚠️ 仍分段 | 中 | 阶段 1（已弃） |
| 展示队列（displayQueue） | 解耦，匀速 reveal | 可控 | ✅ 接近 ChatGPT | 中高 | **当前** |
| 改 BFF 逐字发送 | 人为拆小 SSE | 不变 | ❌ 无法解决 read 批量 | 低 | **不推荐** |
| 服务端节流 | 降低 SSE 频率 | 降低 | ⚠️ 增加首字延迟 | 中 | 未采用 |

## 6. 当前实现要点

### 6.1 `chatStore.ts` 流程

```text
sendMessage
  → 创建 displayQueue
  → consumeSseStream：token → displayQueue.enqueue(text)
  → 网络结束：markNetworkDone() + await waitUntilIdle()
  → onIdle：streamingConversationId = null
  → abort：displayQueue.cancel()，保留已显示文字，丢弃 buffer
```

**重要行为变化：** 网络 SSE 已 `{type:"done"}`，但输入框仍 disabled，直到 **展示队列排空**——与 ChatGPT「还在打字就不能发」一致。

### 6.2 `displayQueue` API

| 方法 | 用途 |
|------|------|
| `enqueue(text)` | 网络 token 入 buffer |
| `markNetworkDone()` | SSE 流结束，开始收尾逻辑 |
| `waitUntilIdle()` | Promise，队列展示完毕后 resolve |
| `cancel()` | abort 时停止并丢弃未展示 buffer |
| `flushSync()` | 错误场景立即展示剩余（API 保留，当前主路径未用） |

### 6.3 `MessageList` 滚动（阶段 1 保留）

流式期间 `contentScrollTrigger` 变化时调用 `scrollToBottomOnFrame("auto")`，与展示队列配合，避免每字都触发布局重算。

## 7. 性能影响：当前方案有没有优化？

**结论：** 展示队列的**首要目标是打字机 UX**，不是性能优化；但相对阶段 0（每 token 立即 `set`），**客观上显著减轻 React 与布局压力**。相对阶段 1（rAF 合并），性能**相当或略好**，主要收益仍在观感。

### 7.1 三阶段渲染频率对比

| 方案 | 大约 UI 更新频率 | 每次更新量 | React / 布局压力 |
|------|------------------|------------|------------------|
| 阶段 0：每 token 立即 `set` | 不固定；一次 `read()` 内可达 **几十～上百次** | 1 个小 token | **很高** |
| 阶段 1：rAF 合并（tokenFlush） | **≤ ~60 次/秒**（每帧最多 1 次 `set`） | 一帧内多个 token 合并 | 中等 |
| 阶段 2：displayQueue（**当前**） | **约 20～45 次/秒**（由 `msPerChar≈22` 决定） | 通常 1～4 个字符 | **较低且稳定** |

**典型场景：** Network 一次 `read()` 解析出 30 个 token 时——

- **阶段 0：** ~30 次 `set()` → ~30 次 MessageList 重渲染 + 多次 scroll  
- **阶段 2：** 30 个 token 先 `enqueue` 进 buffer，展示层按 ~22ms/字 `reveal` → **`set()` 次数有上限**

### 7.2 具体优化了哪些

1. **Zustand / React 重渲染** — 更新节奏由 **`msPerChar` 展示时钟**控制，不再跟着网络 burst 暴走。  
2. **MessageList 滚动** — 流式期间 `scrollToBottomOnFrame`，每帧最多 scroll 一次，不与每个 token 绑定。  
3. **主线程抖动** — 避免「瞬间 N 次 set + N 次 layout」造成的 Long Task；观感更顺，Performance 面板通常更好看。

### 7.3 额外成本（并非「白赚」的性能）

| 项 | 说明 |
|----|------|
| rAF 循环 | 流式期间每帧执行 `tick`，有少量 CPU，一般可忽略 |
| buffer 字符串 | 网络快于展示时会暂存未 reveal 文本，多占一点内存 |
| 展示延迟 | UI **故意晚于**网络，不是「更快显示全文」 |
| 尾部打字时间 | SSE `{type:"done"}` 后队列仍可能继续 reveal 若干字 |

### 7.4 与 rAF 合并的性能取舍

| 维度 | rAF 合并（阶段 1） | displayQueue（阶段 2） |
|------|-------------------|------------------------|
| 渲染上限 | ~60 次/秒 | ~20～45 次/秒（可调） |
| 单次 append 量 | 可能整批 token | 1～4 字符为主 |
| 观感 | 仍「分段蹦」 | 匀速打字机 |
| 若只追求最少 `set` | 略优（大批合并） | 略多几次但每次数值小 |

若**纯追求最少 React 更新**、不在乎观感，可以 rAF 合并 + 更大 chunk——但会回到「一段段蹦字」。当前方案是 **UX 优先，性能顺带改善**。

### 7.5 调参对性能与观感的影响

| 调整 | 观感 | 性能（`set` 频率） |
|------|------|---------------------|
| `msPerChar` ↓（如 18） | 打字更快、更丝滑 | 更新更勤，略增渲染 |
| `msPerChar` ↑（如 28～32） | 打字更慢 | 更新更少，更省 |
| `catchUpThreshold` ↓ | 更早加速、减少积压 | 加速档 `set` 次数可能增加 |

### 7.6 一句话

> **目的：** 打字机体验（网络层与展示层解耦）。  
> **性能：** 相对「每 token 立即 set」**有明显优化**；相对「纯 rAF 合并」**相当或略好**。  
> **不是：** 为性能而设计的方案——是 UX 方案，附带降低渲染频率。

## 8. 调参指南

在 `lib/streaming/displayQueue.ts` 修改：

```ts
const msPerChar = options.msPerChar ?? 22;        // 越小越快
const catchUpThreshold = options.catchUpThreshold ?? 36;
```

或在 `chatStore` 创建队列时传入：

```ts
createDisplayQueue(append, onIdle, { msPerChar: 18, catchUpThreshold: 48 });
```

**偏慢/偏快：** 优先调 `msPerChar`（18～30 常见）。  
**积压太多：** 降低 `catchUpThreshold` 或提高加速档位的字数。

## 9. 面试官追问与解答

### Q1：流式输出「卡顿、分段出现」一般怎么排查？

**答：**

1. **结论：** 先看 Network SSE 行频与 UI 更新频率是否一致；不一致则问题在客户端合并/渲染；一致但仍分段则是 token/read 批量本身。  
2. **原理：** 四层粒度 — token、SSE 帧、read chunk、渲染帧。  
3. **结合项目：** DevTools 看 `data:` 很密但 UI 跳 → 查 `chatStore` 展示策略；`data:` 本身成批 → `reader.read()` + 模型 burst。  
4. **加分：** 贴我们三阶段演进（立即 set → rAF → displayQueue）。

---

### Q2：为什么 rAF 合并了还是不像打字机？

**答：**

- rAF 解决的是 **渲染次数**（性能），不是 **时间均匀性**（体验）。  
- 同一帧内仍会把一批 token 一次性 append，批次之间仍有网络空档 → 观感仍是「段」。  
- 真打字机需要 **展示时钟** 与 **网络时钟** 分离 → displayQueue。

---

### Q3：展示队列和 double buffering / 视频播放有什么相似性？

**答：**

- 类似 **生产者-消费者**：网络生产字符串，UI 消费者按固定速率消费。  
- buffer 积压时加速（自适应 catch-up），类似视频 jitter buffer。  
- abort = 丢弃播放队列中未消费部分，已播放保留。

---

### Q4：`streamingConversationId` 为什么在网络 done 之后还不清空？

**答：**

- 用户可见的「还在生成」= **屏幕仍在打字**，不仅是 **socket 仍在收包**。  
- 若 done 立刻清空，用户可在打字未完成时发下一条 → 并发流式、体验混乱。  
- `waitUntilIdle()` 后再 `streamingConversationId = null`。

---

### Q5：abort 时 buffer 里未展示的字怎么办？

**答：**

- `displayQueue.cancel()`：停止 rAF、清空 buffer、**不** flush 到 UI。  
- 已 reveal 的内容保留在 `message.content` 中。  
- 与「取消生成保留 partial」产品语义一致。

---

### Q6：能否在 BFF 层做打字机，不让前端操心？

**答：**

- BFF 只能控制 SSE **发送节奏**，无法控制浏览器 **read 批量**。  
- 人为 sleep 发送会 **增加延迟**、占用 Serverless 时间。  
- 主流做法：**BFF 尽快转发**，**前端展示队列** 做 UX。

---

### Q7：中文 1 token 1 字，为什么还不像逐字？

**答：**

- 英文混排时 token 可能是 `Deep`/`Se`/`ek`。  
- 即使中文，**一次 read 仍可能含多个 token**，阶段 0/1 会成批显示。  
- displayQueue 按 **字符** reveal，与 token 边界无关（`enqueue` 拼字符串，按 char slice）。

---

### Q8：如何测试展示队列？

**答：**

- **单测：** mock `append` 回调，enqueue 快速写入 100 字，断言调用间隔 ≈ `msPerChar`。  
- **E2E：** 发送后观察 DOM `textContent` 长度随时间单调递增且平滑。  
- **对比：** 临时改回「每 token set」对比观感（勿合并主分支）。

---

### Q9：displayQueue 和 1.6 Markdown 渲染如何共存？

**答：**

- 1.4 纯文本 append 无冲突。  
- 1.6 若流式 Markdown 解析，仍应对 **已 reveal 的 content** 渲染；未 reveal 部分不解析。  
- 异步撑高（图片）需 `ResizeObserver` + 粘底补滚（见 [1.4-chat-scroll-ux.md](./1.4-chat-scroll-ux.md)）。

---

### Q10：性能上 displayQueue 比每 token set 更好还是更差？

**答：**

- **React 渲染：** 更好 — reveal 频率有上限（~22ms/字 + 加速档），见 [§7 性能影响](#7-性能影响当前方案有没有优化)。  
- **内存：** 多一个 string buffer，长回复可忽略。  
- **CPU：** rAF 循环轻量；总体优于 hundreds of set/s。  
- **延迟：** 展示略滞后于网络（故意），网络 done 后仍有尾部打字时间。  
- **定位：** UX 方案附带性能收益，不是纯性能优化。
