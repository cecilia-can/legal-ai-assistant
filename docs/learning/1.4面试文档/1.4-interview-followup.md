# Change 1.4 前端面试追问与解答思路

> 类型：Change 1.4 专项 · 面试向  
> 范围：`ai-api-streaming` spec 及其实现（SSE 流式、BFF、Zustand、fetch + ReadableStream）  
> 日期：2026-07-26

本文从**资深前端面试官**视角，列出针对 Change 1.4 的高频追问，并给出**解答思路**（不是背标准答案，而是「怎么组织回答、要点是什么、如何加分」）。

---

## 使用说明

- **解答思路** = 建议的回答结构 + 必提关键词 + 常见坑 + 加分项。
- 面试时用 **「结论 → 原理 → 结合项目 → trade-off」** 四段式，控制在 1～3 分钟/题。
- 本项目真实路径：`app/api/chat/route.ts`、`lib/api/sse.ts`、`lib/stores/chatStore.ts`、`lib/ai/client.ts`。

---

## 一、流式与协议（SSE / HTTP）

### Q1：你们的流式方案是怎么做的？为什么不用 WebSocket？

**解答思路：**

1. **结论**：`POST /api/chat` 返回 `text/event-stream`，body 是 SSE 帧 `data: {"type":"token","text":"..."}\n\n`；前端 `fetch` + `getReader()` 解析，不用 WebSocket。
2. **原理**：一轮问答是「客户端提交 messages → 服务端单向推送生成结果」，HTTP 流足够；WebSocket 适合高频双向、协作、语音。
3. **结合项目**：BFF（`route.ts`）从 DeepSeek SDK 抽 `delta.content`，重打包成自家 `ChatStreamEvent`，为 Phase 4 Agent 事件预留 `type` 字段。
4. **Trade-off**：比 plain text 多 JSON 包装，但比 WebSocket 简单、与 Vercel Serverless 更合拍。

**加分项：** 提到 TTFT（首 token 时间）、Vercel function duration 上限。

**减分项：** 说「流式就是 WebSocket」或「SSE 只能 EventSource」。

---

### Q2：既然用了 SSE，为什么不用 `EventSource`？

**解答思路：**

1. **结论**：`EventSource` 只能 **GET**，不能 POST body，不能方便带 `Authorization`；聊天必须把 **多轮 messages** POST 给 BFF。
2. **原理**：SSE 是 **wire format**（`data:` 行）；`EventSource` 只是消费 SSE 的一种 API；`fetch` + 手动解析是 POST 场景主流做法。
3. **结合项目**：`consumeSseStream` + `parseSseChunk` 在 `lib/api/sse.ts`。
4. **Trade-off**：要自己处理 remainder、UTF-8 stream decode，代码量比 EventSource 多，但更灵活。

**加分项：** 对比 ChatGPT 类产品也是 BFF + fetch 读流。

---

### Q3：`reader.read()` 返回的 chunk 和 SSE 帧、token 是什么关系？

**解答思路：**

1. **结论**：**三者没有 1:1 关系**；一次 `read()` 可能读到半帧、多帧或任意字节切分。
2. **原理**：`read()` 读的是 TCP/HTTP 字节管道；SSE 帧以 `\n\n` 分隔；token 是模型语义单位。
3. **结合项目**：`remainder` 缓冲 + `TextDecoder({ stream: true })` + `parseSseChunk` 的 `pop()` 机制。
4. **Trade-off**：不能假设「读一次解析一个 token」。

**加分项：** 画三层：DeepSeek → BFF enqueue 完整帧 → 浏览器 read 任意切分。

---

### Q4：为什么 BFF 不直接把 DeepSeek 的 SSE 透传给浏览器？

**解答思路：**

1. **结论**：透传会暴露 OpenAI 格式、前端与 DeepSeek 耦合；我们在 BFF 统一为 `{ type: "token" | "done" | "error" }`。
2. **原理**：BFF 职责是 **协议适配 + 藏密钥 + 统一错误**。
3. **结合项目**：`extractDeltaText` → `encodeSseEvent`。
4. **Trade-off**：多一次序列化/反序列化，换协议自主权和 Agent 扩展。

---

## 二、React / 状态管理（Zustand）

### Q5：流式更新为什么用 Zustand 而不是 Context 或 Redux？

**解答思路：**

1. **结论**：流式场景 **高频局部更新**；Zustand selector 可精确订阅，避免 Context 整树重渲染；比 Redux 轻量。
2. **原理**：1.3 已用 `conversationStore`；1.4 按 domain 拆 `chatStore`，职责清晰。
3. **结合项目**：`streamingConversationId` 控制输入禁用；`messagesByConversation` 按会话分桶。
4. **Trade-off**：两个 store 要在 `page.tsx` 编排（abort、删会话清消息）。

**加分项：** 提到 Phase 1.5 持久化时只扩展 chatStore action。

---

### Q6：每个 token 都 `set` 一次，性能有问题吗？怎么优化？

**解答思路：**

1. **结论**：**会有问题潜力**——当前实现每个 token 触发 Zustand `set` + 可能整列表重渲染；MVP 可接受，优化方向是 **batch/throttle**。
2. **原理**：`messages.map` immutable 更新 assistant `content`；token 多时有 O(次数 × 消息数) 更新。
3. **优化方案（任选讲 1～2 个）**：
   - `requestAnimationFrame` / 50ms 节流批量写入；
   - 流式期间单独 `streamingContent` 字段，done 再 merge；
   - `React.memo` MessageBubble（需 stable props）。
4. **Trade-off**：批量更新略牺牲「逐字」平滑度，换帧率。

**加分项：** 区分「体感性能」和「API 成本性能」（全量 history 在 1.7 优化）。

---

### Q7：乐观更新是怎么做的？失败怎么回滚？

**解答思路：**

1. **结论**：`sendMessage` 先插入 user + **空 assistant 占位**，再 fetch；失败时 **移除空 assistant**，保留 user，写 `error`。
2. **原理**：乐观 UI 提升响应感；流式失败与 abort 要区分——abort 保留已生成 partial content。
3. **结合项目**：`controller.signal.aborted` 时 catch 里直接 return，不写 error。
4. **Trade-off**：占位气泡在极短失败窗口可能闪一下。

---

## 三、请求生命周期与取消

### Q8：如何实现「停止生成」或切换会话时取消请求？

**解答思路：**

1. **结论**：`AbortController` 绑在 `fetch` 的 `signal`；`abortStream` 同时 `reader.cancel()`；模块级 `activeStreamConversationId` 丢弃迟到 token。
2. **原理**：仅 abort fetch 不够，还要忽略 abort 后已缓冲的 SSE 事件。
3. **结合项目**：新建聊天、切换会话、同会话新发消息都会 `abortStream()`。
4. **Trade-off**：同一时刻只允许一条活跃流（产品决策）。

**加分项：** 提到服务端应监听 request abort 停止读 upstream（当前可改进点）。

---

### Q9：流式 API 的错误怎么处理？和 JSON API 有何不同？

**解答思路：**

1. **结论**：分 **流开始前** 与 **流开始后** 两阶段。
2. **流开始前**：参数错、Key 缺失、DeepSeek 4xx → `jsonError` envelope（400/500/502），前端 `response.json()`。
3. **流开始后**：HTTP 200 已发出；中途错误用 SSE `{ type: "error" }` 或连接断开；前端 `consumeSseStream` throw / 清理空 assistant。
4. **结合项目**：与 `openspec/specs/api-response` 并存——JSON 路由用 envelope，流式 body 不用 envelope。

**减分项：** 说「流式也用 `{ code, message, data }` 包每一帧」。

---

## 四、架构与 BFF

### Q10：你们项目有后端吗？BFF 在哪？

**解答思路：**

1. **结论**：有后端，在 Next.js 服务端；`app/api/*` 是 **BFF 入口**，`lib/ai`、`lib/db` 是内部能力。
2. **原理**：全栈单体，不是独立 Java 服务；BFF ⊂ 后端，不是与后端并列的第四层。
3. **结合项目**：`/api/chat` 藏 `OPENAI_API_KEY`，浏览器只调同源 API。
4. **Trade-off**：多一跳延迟，换安全与协议统一。

---

### Q11：为什么不让浏览器直连 DeepSeek？

**解答思路：**

1. **结论**：API Key 会暴露在客户端；无法做统一限流、日志、换模型。
2. **原理**：生产环境 AI Key 必须 server-only。
3. **结合项目**：Key 只在 `lib/ai/client.ts` 读 `process.env`。
4. **Trade-off**：BFF 增加 Serverless 冷启动与超时风险。

---

## 五、实现细节（代码层）

### Q12：`parseSseChunk` 里 `remainder` 是干什么的？

**解答思路：**

1. **结论**：保存 **还没有 `\n\n` 结尾的不完整 SSE 帧**，与下次 `read()` 拼接后再解析。
2. **原理**：`split("\n\n")` 后 `pop()` 最后一段；完整帧进 `parseSseFrame`。
3. **易错点**：半帧不是 DeepSeek 发坏了，是 **浏览器 read 边界** 不对齐。
4. **加分项：** 流结束 `decoder.decode()` flush。

---

### Q13：`TextDecoder` 为什么要 `{ stream: true }`？

**解答思路：**

1. **结论**：UTF-8 多字节字符（中文）可能被拆在两个 `Uint8Array` chunk 之间；stream 模式让 decoder 记住不完整字节。
2. **原理**：不开启可能产生乱码或截断。
3. **结合项目**：`consumeSseStream` 循环里 decode，结束后无参 flush。

---

### Q14：为什么 `abortController` 放在 store 外面？

**解答思路：**

1. **结论**：AbortController 是 **副作用句柄**，不是 UI 状态；放 store 外避免无意义 re-render，且保证全局同一时刻一条流。
2. **原理**：Zustand 适合 serializable/UI 相关 state；模块级变量类似「单例资源管理」。
3. **加分项：** 也可放 store 的 ref 字段，但当前方案更简单。

---

## 六、方案对比类（面试官爱问）

### Q15：SSE 事件 vs plain text 流，你们为什么选 SSE？

**解答思路：**

| 维度 | plain text | SSE + JSON（本项目） |
|------|------------|----------------------|
| 前端解析 | 直接拼接 | 解析 `data:` + JSON |
| 扩展 Agent 事件 | 需自造分隔符 | 加 `type` 即可 |
| 对齐业界 | 弱 | 强 |
| 实现成本 | 低 | 中 |

**结论句：** 1.4 用精简版 B（token/done），为 4.x 留扩展，不选 WebSocket。

---

### Q16：为什么不用 Vercel AI SDK 的 `useChat` / `streamText`？

**解答思路：**

1. **结论**：SDK 省 boilerplate、内置流式；自研为了 **学习链路清晰**、与 roadmap 分 store、控制 SSE 事件协议。
2. **原理**：SDK 适合快速上线；教学/法律 Agent 长期要自定义事件与多 store。
3. **Trade-off**：自研要维护 sse 解析、错误边界；SDK 抽象掉细节。
4. **加分项：** 说「生产可评估迁移，BFF 边界可保留」。

---

### Q17：消息为什么只放内存？刷新就没了，怎么改进？

**解答思路：**

1. **结论**：spec 1.4 刻意不做持久化；Change 1.5 会加 messages API + DB。
2. **原理**：分阶段交付：先打通流式，再持久化，再 Token 限制（1.7）。
3. **改进路径**：1.5 加载历史；发送时 user/assistant 落库；流式可先内存展示再异步 save。

---

## 七、安全与工程化

### Q18：如何防止用户刷爆 AI 接口？

**解答思路：**

1. **结论**：1.4 **未做**；上线应在 BFF 加 **限流**（IP/用户）、配额、鉴权。
2. **思路**：Upstash Ratelimit、middleware、或 API Gateway。
3. **结合项目**：当前仅 `disabled` 输入防连点，无服务端 rate limit。
4. **加分项：** AI 按 token 计费，限流比传统 API 更重要。

---

### Q19：如何测试流式逻辑？

**解答思路：**

1. **单元测试**：`parseSseChunk` / `encodeSseEvent`（跨 chunk 用例）；`isChatStreamEvent`。
2. **集成测试**：mock `fetch` 返回 ReadableStream，喂固定 SSE 字节。
3. **E2E**：Playwright + mock `/api/chat` 或使用测试 Key。
4. **手动**：DevTools Network 看 `text/event-stream` 与 `data:` 行。

**加分项：** 专门测 abort 后不再 update store。

---

## 八、开放题（考察思维深度）

### Q20：如果 Agent 要展示「工具调用进度」，你会怎么改 1.4 架构？

**解答思路：**

1. **结论**：**不换 WebSocket**；在现有 SSE 上扩展事件类型即可。
2. **示例事件**：`tool_start`、`tool_result`、`token`、`done`。
3. **前端**：`switch (event.type)` 更新步骤面板 + 答案区；chatStore 或拆 `agentRunStore`。
4. **Trade-off**：UI 复杂度上升，传输层不变。

---

### Q21：长会话 context 太长，前后端分别怎么优化？

**解答思路：**

| 层 | 手段 |
|----|------|
| 前端 | 只展示最近 N 条；摘要气泡 |
| BFF | Token 计数、滑动窗口、截断 system 前历史 |
| 产品 | 1.7 Prompt/context 模块；Memory 摘要 |

**结合 roadmap：** Change 1.7 专门做，1.4 全量发送是刻意简化。
