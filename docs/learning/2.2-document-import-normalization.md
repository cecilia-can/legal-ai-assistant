## 沉淀 2026-08-15（第 1 次）

### OCR 的职责是补齐扫描 PDF 的可检索文字层

- **来源问题**：为什么要接入 OCR；图片型 PDF、文字型 PDF 与带 OCR 文本层的扫描 PDF 有何区别？
- **结论**：PDF 应先提取已有文字层；只有没有可用文字层的页面才需要 OCR。OCR 输出独立的可搜索 PDF，再从中提取文本进入规范化文档。
- **原理 / 为什么**：文字型 PDF 已有可复制文本，重复 OCR 会降低原始文字质量；纯扫描 PDF 本质是页面图像，必须经 OCR 才能供后续检索使用。
- **易错点 / 坑**：Word 中插入图片后另存的 PDF 可能带有文档结构标记，却依然需要 OCR；不能仅凭“PDF 已有结构”判断可直接提取文字。
- **延伸**：OCR 质量应通过当事人、日期、金额、条款编号、表格等关键字段抽样验收。✅
- **标签**：#ocr #pdf #document-ingestion
- **状态**：已掌握
- **日期**：2026-08-15

### Windows 下 OCRmyPDF、Tesseract 与虚拟环境是不同层次的依赖

- **来源问题**：为什么激活 `.venv` 后能找到 `ocrmypdf`，却找不到 `tesseract`；`.env` 应如何配置？
- **结论**：OCRmyPDF 可安装在项目虚拟环境中；Tesseract 是独立系统程序。导入服务应通过 `.env` 中的绝对路径调用两者，而不依赖用户当前终端是否激活虚拟环境或 PATH 是否完整。
- **原理 / 为什么**：虚拟环境只改变 Python 包及其脚本的查找路径，不会自动包含系统安装的 Tesseract；OCRmyPDF 的子进程还必须能定位到 Tesseract。
- **易错点 / 坑**：仅在当前 PowerShell 中手动激活虚拟环境，不能保证导入任务或其他终端稳定运行。
- **延伸**：外部命令依赖应在导入前做可读错误检查，并保留可替换 OCR 适配器边界。✅
- **标签**：#windows #ocr #environment
- **状态**：已掌握
- **日期**：2026-08-15

### 规范化 JSON 是项目定义的数据契约，而非 OCR 工具输出格式

- **来源问题**：`normalized.json` 是否由项目自行定义；`block`、`kind` 与 `locator` 分别有什么作用？
- **结论**：`normalized.json` 是所有输入格式统一输出的中间表示；block 是标题、正文、列表或表格等最小可检索单元，locator 是该单元在原文中的唯一地址。
- **原理 / 为什么**：后续切片、检索和来源引用不能依赖 PDF、DOCX、HTML 各自不同的内部格式；统一契约使下游逻辑只处理一种数据形状。
- **易错点 / 坑**：`locator: "p"` 不是唯一定位，无法区分多个段落；应生成如 `paragraph:13`、`table:2`、`page:2:block:1` 的稳定标识。
- **延伸**：法律文本可在 block 上附加 `sectionPath`、`articleNumber` 和可用的 `sourcePage`。✅
- **标签**：#normalized-json #provenance #rag
- **状态**：已掌握
- **日期**：2026-08-15

### DOCX 的物理页码与真实文档结构需要分开处理

- **来源问题**：为什么司法解释 DOCX 的输出只有一页、全部是 `paragraph` 且 locator 都是 `p`；结构应如何提升？
- **结论**：DOCX 不应被伪造成固定的物理页码。应直接读取 OOXML 中的段落、样式、编号和表格节点，生成段落级唯一定位；真实页码只有经排版引擎渲染为 PDF 后才可靠。
- **原理 / 为什么**：Word 的分页会随字体、纸张、边距和渲染程序变化，通常不是稳定的源数据；而段落、列表和表格才是 DOCX 内置的真实结构。
- **易错点 / 坑**：只把 DOCX 转成 HTML 会丢失部分样式、编号和定位信息；“一、”“第一条”等法律文本规则应作为原始结构之外的补充。
- **延伸**：DOC 文件先转换为 DOCX，再复用同一结构解析流程。✅
- **标签**：#docx #ooxml #legal-structure
- **状态**：已掌握
- **日期**：2026-08-15

### 导入去重不能阻止失败恢复或显式重新处理

- **来源问题**：修正 OCR 配置后，为什么同一文件仍返回 `duplicate`；如何重新生成新版规范化结果？
- **结论**：成功或正在处理的同内容文件应去重；`failed`、`ocr_failed`、`manual_review` 状态应复用原记录重试。已成功的文件则通过显式 `--reprocess` 重新处理。
- **原理 / 为什么**：内容哈希与稳定来源标识用于避免无关重复记录，但失败记录本身不能成为恢复障碍；显式重新处理保证升级解析器时行为可控。
- **易错点 / 坑**：把所有已存在记录一律视为重复，会让修复配置后的任务永远无法重试。
- **延伸**：后续可记录派生产物与解析器版本历史，支持更细粒度的产物回滚。⚠️ 需验证
- **标签**：#idempotency #retry #document-ingestion
- **状态**：已掌握
- **日期**：2026-08-15

### 乱码与 JSON 转义必须区分来源处理

- **来源问题**：为什么 JSON 中出现 `\n` 和 `�`；它们是否会影响检索？
- **结论**：`\n` 是 JSON 对换行字符的标准表示，解析后恢复为换行；HTML 段落中的视觉换行可归一为空格。`�` 是 Unicode 替换字符，若原始文件已包含它，解析器不能安全地猜测并替换。
- **原理 / 为什么**：换行属于文本格式问题，不影响 JSON 有效性；替换字符意味着原始字符已丢失或损坏，自动替换可能篡改法律原文。
- **易错点 / 坑**：不能把所有显示异常都归咎于解析器。已验证的 HTML 原文件本身含有 `�`，重新处理只能应用格式归一，不能恢复丢失字符。
- **延伸**：可在后续质量校验中统计替换字符并标记人工复核，而不是静默清洗。✅
- **标签**：#encoding #data-quality #html
- **状态**：已掌握
- **日期**：2026-08-15
