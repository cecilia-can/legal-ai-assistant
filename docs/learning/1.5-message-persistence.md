### 游标分页针对的是会话内消息列表

- **来源问题**：列表（游标分页）指的是聊天列表吗？什么是游标分页，作用是什么？
- **结论**：这里的「列表」是**某个会话里的消息时间线**（气泡列表），不是侧栏会话列表；游标分页用上一页末尾的「书签」（cursor）拉取更早/下一批数据，而不是 `page=2`。
- **原理 / 为什么**：侧栏会话仍走既有 `GET /api/conversations`。消息 API 的 `GET .../messages?limit&cursor` 首屏取最近 N 条（再按时间升序展示），向上翻历史时带 `cursor` 继续要更早消息。游标通常由 `createdAt + id` 编码；服务端用 keyset 条件定位，避免深分页时 `OFFSET` 越扫越慢，也减少插入新消息时页码错位/漏读。
- **易错点 / 坑**：不要把「消息分页」和「会话列表」混为一谈；cursor 是位置令牌，一般不能像页码那样跳到任意第 N 页。
- **延伸**：
  - 游标（API 令牌）与 keyset（SQL `WHERE (created_at, id) < ...`）常配套：前者是接口形态，后者是高效实现 ✅
  - 需要「跳到第 N 页」的管理后台仍可能用 offset；聊天气泡无限上翻更适合 cursor ✅
  - 🔗 https://jsonic.io/guides/json-pagination-guide
  - 🔗 https://blog.openreplay.com/api-pagination-patterns/
- **标签**：#pagination #cursor #message-api #api-design
- **状态**：#待复习
- **日期**：2026-07-27

### 分页与虚拟列表解决不同问题

- **来源问题**：消息列表为什么不用虚拟列表？
- **结论**：1.5 用分页是为了**少拉数据**；虚拟列表是为了**少渲染 DOM**。本阶段目标是持久化与加载，未把虚拟滚动纳入范围。
- **原理 / 为什么**：分页控制从服务端/内存进入前端的消息条数（如首屏 50）；虚拟列表在已有大量 DOM 节点时只渲染可视区域。二者可叠加，但 Chat 场景消息量通常远未到必须虚拟滚动；完整骨架屏/长列表性能更接近后续 UX（如 1.8）议题。
- **易错点 / 坑**：以为「做了分页就等于虚拟列表」，或反过来认为「没虚拟列表就不能分页」——二者正交。
- **延伸**：
  - 常见虚拟列表库：`react-window` / `@tanstack/react-virtual`（本仓库尚未引入）✅
  - 若单会话历史极长且已全量在内存，再考虑虚拟列表；也可与「向上加载更早一页」组合 ✅
- **标签**：#virtual-list #pagination #performance #ux
- **状态**：#待复习
- **日期**：2026-07-27

### 当前消息只在 chatStore 内存，尚未写入数据库

- **来源问题**：目前一个消息对话是存储在哪里了？数据库中吗？还是 store 里？

### `/api/chat` 只推 SSE，落库走消息 API

- **来源问题**：`/api/chat` 仍只做 SSE，不直接写库；落库走消息 API——这句话是什么意思？
- **结论**：流式接口专心「调模型并推 token/done」；把消息写入 `Message` 表由另一套 REST（`/api/conversations/[id]/messages`）完成，由 `chatStore` 在适当时机调用。
- **原理 / 为什么**：职责分离——生成（SSE BFF）与持久化（CRUD API）解耦，符合 roadmap 交付物（独立 messages route + `messageService`），也避免在流式 Handler 里处理半写入、回滚等复杂逻辑。仅调 `/api/chat` 而不调消息创建 API 时，库中不应因该次聊天调用新增 Message。
- **易错点 / 坑**：以为「接了 AI 聊天就等于消息已进数据库」；落库失败时可能出现内存有、刷新后无的情况，需要错误提示。
- **延伸**：
  - 方案 B：`done` 或 abort（assistant 非空）时再 POST user + assistant ✅
  - 备选是在 `/api/chat` 内直接写库，本 Change 明确不做（耦合高）✅
- **标签**：#sse #api-design #separation-of-concerns #message-api
- **状态**：#待复习
- **日期**：2026-07-27

### Message 上 `(conversationId, createdAt)` 索引与 migration

- **来源问题**：数据层给 Message 增加 `(conversationId, createdAt)` 索引 + migration 的作用是什么？
- **结论**：复合索引加速「按会话过滤并按时间排序/取最近 N 条」的查询；migration 把该索引真正建到 PostgreSQL，通常只加索引、不改行数据、无需 reset。
- **原理 / 为什么**：消息列表与游标分页的典型 SQL 是 `WHERE conversationId = ? ORDER BY createdAt ... LIMIT N`。没有合适索引时，会话一长容易变成大范围扫描甚至额外排序；`(conversationId, createdAt)` 让过滤与排序能走同一索引路径。Prisma `@@index` 声明后需 `migrate` 才会落库，仅改 schema 文件不够。
- **易错点 / 坑**：复合索引有最左前缀规则——以 `conversationId` 打头才能很好地服务「某会话下按时间查」；有索引功能也能跑，只是数据量大时变慢。
- **延伸**：
  - 与游标/keyset 分页搭配时，索引列常与排序键一致 ✅
  - 🔗 https://www.elysiate.com/blog/postgresql-compound-indexes-explained
  - 🔗 https://www.postgresql.org/docs/current/indexes-multicolumn.html
- **标签**：#postgresql #index #prisma #migration #performance

### abort 不落库（方案 A）是取舍而非唯一正解

- **来源问题**：为什么 abort 不落库，这样的设计合理吗？
- **结论**：合理，但是刻意取舍：把「完整一轮（收到 `done`）」当落库边界，历史更干净、实现更简单；代价是误切会话/取消时可能丢掉已生成内容。
- **原理 / 为什么**：abort 时 assistant 常常不完整；若一律入库，刷新后会出现「说到一半」的历史，也可能干扰后续多轮上下文。与「仅 `done` 后写 user+assistant」一致时，失败路径少。主流产品（如 ChatGPT）则更常保留已生成部分，因此 A 不是体验最优，而是实现/数据干净优先。
- **易错点 / 坑**：把「abort = 取消 = 必须丢弃」当成行业唯一标准；也容易忽略用户其实只是误切换会话。
- **延伸**：
  - 若更在意「切走也不丢已生成」，应改用方案 B（本 Change 已采纳）✅
  - 半截回复是否在 UI 标注「已中断」可留到 UX 阶段（如 1.8）✅
- **标签**：#abort #persistence #design-tradeoff #streaming
- **状态**：#待复习

### 消息落库时机：方案 A / B / C 对比

- **来源问题**：请对比不同方案（abort 落库策略）的优缺点。
- **结论**：A 仅 `done` 落库（实现简单、历史干净、防误丢弱）；B 在 abort 且 assistant 非空时也落库半截（体验更好、历史可能含未完成轮次）；C 发送即落库 user，结束/abort 再落库 assistant（user 最稳，状态机最重，易出现孤儿 user）。
- **原理 / 为什么**：差别在于「一轮对话」的事务边界，以及 abort 后是否还想看见已生成文本。A 以完整回复为界；B 以「有可见 assistant 文本」为界；C 以「用户已发出」为界并拆成多次写库。复杂度：A < B < C；防丢内容：A < B < C（至少保住 user）。
- **易错点 / 坑**：把分页/虚拟列表问题和落库时机混为一谈；或以为必须在 `/api/chat` 里边流边写库才能支持 B/C——本设计仍可由 `chatStore` 调消息 API 编排。
- **延伸**：
  - 对后续 Change 1.7 上下文：B/C 可能要把过短/未完成轮次过滤或截断 ✅
  - C 更利于马上做「重新生成」，因 user 已稳定在库 ✅
  - 横向简表：实现复杂度 A 低 / B 中低 / C 中高；历史干净度 A 高 / B·C 中 ✅
- **标签**：#abort #persistence #api-design #chatStore #tradeoff
- **状态**：#待复习
- **日期**：2026-07-27

### Change 1.5 选定方案 B：abort 有内容也落库

- **来源问题**：请改成使用方案 B。
- **结论**：本 Change 采用方案 B——`done` 且 assistant 非空，或 abort 且 assistant 已有非空内容时，持久化本轮 user +（完整或半截）assistant；abort 时尚无文本或流开始前失败则不落库。
- **原理 / 为什么**：在实现成本接近 A 的前提下，更贴近主流 Chat「取消/切换也不轻易丢已打出内容」的体验；仍比 C 简单（不必发送瞬间写 user、也少悬空 user）。OpenSpec 已同步：`proposal` / `design` / `chat-state` spec / `tasks` 中的落库与验证项。
- **易错点 / 坑**：实现时漏掉「abort 且 content 为空不落库」分支，可能写出空 assistant；或 abort 路径忘记用服务端 id 替换临时 id。
- **延伸**：
  - 验证点：有文本时 abort → 刷新仍见半截；无文本 abort → 刷新无本轮 ✅
  - 半截进入历史对 1.7 Token/上下文的影响，可在 Prompt 阶段再处理 ✅
- **标签**：#abort #scheme-b #message-persistence #openspec
