### 对话上下文、会话历史与 Agent 记忆的边界

- **来源问题**：当前项目是否需要上下文机制；Chatbot 的上下文与 Agent 上下文有什么关联？
- **结论**：Chatbot 与 Agent 都需要上下文，但 Chatbot 主要使用角色规则、会话历史与 RAG；Agent 还需要目标、计划、工具结果和执行状态等工作记忆。
- **原理 / 为什么**：模型每次调用只看本次传入的输入，不会自动读取数据库中的完整会话。当前项目已在服务端组合固定法律助手提示词、会话消息和按最新问题检索到的 RAG 资料；这已足够支撑多轮 Chatbot。Agent 的差异不在于“保留更多聊天记录”，而在于能把任务与工具执行结果带入循环决策。
- **易错点 / 坑**：把数据库保存的消息误认为模型天然记得；实际上必须在每次调用中明确选择并传入。
- **延伸**：
  - Agent 的工具调用结果应以结构化任务状态或摘要进入上下文，不能无限追加完整日志。✅
  - 会话级记忆与跨会话用户记忆应分开；法律场景的跨会话记忆需要用户同意、可查看和可删除机制。✅
  - 🔗 [OpenAI API：超出输入限制时会从最早消息开始截断](https://platform.openai.com/docs/api-reference/realtime-client-events/session)

### 单次调用的上下文窗口与应用级 token 预算

- **来源问题**：总上下文窗口是否指本次单轮回答；DeepSeek 1M 上下文、最大 384K 输出时项目应如何分配？
- **结论**：上下文窗口是单次模型调用的输入与输出总容量，而非整段会话的永久容量；应用应设置低于模型能力上限的产品级预算，并为输出预留空间。
- **原理 / 为什么**：下一轮调用时，历史消息会作为新的输入再次发送。输入由系统提示词、RAG、摘要、历史原文和本轮问题共同构成；可用输入预算等于应用设定的总预算减去最大输出预留。模型支持 1M 上下文不意味着日常法律问答应默认传入 1M token，否则成本、延迟和无关信息干扰都会增加。
- **易错点 / 坑**：`CHAT_MAX_OUTPUT_TOKENS` 若只用于本地估算、未同步传给模型 API 的输出参数，就不是供应商实际执行的输出上限。
- **延伸**：
  - 可按“普通聊天”和“长文书/案卷分析”设置不同的应用级输入与输出预算。✅
  - 软阈值应根据应用输入预算计算，例如在预算约 65% 时开始压缩，而不是等到硬上限。✅
  - 🔗 [OpenAI API：输入上限受上下文窗口减最大输出 token 约束](https://platform.openai.com/docs/api-reference/realtime-client-events/session)
- **标签**：#tokens #context-window #budget #rag

### 通用会话摘要与可选案件事实块

- **来源问题**：用户可能只是连续提问法律知识，是否还应做案件摘要；摘要应该分类还是使用一类通用总结？
- **结论**：以通用会话摘要为主体，并在其中提供可选的案件事实块，比强制把每个会话分类为“普通问答”或“案件”更适合作为第一版方案。
- **原理 / 为什么**：通用字段可记录主题、已有结论、未解决问题和摘要覆盖的最后消息；只有出现明确的当事人、时间线、证据或争点时，才填充案件字段。这样普通知识问答不会被错误案件化，用户从泛问答逐步转为个案咨询时也无需迁移记忆类型。
- **易错点 / 坑**：不能把模型推测写成事实；案件字段应区分已确认事实、用户单方陈述和待核实信息，并保留原始消息作为唯一完整档案。
- **延伸**：
  - `coveredUntilMessageId` 可标识摘要覆盖到哪条消息，防止后续组装上下文时重复或遗漏原文。✅
  - 结构化摘要写入前应通过 JSON Schema 或 Zod 校验字段、枚举值和必填项。✅
- **标签**：#memory #summary #legal-ai #structured-data

### 使用独立模型调用进行增量历史压缩

- **来源问题**：摘要压缩如何实现，是否需要再次接入模型？
- **结论**：需要独立的模型调用进行语义压缩；输入是旧摘要与即将移出上下文的早期消息，输出是经服务端校验后保存的新摘要。
- **原理 / 为什么**：单靠截断或正则无法可靠区分案件事实、假设、法律分析和用户纠正。增量摘要只覆盖旧片段，保留近期 6～12 条原文，使模型既获得长期脉络，也能看到最近的措辞与追问。
- **易错点 / 坑**：不要让面向用户的回答调用顺带产生不受约束的摘要；应使用专门提示词，要求不推断、不补充事实、仅返回规定的 JSON。原始消息必须持续保留，以便重建或纠正摘要。
- **延伸**：
  - 未到硬上限时可在回答后由可靠队列异步压缩；已经无法容纳必要上下文时，需在主回答前同步压缩。✅
  - 摘要调用也会消耗 token、复制敏感内容，应纳入用量统计和隐私说明。✅
  - 🔗 [OpenAI API：自动截断会丢弃最早消息，应用可在更低阈值主动控制截断](https://platform.openai.com/docs/api-reference/realtime-client-events/session)
