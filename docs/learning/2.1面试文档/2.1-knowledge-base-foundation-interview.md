# Change 2.1 面试官追问与解答思路

> 类型：Phase 2 / Change 2.1 专项 · 面试向  
> 范围：PostgreSQL、pgvector、Prisma 数据模型、知识库归属、文档切片与 Embedding 基础设施  
> 日期：2026-08-09

本文从面试官视角整理 Change 2.1 可能被问到的问题。回答时建议使用：

> 结论 → 原理 → 结合项目 → trade-off / 后续演进

需要明确：Change 2.1 只完成知识库数据模型和向量基础设施，还没有实现文档解析、切片算法、真实 Embedding 批处理和 RAG 检索。

## 一、项目总体设计

### Q1：Change 2.1 主要解决什么问题？

**解答思路：**

1. **结论**：为后续法律文档导入、切片、向量化和 RAG 检索建立稳定的数据基础。
2. **原理**：知识库不能只保存一个文件和一个向量，需要同时保存归属、来源、版本、解析状态、切片定位和 Embedding 模型信息。
3. **结合项目**：新增 `KnowledgeBase`、`Document`、`DocumentChunk` 和 `Embedding`，关系为：

   ```text
   KnowledgeBase → Document → DocumentChunk → Embedding
   ```

4. **边界**：解析属于 Change 2.2，法律结构切片属于 Change 2.3，实际向量化和 RAG 属于 Change 2.4。

### Q2：为什么先做数据模型，而不是直接导入文档和生成向量？

**解答思路：**

文档切片方式和 Embedding 模型会影响向量结构。如果先生成向量，后面修改切片策略就需要大批量重建。先建立 `DocumentChunk`、来源定位、内容哈希和模型版本字段，可以支持后续重新切片和重新嵌入。

## 二、PostgreSQL 与 pgvector

### Q3：PostgreSQL 和 pgvector 分别负责什么？

**解答思路：**

1. PostgreSQL 负责保存用户、知识库、文档、切片、权限和版本等关系数据。
2. pgvector 是 PostgreSQL 扩展，提供 `vector` 类型、向量距离计算和向量索引。
3. Embedding 模型负责把文本转换成数字向量；pgvector 负责保存和检索这些向量。

```text
文档切片 → Embedding 模型 → 向量
                         ↓
               PostgreSQL + pgvector
                         ↓
                    相似度检索
```

### Q4：为什么不用 Milvus、Pinecone 或 Qdrant？

**解答思路：**

当前项目是单体应用和学习型 MVP，数据量还不大。PostgreSQL 已经负责用户和业务数据，使用 pgvector 可以减少额外服务、部署、权限和数据同步成本。

如果未来向量规模非常大、需要独立扩缩容或复杂向量检索，再考虑独立向量数据库。

### Q5：`pgvector/pgvector` Docker 镜像是不是自动启用了扩展？

**解答思路：**

不是一回事。镜像提供 pgvector 扩展文件和能力，但数据库仍然需要执行：

```sql
CREATE EXTENSION IF NOT EXISTS vector;
```

因此项目把这条语句放入版本化 Prisma migration，保证全新数据库也能完成初始化。

## 三、数据模型设计

### Q6：为什么不能直接在 Document 上保存向量？

**解答思路：**

因为 RAG 检索的最小单位通常是文档切片，而不是整份文档。法律法规需要按条、款检索，合同需要按条款检索，案例需要按事实和裁判观点检索。

独立的 `DocumentChunk` 可以保存：

- 切片顺序；
- 章节路径；
- 页码；
- 法条或合同条款编号；
- 切片策略版本。

这样回答时才能引用具体来源。

### Q7：为什么 Embedding 要单独建表？

**解答思路：**

同一个切片未来可能使用不同的 Embedding 模型。单独建表可以保存：

- `model`；
- `dimensions`；
- `contentHash`；
- 向量值；
- 创建时间。

项目使用 `(chunkId, model, contentHash)` 组合唯一约束，避免同一内容使用同一模型重复生成向量，同时支持模型升级和内容变更。

### Q8：为什么需要 KnowledgeBase，而不是只给 Document 增加 userId？

**解答思路：**

因为项目同时存在两类资料：

- 系统公共法律法规、案例和合同模板；
- 用户私有上传资料。

公共知识库不应错误地归属于某一个用户。因此项目让 `Document` 必须属于一个 `KnowledgeBase`，由知识库表达 `system` 或 `user` 范围。

### Q9：`ownerId` 为什么允许为空？

**解答思路：**

系统公共知识库没有普通用户所有者，所以 `ownerId` 可以为空；用户私有知识库必须绑定用户 ID。

但这只是数据模型设计，不能代替授权校验。真正访问文档时，服务层仍然需要根据当前 session 检查知识库 scope 和 ownerId，不能只相信客户端传来的 ID。

## 四、Prisma 与原生 SQL

### Q10：为什么使用 `Unsupported("vector")`？

**解答思路：**

Prisma 可以很好地管理关系字段、索引和迁移，但对 pgvector 类型和向量索引的表达能力有限。因此项目采用混合方式：

- 普通字段和关系：使用 Prisma Schema；
- `vector` 列和扩展：使用 migration 原生 SQL；
- 向量距离查询：后续使用参数化 raw SQL 或专门的查询封装。

这样既保留 Prisma 的类型安全，又能使用 PostgreSQL 的向量能力。

### Q11：为什么现在没有创建 HNSW 或 IVFFlat 索引？

**解答思路：**

向量索引依赖最终模型和维度。Change 2.1 还没有确定最终 Embedding 模型，因此只建立向量列和元数据，不提前固定索引参数。

Change 2.4 确定模型和维度后，再根据数据量和查询性能选择 HNSW 或 IVFFlat。

### Q12：HNSW 和 IVFFlat 怎么选择？

**解答思路：**

- HNSW：通常召回质量和查询延迟较好，但建索引和内存成本更高；
- IVFFlat：索引和构建成本较低，但需要训练列表，参数调优更敏感。

当前数据规模较小，可以先使用简单精确检索建立基线，再根据实际召回率、延迟和数据量选择索引，而不是一开始盲目优化。

## 五、数据质量与可追溯性

### Q13：为什么保存 contentHash？

**解答思路：**

`contentHash` 用于：

- 检测重复文件；
- 判断文档内容是否发生变化；
- 判断切片是否需要重新 Embedding；
- 避免重复导入相同资料。

项目在文档和 Embedding 层都保存内容哈希，因为文档内容哈希和切片内容哈希的生命周期不同。

### Q14：为什么切片必须保存页码、章节和条款定位？

**解答思路：**

法律场景不能只返回“相似文本”，还要告诉用户依据来自哪里。`locator`、`pageFrom`、`pageTo`、`sectionPath` 等字段可以让后续 RAG 回答输出：

```text
来源：中华人民共和国民法典
位置：第三编合同，第一章一般规定，第一条
```

这也是法律 RAG 与普通问答系统的重要区别。

### Q15：如何处理文档版本和重新切片？

**解答思路：**

文档保存 `documentVersion`、`parserVersion` 和 `normalizationVersion`；切片保存 `chunkStrategyVersion`；Embedding 保存模型和内容哈希。

当解析器、切片算法或模型发生变化时，可以判断哪些阶段需要重新执行，而不是无条件重建全部数据。

## 六、迁移与安全

### Q16：如何保证 migration 不影响已有用户和会话？

**解答思路：**

本次 migration 只新增知识库相关表、索引、外键和 pgvector 扩展，不修改 `User`、`Conversation`、`Message` 的既有字段和数据。执行后通过数据库记录数量和关系读写测试确认已有租户数据不变。

实际验证中，已有 `User=2`、`Conversation=3`，迁移后数量保持不变。

### Q17：为什么不直接执行 `prisma migrate reset`？

**解答思路：**

`migrate reset` 会删除数据库并重建，适合完全没有重要数据的本地实验环境，不适合已经存在用户和会话的数据库。

本次发现 migration 初始化问题后，只处理本 Change 新建且为空的表，没有重置整个数据库。

### Q18：级联删除会不会有风险？

**解答思路：**

知识库删除会级联删除文档、切片和 Embedding，这是保持孤儿数据清理简单的选择。但生产环境需要增加删除确认、软删除、审计日志或异步删除，避免误删大量知识资料。

## 七、真实工程问题

### Q19：本次实现中遇到过什么问题？

**解答思路：**

可以讲两个真实问题：

1. 本地已有一个健康运行的 `legal-ai-postgres` 容器，启动 Compose 时发生名称冲突。确认镜像和数据后复用了已有容器，没有删除或重置数据库。
2. Prisma 自动生成的 migration 因当前数据库已经存在 pgvector 扩展，没有自动写出扩展初始化语句。检查生成 SQL 后，补充了 `CREATE EXTENSION IF NOT EXISTS vector`，并在不影响既有用户数据的情况下重新应用空的知识库表 migration。

### Q20：如何验证 Change 2.1 是有效的？

**解答思路：**

验证分为四层：

1. `prisma validate`：Schema 语法正确；
2. `prisma generate`：生成客户端成功；
3. `prisma migrate status`：数据库与 migration 同步；
4. 基础读写脚本：创建系统/用户知识库、文档、切片和向量，查询 `vector_dims`，再清理测试数据并确认已有用户和会话不变。

另外，项目级 `npm run lint` 和 `npm run build` 均通过。

## 八、面试时不要夸大当前实现

如果面试官问“现在已经能做 RAG 了吗”，应该诚实回答：

> 目前 Change 2.1 只完成了知识库数据模型和 pgvector 基础设施。文档解析、法律结构切片、Embedding 批处理、相似度检索和 RAG Prompt 会在后续 Change 中实现。当前已经验证了数据关系和 pgvector 向量列可以正常写入和读取。
