# Change 1.9：登录后会话不同步（侧栏 UserMenu 需刷新才出现）

> Phase：1 ChatBot + 鉴权  
> 涉及：`app/layout.tsx`、`app/providers.tsx`、`auth.config.ts`、`components/auth/UserMenu.tsx`、`lib/auth/actions.ts`  
> 关联 Change：1.9 多用户登录鉴权与数据隔离（Auth.js v5 + JWT + Credentials）  
> 日期：2026-08-02

---

## §0 Executive Summary

**问题：** 用户登录/注册成功进入聊天页后，侧栏底部不显示当前账号邮箱与「退出登录」按钮；**手动刷新页面**后才出现。与此同时，会话列表加载、发消息、流式回复等 API 功能正常。

**根因：** 服务端鉴权（`auth()` + Cookie）与客户端 Session 展示（`useSession()` + `SessionProvider`）是**两条独立链路**。登录跳转后，客户端 `SessionProvider` 仍可能持有 **`session=null` 的 stale 初始值**，且 JWT callback 未完整写入 `email`/`name`；再叠加 App Router 对 layout 的缓存，导致 `UserMenu` 在 `!session?.user` 时直接 `return null`。

**方案：**

1. 根 layout `await auth()` 并将 session 注入 `SessionProvider`  
2. JWT / session callback 持久化 `id`、`email`、`name`  
3. `export const dynamic = "force-dynamic"` 避免 layout 静态缓存  
4. `UserMenu` 挂载时调用 `useSession().update()` 主动同步 Cookie 中的 session  

**效果：** 登录进入首页后，侧栏底部先短暂显示「加载用户信息…」，随后自动展示邮箱与退出按钮，**无需手动刷新**。

## 1. 背景

### 1.1 项目阶段

Change 1.9 引入多用户体系：

| 维度 | 选型 |
|------|------|
| 认证框架 | Auth.js v5（`next-auth`） |
| Session 策略 | **JWT**（Credentials 不支持 database session） |
| 登录方式 | 邮箱 + 密码（Credentials Provider） |
| 服务端鉴权 | Route Handler 内 `auth()` / `requireApiSession()` |
| 页面守卫 | 根目录 `proxy.ts` 乐观重定向 |
| 客户端展示 | `next-auth/react` 的 `useSession()` + `UserMenu` |

### 1.2 架构上的「双轨 Session」

```text
                    ┌─────────────────────────────────────┐
                    │         浏览器 HttpOnly Cookie       │
                    │    (Auth.js JWT session token)       │
                    └──────────────┬──────────────────────┘
                                   │
           ┌───────────────────────┼───────────────────────┐
           │                       │                       │
           ▼                       ▼                       ▼
   服务端 auth()            GET /api/auth/session      proxy.ts
   (Route Handler)          (SessionProvider 可选拉取)   (乐观检查)
           │                       │
           ▼                       ▼
   API 401/404 正常          useSession() → UserMenu
```

**关键认知：** API 能用，只说明**服务端轨道**正常；侧栏用户信息依赖**客户端轨道**，二者可以不同步。

## 2. 修改前的现象

### 2.1 用户可感知表现

| 维度 | 表现 |
|------|------|
| 登录流程 | 注册/登录成功，跳转到 `/`，可正常使用聊天 |
| 侧栏底部 | **无**邮箱、**无**「退出登录」按钮（空白） |
| 手动刷新 | `F5` / 硬刷新后，邮箱与按钮**出现** |
| API | `GET /api/conversations`、发消息、SSE 流式均正常 |
| 登出 | 刷新前甚至找不到退出入口（只能清 Cookie 或改 URL） |

### 2.2 易误判方向

| 误判 | 实际 |
|------|------|
| 登录失败 / Cookie 没写上 | ❌ API 已带 Cookie 正常工作 |
| `UserMenu` 组件没挂载 | ❌ 刷新后同组件能显示 |
| `proxy.ts` 拦截问题 | ❌ 能进首页说明 proxy 已通过 |
| Auth.js adapter 坏了 | ❌ 服务端 `auth()` 能读到 session |
| 侧栏被 CSS 藏起来 | ❌ 刷新后在同一位置出现 |

本质是 **客户端 Session 状态未在登录跳转后及时更新**，不是认证失败。

## 3. 如何探索问题

### 3.1 推荐排查顺序

1. **`components/auth/UserMenu.tsx`** — 是否 `!session?.user` 就 `return null`  
2. **`app/providers.tsx`** — `SessionProvider` 是否传入 `session` prop  
3. **`app/layout.tsx`** — 是否 `await auth()` 并把结果传给 Providers  
4. **`auth.config.ts`** — JWT callback 是否只写了 `sub` 没写 `email`  
5. **DevTools → Network** — 登录后首次进入 `/` 时 `/api/auth/session` 返回什么  
6. **DevTools → Application → Cookies** — 是否存在 Auth.js session cookie  
7. **`npm run build` 路由表** — `/` 是否为静态 `○`（会加剧 layout stale）

### 3.2 对照实验

| 实验 | 操作 | 预期结论 |
|------|------|----------|
| A | 登录后不刷新，看 Network 里 API 是否 200 | Cookie 有效，服务端已登录 |
| B | 看 `/api/auth/session` 首次响应 | 可能有 user，但 UI 未消费 |
| C | 刷新后再看 UserMenu | 说明客户端初始 session 为空 |
| D | 临时在 UserMenu 打印 `status` / `session` | 常见：`unauthenticated` + `null` |

### 3.3 相关代码（修复前的问题点）

**UserMenu 在无 session 时完全隐藏：**

```tsx
if (!session?.user) {
  return null;  // 用户看到侧栏底部空白
}
```

**SessionProvider 未注入服务端 session（修复前）：**

```tsx
<SessionProvider>{children}</SessionProvider>
```

**JWT callback 信息不全（修复前）：**

```tsx
jwt({ token, user }) {
  if (user?.id) {
    token.sub = user.id;  // 仅有 id，无 email/name
  }
  return token;
}
```

## 4. 根因分析

### 4.1 直接原因

1. **`UserMenu` 依赖 `useSession()`**，而登录后首次渲染时 `session` 为 `null`  
2. **`SessionProvider` 初始 props 为 `session=null`** 时，不会自动假设 Cookie 已登录而重拉（需显式 `update()` 或服务端传入正确 session）  
3. **JWT callback 未把 `email`/`name` 写入 token**，即使 session 存在，展示字段也可能缺失  

### 4.2 为什么「刷新」能好

刷新触发**完整 document 请求**：

- 根 layout 重新执行 `await auth()`，读到 Cookie 中的 JWT  
- 新的 RSC payload 将**非 null 的 session** 传给 `SessionProvider`  
- `useSession()` 获得正确初始值 → `UserMenu` 渲染  

### 4.3 为什么「登录跳转」不能好（修复前）

登录走 Server Action + `signIn()` + `redirect("/")`：

- Cookie 在 **Server Action 响应**中 Set-Cookie  
- 跳转到 `/` 可能是 App Router **软导航 / Router Cache**  
- layout 的 RSC payload 仍可能携带**跳转前**的 `session=null`（尤其在 `/` 被静态优化为 `○` 时）  
- 客户端 `SessionProvider` 以 `null` 初始化 → `UserMenu` 隐藏  

### 4.4 与「API 正常」不矛盾

| 链路 | 读取方式 | 登录后是否立即可用 |
|------|----------|-------------------|
| `/api/conversations` 等 | 服务端 `auth()` 读 Cookie | ✅ 是 |
| `UserMenu` | 客户端 `useSession()` | ❌ 修复前否 |

---

## 5. 解决方案

### 5.1 根 layout 注入服务端 session

```tsx
// app/layout.tsx
export const dynamic = "force-dynamic";

export default async function RootLayout({ children }) {
  const session = await auth();
  return (
    <Providers session={session}>{children}</Providers>
  );
}
```

- **`force-dynamic`**：每次请求重新跑 `auth()`，避免静态 shell 固化 `session=null`  
- **传入 `session` prop**：让 `SessionProvider` 首屏尽量与服务端一致  

### 5.2 完善 JWT / session callback

```tsx
jwt({ token, user }) {
  if (user) {
    token.sub = user.id;
    token.email = user.email;
    token.name = user.name;
  }
  return token;
},
session({ session, token }) {
  if (session.user && token.sub) {
    session.user.id = token.sub;
    session.user.email = typeof token.email === "string" ? token.email : session.user.email;
    session.user.name = typeof token.name === "string" ? token.name : session.user.name;
  }
  return session;
},
```

Credentials + JWT 必须在 **`jwt` 首次登录时**把 user 字段写入 token，否则后续请求 session 里没有 email。

### 5.3 UserMenu 主动 sync（兜底）

```tsx
const { data: session, status, update } = useSession();
const [hasSynced, setHasSynced] = useState(() => Boolean(session?.user));

useEffect(() => {
  if (session?.user || hasSynced) return;
  void update().finally(() => setHasSynced(true));
}, [session?.user, update, hasSynced]);
```

- 若首屏 `session` 仍为空，调用 **`update()`** 请求 `/api/auth/session`  
- 同步完成前显示「加载用户信息…」，避免空白闪烁  
- 同步后仍无 user → `return null`（真正未登录）

### 5.4 修改文件清单

| 文件 | 改动 |
|------|------|
| `auth.config.ts` | JWT / session callback 写入 email、name |
| `app/layout.tsx` | `await auth()`、`dynamic = "force-dynamic"` |
| `app/providers.tsx` | `SessionProvider session={session}` |
| `components/auth/UserMenu.tsx` | `update()` 主动同步 + loading 态 |

## 7. 延伸：同类问题预防清单

实现 App Router + Auth.js 时建议默认做：

- [ ] 根 layout `await auth()` + 传入 `SessionProvider`  
- [ ] 含 session 的 layout 标记 `dynamic = "force-dynamic"`  
- [ ] Credentials + JWT 时 callback 显式写入需要的 user 字段  
- [ ] 客户端 UI 不要假设 `useSession()` 首屏一定有值；必要时 `update()`  
- [ ] 区分「服务端已登录」与「客户端已感知」分别验收

## 8. 面试官追问与解答

### Q1：用户说登录成功了但看不到账号信息，你怎么排查？

**答：**  
先确认是**全站未登录**还是**仅 UI 未展示**。看 API（如 `GET /api/conversations`）是否 200：若 200 则 Cookie / 服务端 `auth()` 正常，问题在客户端 `useSession()` 或 `SessionProvider`。再看 `/api/auth/session` 响应、layout 是否传入 session、JWT callback 是否写入 email。最后看 UserMenu 是否在 `!session` 时直接 return null。

**加分：** 提到服务端 / 客户端双轨 session。  
**减分：** 只查密码是否正确或 adapter 是否安装。

---

### Q2：为什么 API 正常但侧栏没有用户信息？

**答：**  
Route Handler 每次请求在服务端调用 `auth()`，直接读 Cookie，与 RSC 缓存无关。侧栏用客户端 `useSession()`，依赖 `SessionProvider` 初始 props 或 `/api/auth/session` 拉取。登录软导航后 Provider 可能仍以 `session=null` 初始化，而 API 请求已带 Cookie，所以出现分裂。

---

### Q3：JWT session 和 database session 有什么区别？你们为什么用 JWT？

**答：**  
Database session 把 session 存 DB，Cookie 里放 session id，可服务端吊销、多设备管理。JWT session 把 claims 放 Cookie（签名），无 DB 读 session，扩展性好。Auth.js 的 **Credentials Provider 不支持 database session**，Change 1.9 只有邮箱密码，故选 JWT；`Session` 表建好供 1.9.1 OAuth 预留。

---

### Q4：`SessionProvider` 的 `session` prop 传 `null` 和完全不传有什么区别？

**答：**  
传 `null` 表示服务端明确告知「当前无 session」，Provider 以未登录初始化，**不一定会**再自动拉 Cookie。不传时部分版本会 client fetch。最佳实践是 App Router 下 layout **`await auth()` 后传入真实 session**；若仍为 null 但 Cookie 存在，需 `update()` 或 `router.refresh()` 兜底。

---

### Q5：为什么刷新页面就好了？

**答：**  
刷新是完整 document 请求，layout 重新 `await auth()`，带 Cookie 得到非 null session，新 HTML/RSC 注入 Provider。登录后的第一次软导航可能复用 stale layout payload（尤其静态优化路由），所以 refresh 能「治好」。

---

### Q6：`export const dynamic = "force-dynamic"` 有什么代价？

**答：**  
该 layout 子树每次请求动态渲染，无法静态缓存，TTFB 略增。对含 `auth()` 的根 layout 合理：session 是 per-user 的，本就不该静态。只读 marketing 页可放另一 route group 保持静态。

---

### Q7：`useSession().update()` 做什么？和 `router.refresh()` 区别？

**答：**  
`update()` 由 next-auth 客户端调用 `/api/auth/session` 刷新 context，**不整页 reload**。`router.refresh()` 让 Next.js 重新 fetch 当前 route 的 Server Components（含 layout 的 `auth()`），范围更大。登录后 sync 可先 `update()`；仍不行再 `router.refresh()`。

---

### Q8：登录用 Server Action 好还是客户端 `signIn()` 好？

**答：**  
Server Action + `signIn()`：密码只在服务端处理，更安全；但跳转后客户端 session sync 要额外处理（本次 bug 来源之一）。客户端 `signIn({ redirect: false })` 后 `router.refresh()` + `router.push()`：session sync 更可控，密码经 HTTPS 到 Next 再转服务端。生产可 Server Action 登录 + layout 注入 + `update()` 兜底。

---

### Q9：Credentials 登录时 JWT callback 为什么必须写 email？

**答：**  
JWT 只在**首次 `authorize` 成功**时收到完整 `user` 对象；之后请求只有 token。若不在 `jwt()` 里把 `email`/`name` 写入 token，`session()` callback 无法还原展示字段。Database session 可从 DB 查 user；JWT 必须自己 persist claims。

---

### Q10：两个浏览器标签页能登录两个不同账号吗？

**答：**  
同一浏览器 profile 的多个标签**共享 Cookie**，后登录会覆盖先登录的 session，**不能**同时两账号。要并行测隔离：普通窗口 + 无痕、或两个 Chrome Profile、或 Chrome + Edge。

---

### Q11：`proxy.ts` 和 `auth()` 分工是什么？

**答：**  
`proxy.ts` 做**乐观**检查（Cookie 是否存在），快速重定向未登录用户，**不应查 DB**。真正授权在 Route Handler / Server Action 里 `auth()` + 资源归属校验。仅 proxy 不够：Server Action 等入口会绕过 proxy。

---

### Q12：UserMenu 为什么一开始 return null 而不是 loading？

**答：**  
修复前认为「无 session = 未登录」直接隐藏，未考虑「已登录但 client 未 sync」中间态。修复后：sync 前显示 loading，sync 后仍无 user 才 null。避免「其实已登录却像没做 UserMenu」的 UX。

---

### Q13：这个问题和 Hydration mismatch 有关吗？

**答：**  
不完全是。Hydration mismatch 是服务端 HTML 与客户端首次 render 不一致。这里是 **client session context 初始值错误**，不一定报 hydration 警告，但表现类似「要刷新才对」。都可归因为「首屏状态与真实登录态不一致」。

---

### Q14：如果不用 `next-auth/react`，怎么显示用户信息？

**答：**  
方案 A：layout Server Component 读 `auth()`，把 `email` 当 props 传给 Server Component 侧栏（无 sync 问题，但登出要 Server Action）。方案 B：自建 `/api/me` 返回 user，client fetch。方案 C：继续 SessionProvider + 本次 sync 方案。App Router 官方推荐 A + Provider 混合。

---

### Q15：怎么写自动化测试覆盖这个问题？

**答：**  
E2E（Playwright）：注册 → 登录 → **不 refresh** → assert 侧栏有邮箱。单测难覆盖 Router Cache，偏 E2E。API 层用 `verify-tenant-isolation.ts` 测隔离，不覆盖 client session sync。
