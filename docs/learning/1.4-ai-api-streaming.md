### BFF（Backend for Frontend）是什么、在本项目里指什么

- **来源问题**：BFF 层作用是什么？在当前的项目里有吗？
- **结论**：BFF 是夹在浏览器与后端能力（数据库、AI API 等）之间、**专门为这个前端**提供 HTTP API 的服务端层；本项目里 **`app/api/` 下的 Route Handlers 就是 BFF**，例如已有的 `/api/conversations`，规划中的 `/api/chat`。
- **原理 / 为什么**：BFF 负责藏密钥、协议适配（如 DeepSeek SSE → 自家 SSE 事件）、统一 JSON envelope、按 UI 需求裁剪数据；浏览器只调 `/api/*`，不直连 PostgreSQL 或 DeepSeek。在 Next.js 全栈里，BFF 与业务逻辑同在同一个应用，不必单独部署一个「BFF 微服务」。
- **易错点 / 坑**：不要把 BFF 理解成与「后端」并列的第四层——**BFF 是后端的对外入口**，`lib/db.ts`、`lib/ai/client.ts` 是后端内部能力。
- **延伸**：
  - Change 1.4 的 `/api/chat` 典型 BFF 职责：隐藏 `OPENAI_API_KEY`、重打包 SSE 事件 ✅
  - BFF 模式由 Sam Newman 提出，常与 API Gateway 组合而非替代 ✅
  - 🔗 https://learn.microsoft.com/en-us/azure/architecture/patterns/backends-for-frontends
  - 🔗 https://samnewman.io/patterns/architectural/bff/
- **标签**：#bff #architecture #nextjs #app-router #api

### 本项目有没有「后端」——与 BFF、前端、数据库的关系

- **来源问题**：是不是只有前端、数据库和 BFF，没有后端？
- **结论**：**有后端**，只是没有单独再拆一个「传统后端项目」（如独立 Java/Go 服务）；**后端 = Next.js 服务端代码**，包括 `app/api/*`（BFF 入口）和 `lib/` 里的数据访问与 AI 客户端；前端是 `app/page.tsx`、`components/`、`lib/stores/`。
- **原理 / 为什么**：传统架构里「前端 SPA + 独立后端服务 + 数据库」三分部署；Next.js 全栈把服务端 Route Handlers 与 React 打在同一 repo、同一部署单元里，所以容易误以为「只有前端」。实际上凡在服务器执行、浏览器碰不到的代码（Prisma、调 DeepSeek、API 路由）都是后端。
- **易错点 / 坑**：「有 BFF 就没有后端」是误解——BFF ⊂ 后端；DeepSeek 是**外部 SaaS**，不是你们写的后端，但你们的 Next.js 调它属于后端逻辑。
- **延伸**：
  - 分层记忆：浏览器 → BFF（`app/api`）→ 内部服务（`lib/db`、`lib/ai`）→ 外部/数据库 ✅
  - Vercel 部署时 BFF 以 Serverless Function 形式运行，仍是后端 ✅
  - 若未来规模变大，才可能把部分 `lib/` 拆成独立微服务 ⚠️需查证
  - 🔗 https://vercel.com/i/backend-for-frontend-pattern
- **标签**：#architecture #bff #fullstack #nextjs #backend

### parseSseChunk 的 remainder 机制

- **来源问题**：请逐行讲 parseSseChunk 里的 remainder 机制。
- **结论**：`split("\n\n")` 后 `pop()` 出的最后一段是「还没有遇到帧结束符 `\n\n` 的尾巴」，存入 `remainder` 留给下次与新区块拼接；只有前面各段才是可解析的完整 SSE 帧。
- **原理 / 为什么**：SSE 以 `\n\n` 分隔帧；`parseSseChunk` 一次处理的是「当前累积字符串」，不能假设传入的 buffer 恰好帧对齐。`normalized.replace(/\r\n/g, "\n")` 统一换行后再 split，避免 Windows 换行导致切分失败。
- **易错点 / 坑**：buffer 恰好以 `\n\n` 结尾时，`split` 会产生空尾段，`pop()` 得到 `""`，完整帧仍在 `parts` 里正常解析；若整段没有 `\n\n`，整段都会成为 `remainder`、本次 `events` 为空——这是预期行为而非 bug。
- **延伸**：
  - `consumeSseStream` 用模块级 `remainder += decode(...)` 跨多次 `reader.read()` 累积，与单次 `parseSseChunk` 配合 ✅
  - 流结束时会 `decoder.decode()` flush 并给 remainder 补 `\n\n` 再解析最后一帧 ✅
- **标签**：#sse #streaming #parseSseChunk #remainder
- **状态**：#待复习
- **日期**：2026-07-26

### 为什么会出现「不完整 SSE 帧」的 buffer——不是 DeepSeek 原样返回

- **来源问题**：为什么会出现 `data: ...\n\ndata: ...\n\ndata: {"type":"to` 这种不完整 buffer？这不是 DeepSeek 的 SSE 返回吗？
- **结论**：这种截断 buffer 通常出现在**浏览器 `reader.read()` 读 BFF 响应**时，不是 DeepSeek 原始 SSE 直接进前端。DeepSeek → 服务端由 openai SDK 解析为 chunk 对象；BFF 每次 `encodeSseEvent` 写入的是完整帧；不完整是因为 HTTP 字节流的 read 边界与 SSE 帧边界不对齐。
- **原理 / 为什么**：数据分三层——① DeepSeek SSE → ② SDK 在服务端抽 `delta.content` → ③ BFF 重打包为 `data: {"type":"token",...}\n\n` 发给浏览器。`remainder` 解决的是第 ③ 层客户端读流问题。TCP/ReadableStream 一次 read 可能读半帧、一帧半、多帧，与发送端每次 enqueue 完整字符串无对应关系。
- **易错点 / 坑**：误以为「服务端写完整帧，客户端一次 read 就是一帧」；或把浏览器里看到的半行 `data:` 当成 DeepSeek 协议错误。服务端 `for await (chunk of upstream)` 不需要 remainder，SDK 已处理上游 SSE。
- **延伸**：
  - 分层排查：SDK 层看 chunk，BFF 层看 encodeSseEvent，客户端层看 reader + remainder ✅
  - Phase 4 扩展 SSE 事件类型时，传输层与 remainder 机制不变 ✅
- **标签**：#sse #streaming #bff #deepseek #reader
- **状态**：#待复习
- **日期**：2026-07-26

### fetch 响应体的 reader.read() 是什么

- **来源问题**：请讲一下 reader.read()。
- **结论**：`response.body.getReader()` 得到 `ReadableStreamDefaultReader`；`await reader.read()` 异步返回 `{ done, value }`，其中 `value` 是本次读到的 `Uint8Array` 字节块；`done === true` 表示流结束。Change 1.4 用 fetch POST（不用 EventSource），再 decode + parseSseChunk 消费 SSE。
- **原理 / 为什么**：Streams API 把 HTTP 流式 body 当作字节管道；read 块大小由运行时/网络决定，与 token 数、SSE 帧数无关。故需 `TextDecoder(..., { stream: true })` 处理 UTF-8 多字节字符跨 chunk 截断，并与 `remainder` 拼完整 SSE 帧。
- **易错点 / 坑**：一次 `read()` 不等于一个 `token` 事件；abort 时需同时 `AbortSignal` 取消 fetch 并 `reader.cancel()`，避免 abort 后仍触发 onEvent 更新 UI。
- **延伸**：
  - 流结束后必须 `decoder.decode()` 无参 flush 剩余字节 ✅
  - 与 EventSource 对比：后者自动读 SSE 但仅 GET，聊天 POST 必须 fetch + reader ✅
  - 🔗 https://developer.mozilla.org/en-US/docs/Web/API/ReadableStreamDefaultReader/read
- **标签**：#streaming #fetch #ReadableStream #reader #sse
- **状态**：#待复习
- **日期**：2026-07-26

### lib/api/sse.ts 的职责：SSE 编解码工具层

- **来源问题**：`lib/api/sse.ts` 这个文件的作用是什么？
- **结论**：该文件是 **SSE 流式协议的编解码工具层**，负责把 `ChatStreamEvent`（`token` / `done` / `error`）序列化为 SSE 文本帧，并在客户端从 HTTP 流中增量解析；不包含 AI 调用或 UI 状态逻辑。
- **原理 / 为什么**：项目把传输格式（SSE 字节帧）与应用语义（聊天事件）分离：`encodeSseEvent` 产出 `data: {...}\n\n`；`parseSseChunk` + `remainder` 处理 TCP/read 边界与帧边界不对齐；`consumeSseStream` 封装 `reader.read()` 循环。服务端 `app/api/chat/route.ts` 用 encode，客户端 `chatStore` 用 consume。
- **易错点 / 坑**：不要把该文件当成「聊天业务层」——它不知道 conversationId、不知道 Zustand；`done` 事件在 consume 侧通常无需单独处理，流结束即可。
- **延伸**：
  - 与 BFF 分层：DeepSeek chunk → route 编码 SSE → sse.ts 解码 → store 更新 UI ✅
  - `parseSseChunk` 的 remainder 机制见本文件第 2 次沉淀 ✅
  - Phase 4 新增 SSE 事件类型时，主要改 `types/chat.ts` 与 encode/decode，传输层不变 ✅
- **标签**：#sse #lib-api #streaming #ChatStreamEvent
- **状态**：#待复习
- **日期**：2026-07-26

### ReadableStream：流式 HTTP body 的「逐块读取管道」

- **来源问题**：什么是 ReadableStream？
- **结论**：`ReadableStream` 是 Web Streams API 中表示**可逐块读取的数据流**的类型；`fetch` 的 `response.body` 即为此类型，通过 `getReader()` + `read()` 每次取 `Uint8Array`，适合 AI 打字机、大文件、实时推送等场景。
- **原理 / 为什么**：与普通「等完整响应再 `text()`」不同，流式响应边产生边发送，降低首字节延迟与内存占用。在本项目中：Route Handler 用 `new ReadableStream` + `controller.enqueue` 写出 SSE 字节；客户端 `response.body.getReader()` 交给 `consumeSseStream` 消费。
- **易错点 / 坑**：ReadableStream 是**传输层**（字节怎么一块块来），SSE 是**应用层**（字节按 `data:` 格式表示什么事件）；一次 `read()` 不等于一个 token 或一帧 SSE。
- **延伸**：
  - 一个 stream 同时只能有一个 active reader；取消时需 `reader.cancel()` 配合 `AbortSignal` ✅
  - 与 EventSource 对比：后者自动读 SSE 但通常仅 GET，聊天 POST 需 fetch + ReadableStream ✅
  - 🔗 https://developer.mozilla.org/en-US/docs/Web/API/ReadableStream
- **标签**：#ReadableStream #streaming #fetch #web-api

### chatStore：聊天客户端状态中心与 conversationStore 分工

- **来源问题**：请讲一下 `lib/stores/chatStore.ts` 这个文件。

- **原理 / 为什么**：消息目前仅存内存（`messagesByConversation`），刷新丢失；会话元数据持久化在服务端。`abortController` 与 `activeStreamConversationId` 放在 store **外**，因它们是进行中的请求控制柄，变更不应触发 React 重渲染。

### sendMessage 流式发送流程：乐观 UI、单流约束与收尾

- **来源问题**：（结合 chatStore 讲解与 sendMessage 时序图）发送消息时客户端完整做了什么？
- **结论**：`sendMessage` 流程为：中断旧流 → 乐观插入 user + 空 assistant → `POST /api/chat` → `consumeSseStream` 逐 `token` 追加 → 正常结束或出错收尾；同一时刻仅允许一条活跃 SSE 流。
- **原理 / 为什么**：乐观更新让用户消息与空 AI 气泡立即出现；预置 assistant 占位并用固定 `assistantMessage.id` 追加 token，避免每次 set 重建整条列表。新消息前 `abortStream()`，切换会话时 `page.tsx` 也会 abort，防止串会话。
- **易错点 / 坑**：用户**取消**时保留已生成部分、不写 `error`，且 finally 里**不**重置 `streamingConversationId`（避免覆盖新会话的 streaming 状态）；**失败**时删除仍为空的 assistant 占位。`done` 事件无需专门处理。
- **延伸**：
  - 分层：UI → chatStore → sse.ts → route.ts → lib/ai/client ✅
  - `abortStream` / `clearConversationMessages` / `clearError` 分别在停止生成、删会话、切换会话时调用 ✅
  - 单流约束下，连发两条消息会先 cancel 前一条 fetch ✅
- **标签**：#chatStore #sendMessage #optimistic-ui #sse #abort
- **状态**：#待复习
- **日期**：2026-07-26
