# Change 1.6：Markdown 渲染性能调研与优化记录

> Phase：1 ChatBot　|　分支：`feature_markdown_rendering_260728`  
> 涉及：`MessageContent`、`MessageBubble`、`MessageList`、`lib/benchmark/`、`app/dev/markdown-bench`  
> 日期：2026-07-28  
> 状态：**优化已实施 · 真实路径达标（§0）**

---

## §0 Executive Summary

**问题：** 5000 字 + 20 条历史消息流式输出时，单次 chunk 更新 p95 **~90 ms**（`incremental-update-legacy`），超过 50 ms 卡顿线。

**根因：** ① 流式期间每个 chunk 反复 Markdown parse；② 无 memo，20 条历史 bubble 每 chunk 重复 render。

**方案：** P0 `React.memo(MessageBubble)` + P1 流式纯文本、结束后切 Markdown + P2 `memo(MessageContent)`。

**结果：** 真实聊天路径（`incremental-update · history=20 · p95`）**90 ms → 1.1 ms（−99%）**，全部法律向用例 **< 6 ms**，满足 60fps 预算。

**验收主指标：** 浏览器 `incremental-update · history=20 · p95`（同树增量更新，非 full-list remount）。

## 1. 背景

Change 1.6 已交付：

- `MessageContent`：`react-markdown` + `remark-gfm` + `rehype-highlight`
- assistant 消息 Markdown 渲染；user 消息纯文本
- 代码块复制、整条消息复制
- 流式时随 `content` prop 增量重渲染

实现功能可用后，需确认 **流式 + 长回复 + 有历史消息** 时渲染是否达标。按 design 约定先不做预优化，引入可控基准测试定位瓶颈，再数据驱动实施 P0/P1/P2。

## 2. 测评方法论

### 2.1 测评逻辑

不连 AI、不连网络。用代码**合成 Markdown**，模拟 `displayQueue` 的 chunk 追加：每次 `content` 变长若干字符（默认 chunk=4），测一次渲染耗时，汇总 **p50 / p95 / max / mean**。

```text
合成 Markdown → 模拟流式变长（120 steps 采样）→ 每次更新测 ms → 统计分位数
```

- **chunk**：每次 UI 更新追加的一小段文字（不是 SSE 网络包）
- 真实路径：`displayQueue` 缓冲 SSE → ~22ms/字 → `message.content` → React 重渲染

### 2.2 终端 vs 浏览器

| | 终端 `measure:markdown` | 浏览器 `/dev/markdown-bench` |
|--|-------------------------|------------------------------|
| 环境 | Node.js | Chrome + 真实 React DOM |
| 测什么 | 解析链（`renderToString` + 同插件链） | `MessageContent` 或完整 `MessageList` |
| 速度 | 快（~1 分钟） | 慢（数百～数千次 mount/render） |
| 历史消息 | 不测 | incremental / full-list 模式 |
| 用途 | 快速扫参、回归解析链 | **验收真实 UI 路径** |

### 2.3 四种浏览器基准模式

| 模式 | 渲染范围 | 回答的问题 |
|------|----------|------------|
| **content-only** | 仅 `MessageContent`（每 step remount） | 单条 Markdown 解析 + 高亮有多贵 |
| **full-list** | 完整 `MessageList`（每 step **整树 remount**） | 保守上界；**不能代表优化后真实体验** |
| **incremental-update** | 同树 `root.render` 增量更新（**优化后**） | **真实聊天路径 · 验收主指标** |
| **incremental-update-legacy** | 同上测法，优化前组件 | 同路径 A/B，量化 P0/P1 收益 |

`history=0`：仅 1 条流式；`history=20`：20 条历史 + 1 条流式（长会话）。

### 2.4 p50 / p95 与帧率

- **p95**：流式体验最关键——95% 的 step 比它快
- **p95 < 16 ms** ≈ 不拖 60fps；**p95 > 50 ms** ≈ 可感知卡顿（Long Task）
- DevTools Performance / React Profiler 验证主观感受；合成基准用于可重复对比

### 2.5 法律向 preset（推荐）

| Preset | 结构 |
|--------|------|
| **legal-typical** | `##/###` + 段落 + 列表 + 有序步骤 + 引用 |
| **legal-heavy** | 多层标题 + 嵌套列表 |
| **legal-table×N** | typical + N 个 GFM 表格 |

推荐实验套餐（`incremental-update · history=20 · p95`）：

1. `1500 · legal-typical` — 日常短答  
2. `5000 · legal-typical` — 长答主力  
3. `5000 · legal-heavy` — 结构加重  
4. `5000 · legal-table×2` / `×4` — 表格成本  

终端快速扫描：`npm run measure:markdown -- --legal`

### 2.6 工具入口

| 路径 | 作用 |
|------|------|
| `lib/benchmark/markdownFixtures.ts` | 合成 Markdown、legal preset、chunk 模拟 |
| `lib/benchmark/stats.ts` | p50/p95 统计 |

## 4. 分析与结论

### 4.1 优化前：瓶颈在哪

- **主因不是法律格式：** legal-heavy ≈ typical（legacy p95 92 vs 90 ms）；table×4 仅 +5 ms
- **字数线性增长：** content-only p95 1500→5000 字：20→32 ms
- **history=20 固定税 +55 ms：** legacy(0) 35 ms → legacy(20) 90 ms（5000 typical）
- **legacy ≈ full-list(20)：** 同量级 → 瓶颈是「每 chunk 重跑全部历史 + 流式反复 parse」，非列表壳子

### 4.2 优化后：真实路径全面达标

| 场景 | legacy p95 | optimized p95 | 目标 | 结论 |
|------|------------|---------------|------|------|
| 1500 · legal-typical | 74 ms | **0.8 ms** | < 16 ms | **达标** |
| 5000 · legal-typical | 90 ms | **1.1 ms** | < 16 ms | **达标** |
| 5000 · legal-heavy | 92 ms | **3.1 ms** | < 16 ms | **达标** |
| 5000 · legal-table×4 | 95 ms | **0.9 ms** | < 16 ms | **达标** |

全部 **< 6 ms**，流式体验达生产级标准。

### 4.3 两项优化各自贡献（A/B 分解）

| 优化 | 机制 | 证据（5000 typical） |
|------|------|----------------------|
| **P1 流式纯文本** | 消除 growing content 反复 parse | legacy(0) 35 ms → optimized(0) **0.7 ms** |
| **P0 memo 历史** | 跳过 20 条历史 bubble re-render | optimized(0) 0.7 ms → optimized(20) **1.1 ms**；legacy(0) 35 ms → legacy(20) **90 ms** |

### 4.4 关于 full-list 测法

`full-list` 每 step **整树 remount**，测不出 memo「跳过历史 re-render」的收益。优化后 full-list(20) p95 仍 59～75 ms，但真实 App 走 incremental 路径 **< 2 ms**。**勿用 full-list(20) 评判优化后体验。**

## 5. 优化方案与实现

### 5.1 优化项（已实施）

| 优先级 | 方案 | 针对问题 | 状态 |
|--------|------|----------|------|
| **P0** | `React.memo(MessageBubble)` + 稳定 props | history=20 固定税 | ✅ |
| **P1** | 流式纯文本，结束后切 Markdown | 反复 parse | ✅ |
| **P2** | `memo(MessageContent)` | 无关 parent 更新 | ✅ |
| **P3** | highlight 按需注册 | 法律场景代码块少，收益有限 | 未做 |
| **P4** | 长列表虚拟滚动 | 消息数 >>50 | 后续（1.8+） |

**明确不做：** 改 SSE/落库、引入 `rehype-raw`、为达标改 benchmark 阈值。

### 5.2 当前数据流

```text
SSE token → displayQueue（~22ms/字）→ chatStore.appendAssistantChunk
    → page 订阅 messagesByConversation 重渲染
    → MessageList.map → memo 跳过未变历史 MessageBubble
    → 流式 assistant（最后一条）：纯文本 whitespace-pre-wrap
    → 流式结束：useMarkdown=true → MessageContent → react-markdown 一次性 parse
```

- `MessageBubble`：`React.memo` + 自定义 props 比较（忽略 `onDelete` 引用）
- `MessageList`：流式时最后一条 assistant 设 `useMarkdown={false}`
- `MessageContent`：`memo` 包裹

### 5.3 代码改动

| 文件 | 改动 |
|------|------|
| `MessageBubble.tsx` | `memo` + `useMarkdown` prop |
| `MessageList.tsx` | 流式时最后一条 assistant 设 `useMarkdown={false}` |
| `MessageContent.tsx` | `memo` 包裹 |
| `MarkdownBenchClient.tsx` | 四模式基准 + incremental-legacy A/B |
| `LegacyMessageList/Bubble/Content.tsx` | 优化前行为，仅 dev 基准 |

### 5.4 回归验证流程


## 6. 面试官提问与解答

### Q1：怎么发现 Markdown 渲染有性能问题的？

**答：** 按 spec 先实现功能，design 约定不做预优化。上线前用合成基准模拟流式 chunk，测 p50/p95。5000 字 + 20 条历史 **legacy p95 ~90 ms**（full-list 保守测法 ~175 ms），超过 50 ms 卡顿线，DevTools 可复现 Long Task。数据驱动决定优化。

### Q2：为什么用合成 Markdown，不直接问 AI 测？

**答：** AI 输出不可控，网络/SSE/模型延迟污染结果。合成 fixture 固定字数、表格数、历史条数，只变一个变量，适合回归。真实对话 + Performance 作 sanity check。

### Q3：为什么看 p95 而不是 p50？

**答：** 流式上百次小更新，用户感受取决于「慢的 step 是否频繁」。p95 代表最坏常见情况；p50 是典型。mean 易被极值拉动。

### Q4：content-only 和 incremental 差距说明什么？

**答：** content-only 高 → 瓶颈在 parse。incremental-legacy 远高于 content-only → 瓶颈在列表 re-render。5000 typical：content-only 32 ms，legacy(20) 90 ms → **memo 是 P0**；legacy(0) 35 ms ≈ content-only → **P1 针对 parse**。优化后 incremental(20) **1.1 ms**。

### Q5：为什么 legal-heavy 和 typical 几乎一样？

**答：** 真正贵的是 **每次对整个 content 做 remark/rehype 管道** 和 **React reconcile**，不是 AST 节点数量。嵌套列表/表格只带来边际差异（+5 ms 量级）。

### Q6：16 ms 和 50 ms 阈值怎么来的？

**答：** 60fps ≈ 16.7 ms/帧；超过 16 ms 可能掉帧。50 ms 是 Long Task 常见可感知卡顿线。合成基准作统一标尺，真机用 DevTools 验证。

### Q7：流式时每个 token 都会重渲染整个列表吗？

**答：** **优化前：** 每次 content 更新，`MessageList` 执行所有 bubble 的 render；无 memo 时 diff 全部子树；流式那条 full Markdown parse。**优化后：** memo 跳过历史 bubble；流式那条纯文本不 parse。history=20 从 +55 ms 固定税变为 +0.4 ms 增量。

### Q8：第一优化为什么选 React.memo，不是虚拟列表？

**答：** history=20 带来 ~55 ms 固定税，20 条远未到虚拟列表刚需（通常 100+ 才明显）。memo 改动面小、针对性强。虚拟列表留作 P4。

### Q9：流式纯文本、结束再 Markdown 的 trade-off？

**答：** **Pros：** 流式阶段避免反复 parse，p95 从 35 ms 降至亚毫秒。**Cons：** 流式中无格式化，结束时有「闪变」。可后续节流 parse 折中。

### Q10：法律场景还要测代码块矩阵吗？

**答：** 不必作主场景。法律回答以段落、列表、表格为主，**legal-typical / legal-table** 更有代表性。代码块矩阵（附录）仅作技术文档式回复上限参考。

### Q11：优化后怎么证明没退化？

**答：** 固定 §3.1 baseline，同参数重跑 §3.2；对比 incremental p95。CI 可选 `npm run measure:markdown -- --legal` 作解析链回归。

### Q12：displayQueue 和渲染性能什么关系？

**答：** displayQueue 控制 **更新频率**（~22ms/字）；渲染优化控制 **单次成本**。两者正交——队列再慢也挡不住单次 90 ms 的主线程占用。
