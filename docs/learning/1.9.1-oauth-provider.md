### Auth.js 的职责：连接登录方式、会话与业务代码

- **来源问题**：Auth.js 的作用是什么？
- **结论**：Auth.js 是认证与会话管理框架，负责接入 Credentials、GitHub、Google 等登录方式，生成和校验登录凭证，处理 Cookie、CSRF、登录回调和退出登录。
- **原理 / 为什么**：业务代码不需要自己实现 OAuth 授权码交换、Cookie 签发和 Session 解析；项目通过 `auth()`、`signIn()`、`signOut()` 和认证 Route Handler 使用这些能力。
- **延伸**：
  - 服务端组件可用 `auth()` 读取当前用户，客户端组件可通过 `SessionProvider` / `useSession()` 读取会话 ✅
  - OAuth Provider 负责第三方身份，业务用户仍应落到自己的 `User` 表中 ✅
  - 🔗 https://authjs.dev/

### JWT Session 与数据库 Session 的区别

- **来源问题**：`auth.config.ts` 里 JWT、Session 两种策略有什么不同？
- **结论**：Auth.js 的 `session.strategy` 实际是在 `jwt` 和 `database` 之间选择；当前项目使用 `jwt`，不是数据库 Session 策略。
- **原理 / 为什么**：JWT 策略把经过签名/加密的 Token 放在 Cookie 中，服务端验证后直接得到用户信息；Database 策略把随机 Session Token 放在 Cookie 中，再用它查询数据库的 `Session` 表。前者减少数据库查询，后者更容易通过删除数据库记录主动撤销单个会话。
- **易错点 / 坑**：`session: { strategy: "jwt" }` 中的 `session` 是配置项，`jwt` 是策略值；不能把它理解成“JWT 和 Session 两种并列对象”。
- **延伸**：
  - JWT 策略更依赖 `AUTH_SECRET`，Secret 变化会使现有登录凭证失效 ✅
  - Database 策略适合设备管理、强制下线等场景，但需要额外数据库查询 ✅
  - 🔗 https://nextjs-docker-example.authjs.dev/server-example
- **标签**：#jwt #session #authjs
- **状态**：#待复习
- **日期**：2026-08-08

### Cookie、Session 对象与 Session 表不是同一个东西

- **来源问题**：服务端根据 Cookie 解析出的 Session 是什么？它和前面说的 Session 是同一个东西吗？什么是登录 Session 记录？
- **结论**：登录 Cookie、运行时 Session 对象和数据库 Session 表记录是三个相关但不同的层次；当前 JWT 模式主要使用前两者。
- **原理 / 为什么**：服务端读取 `authjs.session-token`，验证 JWT 后构造运行时 Session 对象，例如 `session.user.id`；如果使用 Database 策略，Cookie 中只放随机 Token，服务端再根据 Token 查询 `Session` 表。当前项目虽然定义了 `Session` 模型，但 JWT 策略下不依赖它保存登录状态。
- **延伸**：
  - `Session` 对象可由服务端 `auth()` 或客户端 `useSession()` 取得 ✅
  - `Session` 表通常保存 `sessionToken`、`userId` 和 `expires`，不保存密码 ✅
  - 🔗 https://nextjs-docker-example.authjs.dev/client-example
- **标签**：#cookie #session #database-session
- **状态**：#待复习

### 三个 Auth.js Cookie 的职责

- **来源问题**：浏览器中的 `authjs.callback-url`、`authjs.csrf-token`、`authjs.session-token` 分别是什么？
- **结论**：只有 `authjs.session-token` 是当前登录状态的核心凭证；另外两个分别用于登录后跳转和 CSRF 防护。
- **原理 / 为什么**：`authjs.session-token` 携带 JWT；`authjs.callback-url` 保存认证完成后的跳转地址；`authjs.csrf-token` 用于防止跨站伪造认证请求。三者都不能当作密码，Session Token 尤其不能复制给别人。
- **易错点 / 坑**：Cookie 名称中有 `session` 不代表一定存在数据库 Session 行；当前项目的 Session 由 JWT 承载。
- **延伸**：
  - 生产 HTTPS 环境下 Cookie 名称可能带 `__Secure-` 前缀 ✅
  - Cookie 的 `HttpOnly`、`Secure`、`SameSite` 属性会影响脚本访问和跨站请求行为 ✅
- **标签**：#cookie #csrf #security
- **状态**：#待复习

### `auth.config.ts` 与 `auth.ts` 的分工

- **来源问题**：请详细解释 `auth.ts` 和 `auth.config.ts`。
- **结论**：`auth.config.ts` 放通用认证规则，`auth.ts` 创建完整 Auth.js 实例并接入 Prisma、Credentials Provider 和 OAuth 安全校验。
- **原理 / 为什么**：`auth.config.ts` 配置登录页、JWT 策略、Provider 和 JWT/Session callbacks；`auth.ts` 通过 `PrismaAdapter(prisma)` 接入数据库，添加邮箱密码 `authorize()`，并导出 `auth`、`signIn`、`signOut`、`handlers` 供页面、Server Action 和 Route Handler 使用。
- **易错点 / 坑**：`jwt` callback 负责把用户信息写入 Token，`session` callback 负责把 Token 信息暴露为 `session.user.id`；两者不是同一个回调。
- **延伸**：
  - `authorize()` 返回 `null` 表示 Credentials 认证失败，不应返回密码哈希 ✅
  - OAuth 登录还需要 `Account` 表保存 Provider 与用户的绑定关系 ✅
- **标签**：#auth-ts #auth-config #callbacks
- **状态**：#待复习
- **日期**：2026-08-08

### Google OAuth 配置的四个环境变量

- **来源问题**：`AUTH_GOOGLE_ID` 和 `AUTH_GOOGLE_SECRET` 应该怎么获取？Google 项目里如何配置 OAuth？
- **结论**：需要在 Google Cloud 项目中配置 OAuth consent screen，创建 Web application OAuth Client，并把 Client ID、Client Secret 写入本地 `.env`。
- **原理 / 为什么**：Google 会把用户授权结果回调到 Auth.js 的固定地址；本项目本地回调地址是 `http://localhost:3000/api/auth/callback/google`，必须与 Google Cloud 配置完全一致。测试状态下还要把实际登录邮箱加入 Test users。
- **易错点 / 坑**：Client Secret 不能提交到 Git；回调地址的协议、端口、路径和尾部斜杠都可能影响匹配。
- **延伸**：
  - 生产环境应为部署域名配置对应的 HTTPS 回调地址 ✅
  - Google 的 External 测试应用需要维护测试用户列表 ✅
  - 🔗 https://developers.google.com/identity/protocols/oauth2/web-server?hl=zh-cn
- **标签**：#google-oauth #oauth #environment-variables

### OAuth `fetch failed` 的排查方向

- **来源问题**：点击 Google 登录时出现 `TypeError: fetch failed`，是否只要开启 VPN 就能访问 Google？
- **结论**：这是 Auth.js 服务端访问 Google OpenID 配置或授权端点失败，不一定是 Client ID/Secret 错误；必须确认 Node.js 所在的网络路径能够访问 Google。
- **原理 / 为什么**：浏览器能访问 Google 不代表 PowerShell 或 Node.js 使用同一条代理路径。Windows 系统代理、浏览器代理、VPN 分流和 TUN 虚拟网卡可能彼此独立；`InterfaceAlias: Meta` 只能说明 TUN 网卡存在，不能单独证明代理节点可用。
- **易错点 / 坑**：Fake-IP 模式下 `Test-NetConnection` 可能测到虚拟地址；应使用实际 HTTPS 请求和代理日志验证。若关闭 Google 环境变量，则不会触发 Google Provider，但不需要删除 OAuth 代码。
- **延伸**：
  - 可用 `curl.exe -I https://accounts.google.com/.well-known/openid-configuration` 验证终端 HTTPS 通路 ✅
  - 如果代理直连命令成功而 TUN 失败，应检查代理客户端的节点、规则和防火墙配置 ✅
- **标签**：#oauth-debugging #network #vpn
- **状态**：#待复习
- **日期**：2026-08-08

### 登录页 Hydration mismatch 的服务端环境变量原因

- **来源问题**：登录页出现 `Hydration failed because the server rendered HTML didn't match the client`，差异集中在 OAuth 按钮区域，根本原因是什么？
- **结论**：不能在 Client Component 中直接根据服务端私有环境变量决定首屏结构；服务端能读到 OAuth 配置，客户端读不到非 `NEXT_PUBLIC_*` 变量，就会产生不同 HTML。
- **原理 / 为什么**：登录页原先标记为 `use client`，同时调用读取 `AUTH_GOOGLE_*` 的函数。服务端渲染了 OAuth 按钮，客户端渲染时 Provider 列表为空，React 因树结构不一致而重新生成客户端树。修复方式是让页面保持 Server Component，只把 `LoginForm` 保持为 Client Component，并把稳定的 Provider 列表作为 props 传入。
- **延伸**：
  - 修改 Server/Client 边界后应停止开发服务、清理 `.next` 并重启 ✅
  - 其他会造成 Hydration mismatch 的来源包括随机数、时间、Locale 和浏览器扩展 ✅
- **标签**：#nextjs #hydration #server-component
- **状态**：#待复习
- **日期**：2026-08-08

### 登录后侧栏用户菜单不同步的 SessionProvider 问题

- **来源问题**：用户刚登录后，侧边栏为什么没有显示账号和“退出登录”按钮？
- **结论**：登录成功后的 Cookie 已经更新，但根布局中长期存在的 `SessionProvider` 可能仍保留登录前的 `session=null`；客户端 `useSession()` 未重新同步时，`UserMenu` 会返回 `null`。
- **原理 / 为什么**：Next.js 导航不一定重新挂载根布局，Provider 可能继续使用旧的初始 Session。解决方式是在客户端检测到 `unauthenticated` 时调用 Auth.js 的 `update()`，重新请求 `/api/auth/session`，再让 `UserMenu` 根据最新 `session.user` 渲染账号和退出按钮。
- **易错点 / 坑**：`auth()` 服务端读取成功，不代表已经挂载的客户端 `useSession()` 状态会自动同步；服务端 Session 和客户端 Session 状态需要分别考虑。
- **延伸**：
  - Auth.js 官方客户端示例需要 `SessionProvider`，服务端示例直接调用 `auth()` ✅
  - 应避免在 effect 中同步调用 `setState`，否则可能触发 React lint 的 cascading render 规则 ✅
  - 🔗 https://nextjs-docker-example.authjs.dev/client-example
- **标签**：#session-provider #react #nextjs
- **状态**：#待复习
- **日期**：2026-08-08

### Prisma Schema 与生成客户端字段不一致导致登录失败

- **来源问题**：没有修改密码，为什么注册已有账号时会报 `User.passwordHash does not exist`？
- **结论**：问题不是密码错误，而是代码、Prisma Client 和实际数据库字段名不一致；当前数据库字段是 `User.password`，代码查询了不存在的 `passwordHash`。
- **原理 / 为什么**：即使 `findUnique` 只按邮箱过滤，Prisma 读取 User 默认字段时仍会访问整行列，因此缺失的 `passwordHash` 也会让邮箱查询失败。修复必须统一 Schema、生成客户端和业务代码的字段名，并重新执行 `prisma generate`。
- **易错点 / 坑**：不要看到错误就直接重置用户密码或删除账号；先比较 `prisma/schema.prisma`、数据库迁移和生成客户端的字段定义。
- **延伸**：
  - 数据库字段改名时应通过正式 migration，而不是只改 TypeScript 字段名 ✅
  - `prisma generate` 只更新客户端类型和查询代码，不会自动修改数据库结构 ✅
- **标签**：#prisma #database-schema #debugging
- **状态**：#待复习
- **日期**：2026-08-08
