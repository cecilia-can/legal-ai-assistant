### Next.js 的 Metadata 是 TypeScript 类型，不是 JS 原始类型

- **来源问题**：`Metadata` 是什么数据类型吗？
- **结论**：`Metadata` 是 Next.js 从 `"next"` 导出的 TypeScript 类型（interface），用于标注 App Router 中 `layout.tsx` / `page.tsx` 导出的 `metadata` 对象；运行时只是普通 JS 对象，编译后类型会被擦除。
- **原理 / 为什么**：App Router 通过读取导出的 `metadata` 对象自动生成 `<head>` 内容（title、description、Open Graph 等）。TypeScript 类型只在开发期做校验，不参与运行时。
- **易错点 / 坑**：不要把 `Metadata` 当成 JavaScript 内置类型（如 `string`）；它只在 `import type { Metadata } from "next"` 的 TypeScript 语境下存在。
- **延伸**：
  - 同一文件还可导出 `generateMetadata()` 函数，按路由动态生成 metadata ✅
  - `metadata` 与 Client Component 不兼容——含 `"use client"` 的文件不能导出 metadata ✅
  - 🔗 https://nextjs.org/docs/app/api-reference/functions/generate-metadata
- **标签**：#nextjs #typescript #metadata #app-router

### next/font/google 加载字体并注册 CSS 变量

- **来源问题**：`layout.tsx` 里 `Geist({ variable: "--font-geist-sans", ... })` 这段代码的作用是什么？
- **结论**：通过 Next.js 的 `next/font/google` 在构建时优化加载 Geist / Geist Mono 字体，并把它们注册为 CSS 变量（`--font-geist-sans`、`--font-geist-mono`），供全局样式引用。
- **原理 / 为什么**：`next/font` 会在构建阶段下载并自托管字体，减少对外部 Google Fonts 的请求，并采用更稳定的加载策略以降低布局偏移（FOIT/FOUT）。`variable` 选项会在 DOM 上生成对应 class，使 CSS 变量生效。
- **易错点 / 坑**：CSS 变量本身不会自动生效——需要在 `<html>` 或父元素上挂载 `geistSans.variable` 等 class；`subsets: ["latin"]` 只加载拉丁字符子集，中文内容会回退到 fallback 字体。
- **延伸**：
  - `globals.css` 中通过 `@theme inline` 把 `--font-geist-sans` 映射为 Tailwind 的 `font-sans` ✅
  - 中文字体优化可在 `@theme` 或 `font-family` fallback 链中追加本地/系统字体 ✅
  - 🔗 https://nextjs.org/docs/app/building-your-application/optimizing/fonts
- **标签**：#nextjs #fonts #css-variables
- **状态**：#待复习
- **日期**：2026-07-15

### React 组件 props 解构 + TypeScript 类型标注

- **来源问题**：`{ children }: Readonly<{ children: React.ReactNode }>` 这个写法是什么意思？
- **结论**：这是函数组件参数的**解构**加上 **TypeScript 类型标注**：从 props 对象中直接取出 `children`，并声明其类型为 `React.ReactNode`；`Readonly<>` 表示 props 只读。
- **原理 / 为什么**：React 组件本质上是接收 props 对象的函数。解构写法等价于 `props.children`，但更简洁。`React.ReactNode` 表示一切 React 可渲染内容（JSX、字符串、数组等）。Next.js 模板常用 `Readonly<>` 防止在组件内意外修改 props。
- **易错点 / 坑**：解构参数里的 `{ children }` 是 JavaScript 语法，后面的 `: Readonly<...>` 是 TypeScript 类型——两者职责不同，不要混淆。
- **延伸**：
  - 多 prop 解构写法相同，如 `{ sidebar, main }: AppShellProps` ✅
  - 可选 prop 用 `?` 标注，如 `activeId?: string` ✅
- **标签**：#react #typescript #props
- **状态**：#待复习
- **日期**：2026-07-15

### CSS :root、@ 规则与 `--` 自定义属性

- **来源问题**：`globals.css` 里为什么是 `:root`？`@theme` / `@media` 是什么？为什么变量都以 `--` 开头？
- **结论**：`:root` 是选中文档根元素（`<html>`）的 CSS 伪类，适合定义全局 CSS 变量；`@media` 是标准 CSS at-rule；`@theme` 是 Tailwind v4 的 at-rule；`--` 前缀是 CSS 自定义属性（CSS Variables）的语法规定。
- **原理 / 为什么**：`:root` 上的变量全页可用。`@media (prefers-color-scheme: dark)` 按系统主题条件覆盖变量值。`--background` 等是应用语义 token，经 `@theme inline` 映射为 `--color-background` 后，Tailwind 才能生成 `bg-background` 等工具类。
- **易错点 / 坑**：`:root` 的冒号是伪类语法，不是 class 名（`.root` 完全不同）。使用 `@theme inline` 引用外部 CSS 变量时，工具类会直接 resolve 到 `var(--background)` 而非中间层 `--color-background`，这样 dark mode 覆盖 `:root` 变量时工具类也能同步变化。
- **延伸**：
  - `@theme inline` 适合 token 引用 `:root` 或运行时 CSS 变量；普通 `@theme` 会额外生成中间 CSS 变量 ✅
  - 应用内手动切换主题需用 `.dark` class 或 `data-theme` 覆盖变量，而非仅依赖 `prefers-color-scheme` ✅
  - 🔗 https://tailwindcss.com/docs/theme
  - 🔗 https://developer.mozilla.org/en-US/docs/Web/CSS/:root
- **标签**：#css #tailwind #dark-mode #css-variables
- **状态**：#待复习
- **日期**：2026-07-15

### prefers-color-scheme 实现系统级深/浅色切换

- **来源问题**：`@media (prefers-color-scheme: dark)` 是为了白天/黑夜模式切换吗？
- **结论**：是，但它是**跟随操作系统主题**自动切换，不是应用内的手动开关。系统在 dark 模式下，`:root` 里的 `--background` 等变量被覆盖，所有引用处（含 Tailwind 工具类）同步变色。
- **原理 / 为什么**：只改 CSS 变量而不改组件代码，实现"一处定义、全局生效"。`body { background: var(--background) }` 和 `bg-background` 都依赖同一套变量。
- **易错点 / 坑**：用户浏览器/系统设为 light 时，即使用户觉得"现在是晚上"，也不会进入 dark 样式——它读的是系统设置，不是时间。
- **延伸**：
  - 手动主题切换常用 `next-themes` 或自研 `.dark` class + `localStorage` ✅
  - Tailwind v4 可用 `@variant dark` 定义 dark 变体 ⚠️需查证
  - 🔗 https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-color-scheme
- **标签**：#css #dark-mode #tailwind
- **状态**：#待复习
- **日期**：2026-07-15

### "use client" 标记客户端组件

- **来源问题**：`app/page.tsx` 顶部 `"use client"` 是什么意思？
- **结论**：Next.js App Router 指令，声明该文件是 **Client Component**，代码会打包到浏览器端执行，可使用 `useState`、`useEffect`、事件处理等交互逻辑。
- **原理 / 为什么**：App Router 默认组件是 Server Component（在服务器渲染，不发送组件逻辑到浏览器）。一旦需要 state 或浏览器 API，必须在文件顶部加 `"use client"`。该文件中 import 的组件也会被视为客户端组件（除非自身是 server-only）。
- **易错点 / 坑**：Server Component 不能传 event handler 给 Client Component 的"中间层"——需要交互的叶子组件或其父级需标记 `"use client"`。含 `"use client"` 的文件不能导出 `metadata`。
- **延伸**：
  - 最佳实践：尽量把 `"use client"` 推到组件树叶子，减小客户端 bundle ✅
  - Change 1.4+ 流式 AI 回复时，Server Component 负责数据、Client Component 负责渲染流 ✅
  - 🔗 https://nextjs.org/docs/app/building-your-application/rendering/client-components
- **标签**：#nextjs #react #server-components #client-components
- **状态**：#待复习
- **日期**：2026-07-15

### TypeScript 数组类型 `T[]` vs 泛型工具类型 `Record<K, V>`

- **来源问题**：`Conversation[]` 为什么直接是数组，而 `Record<string, ChatMessage[]>` 还有 `<>`？
- **结论**：`[]` 后缀表示"某类型的数组"；`Record<K, V>` 是 TypeScript 内置泛型，`<>` 内填键类型和值类型，表示一个对象/map 结构。两者语法职责不同，不是同一种东西。
- **原理 / 为什么**：`Conversation[]` = Conversation 对象组成的列表（侧边栏会话列表）。`Record<string, ChatMessage[]>` = 以 string（会话 id）为键、ChatMessage 数组为值的对象（每个会话对应的消息列表）。`ChatMessage[]` 里的 `[]` 仍是数组语法，只是作为 Record 的**值类型**写在 `<>` 内。
- **易错点 / 坑**：不要把 `<>` 一律当成"数组"——在 `Record<...>` 里它是泛型参数分隔符。`Record<string, ChatMessage[]>` 等价于 `{ [key: string]: ChatMessage[] }`。
- **延伸**：
  - 后续 Change 1.3 持久化时，同样结构可从 API/数据库加载 ✅
  - 若键类型有限，可用 `{ [id: string]: ChatMessage[] }` 或 `Map<string, ChatMessage[]>`（Map 不适合直接 JSON 序列化）✅
- **标签**：#typescript #generics #data-structure
- **状态**：#待复习
- **日期**：2026-07-15

### AppShell 组合模式：命名插槽式 props

- **来源问题**：`{ sidebar, main }: AppShellProps` 请讲解一下这个写法。
- **结论**：与 `{ children }` 同类写法——解构 props 并标注类型。`AppShell` 是布局壳组件，接收 `sidebar` 和 `main` 两个 `ReactNode` 插槽，只负责排列位置，不关心具体内容。
- **原理 / 为什么**：这是 React **组合模式（Composition）**：父组件（`page.tsx`）决定 sidebar/main 里放什么，布局组件只提供结构。比单一 `children` 更语义化，适合多区域布局。
- **易错点 / 坑**：`sidebar` / `main` 的类型是 `ReactNode` 而非具体组件类型——布局组件不应耦合业务逻辑。
- **延伸**：
  - 类似 Vue 的 named slots / Web Components 的 slot 概念 ✅
  - 更复杂场景可用 `children` + `React.Children` 或 Context，但命名 prop 对此类双栏布局最直观 ✅
- **标签**：#react #composition #layout
- **状态**：#待复习
- **日期**：2026-07-15

### aria-current 标记当前选中项（无障碍）

- **来源问题**：`aria-current` 属性的作用是干嘛的？
- **结论**：ARIA 无障碍属性，告知辅助技术（屏幕阅读器）当前元素是集合中的"当前项"。在 `ConversationList` 中，选中对话设 `aria-current="true"`，未选中则不设置。
- **原理 / 为什么**：视觉用户靠背景色（`bg-primary/10`）区分选中项；非视觉用户需要语义标记。`aria-current` 与 CSS 样式互补，不是替代关系。
- **易错点 / 坑**：同一集合中只应有一个元素标记为 current。取值包括 `page`、`step`、`location`、`true` 等——会话列表用 `"true"` 合适；导航链接常用 `"page"`。
- **延伸**：
  - 键盘导航列表还可配合 `role="listbox"` + `aria-selected` 模式，但 button 列表用 `aria-current` 更轻量 ✅
  - 仅图标按钮需配合 `aria-label` 或 visually hidden label（如 `sr-only`）✅
  - 🔗 https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-current
- **标签**：#a11y #aria #react
- **状态**：#待复习
- **日期**：2026-07-15

### Enter 发送与 Shift+Enter 换行：form submit vs keydown

- **来源问题**：Enter 发送、Shift+Enter 换行怎么实现？`handleSubmit` 和 `handleKeyDown` 有什么区别？
- **结论**：两者都是**发送入口**，最终都调用同一个 `submitMessage()`。`handleKeyDown` 拦截 Enter（无 Shift）并 `preventDefault()` 阻止默认换行；Shift+Enter 不拦截，走 textarea 默认换行。`handleSubmit` 处理表单提交（点击「发送」按钮）。
- **原理 / 为什么**：textarea 内按 Enter 默认行为是换行，不会触发表单 submit。因此需要 `onKeyDown` 单独处理 Enter 快捷键。点击 `type="submit"` 按钮则走 form 的 `onSubmit`。`submitMessage()` 集中处理校验、回调、清空输入，避免重复逻辑。
- **易错点 / 坑**：若只有 `handleSubmit` 没有 `handleKeyDown`，Enter 只会换行不发送。若只有 `handleKeyDown` 没有 `handleSubmit`，点按钮不会发送。`event.preventDefault()` 在 form submit 中用于阻止页面刷新。
- **延伸**：
  - 移动端软键盘"发送"键可通过 `enterKeyHint="send"` 优化 ⚠️需查证
  - 接入 AI 流式回复时，发送后需 `disabled` 输入框防止重复提交 ✅
- **标签**：#react #forms #keyboard #chat-input
- **状态**：#待复习
- **日期**：2026-07-15
