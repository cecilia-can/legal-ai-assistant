### TypeScript `Record<string, ChatMessage[]>` 含义

- **来源问题**：`Record<string, ChatMessage[]>` 这是什么意思？
- **结论**：TypeScript 类型，表示以 `string` 为键、`ChatMessage` 数组为值的对象（字典/map），等价于 `{ [key: string]: ChatMessage[] }`。
- **原理 / 为什么**：`Record<K, V>` 是内置泛型，`<>` 内填键类型和值类型；这里的 `<>` 是泛型参数分隔符，不是数组语法。`ChatMessage[]` 中的 `[]` 才表示数组。在 `page.tsx` 里，`messagesByConversation` 即此类型：每个会话 id 对应一条消息列表。
- **易错点 / 坑**：不要把 `Record<...>` 的 `<>` 一律当成「数组标记」；键不存在时访问得到 `undefined`，读取时常用 `messagesByConversation[activeId] ?? []` 兜底。
- **延伸**：
  - 与 `Conversation[]` 对比：后者是会话对象的**数组**（列表），前者是**对象/map**（按 id 索引）✅
  - Change 1.5 消息持久化后，同样结构可从 API 加载 ✅
- **标签**：#typescript #generics #data-structure

### async 函数返回类型 `Promise<string>`

- **来源问题**：`readErrorMessage` 中的 `Promise<string>` 是什么意思？
- **结论**：`Promise<string>` 是 TypeScript 返回类型注解，表示该函数是异步的，调用后不会立刻得到 `string`，而是得到一个 Promise；Promise 完成后才会解析为 `string`。
- **原理 / 为什么**：函数标记为 `async` 且内部有 `await response.json()` 等异步操作，解析响应体需要等待。`async` 函数即使写 `return fallback`，实际返回的也是自动包装后的 `Promise<string>`，不是裸字符串。调用方需用 `await readErrorMessage(...)` 才能得到 `string`，例如 `throw new Error(await readErrorMessage(...))`。
- **易错点 / 坑**：不要把 `readErrorMessage(...)` 的返回值直接当 `string` 用；忘记 `await` 会把 Promise 对象传给 `new Error()`。`Promise<void>` 同理，表示异步完成但无有意义返回值。
- **延伸**：
  - `await` 会「拆包」Promise：`await readErrorMessage(...)` 的类型是 `string` ✅
  - 不用 `await` 时可用 `.then()` 链式处理，效果等价 ✅
  - 🔗 https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise
- **标签**：#typescript #async #promise
- **状态**：#待复习

### `response.json()` 与 `as { error?: unknown }` 类型断言

- **来源问题**：`const data = (await response.json()) as { error?: unknown };` 这一行是什么意思？为什么要 `as { error?: unknown }`？
- **结论**：这行先异步解析 HTTP 响应体为 JSON 对象，再用类型断言告诉 TypeScript：`data` 可能是带可选 `error` 字段的对象；`as` 只影响编译期类型，不改变运行时数据。
- **原理 / 为什么**：`Response.json()` 返回 `Promise`，需 `await` 等待解析完成。其解析结果在 TypeScript 中通常是宽泛类型（如 `any` 或 `unknown`），编译器不知道具体结构。本项目 API 出错时返回 `{ error: "..." }`（见 `app/api/conversations/[id]/route.ts`），故断言为 `{ error?: unknown }`：`error?` 表示字段可选，`unknown` 迫使下一步用 `typeof data.error === "string"` 做运行时收窄，比直接断言为 `string` 更安全。
- **易错点 / 坑**：`as` 不是运行时校验，API 若返回意外结构 TypeScript 不会报错；JSON 解析失败会被外层 `try/catch` 捕获并回退到 `fallback`。不要把 `as` 当成数据转换。
- **延伸**：
  - 更严格的做法：先 `const data: unknown = await response.json()`，再写 type guard 或 Zod schema 校验 ✅
  - 浏览器 `Response.json()` 解析成功返回 JavaScript 对象（不一定是「对象类型」，也可能是数组等）🔗 https://developer.mozilla.org/en-US/docs/Web/API/Response/json
  - 与成功响应的 `(await response.json()) as ConversationJson[]` 同类模式：都是为 untrusted 的 JSON 补类型 ✅
- **标签**：#typescript #fetch #type-assertion #error-handling
- **状态**：#待复习
- **日期**：2026-07-22

### TypeScript `Pick<T, K>` 与 `serializeConversation` 参数类型

- **来源问题**：`serializeConversation` 里 `Pick<Conversation, "id" | "title" | "createdAt" | "updatedAt"> & { createdAt: Date; updatedAt: Date }` 是什么意思？`Pick` 的作用是什么？
- **结论**：`Pick` 从 `Conversation` 类型中只取出指定的四个属性组成新类型；`&` 交叉类型进一步强调 `createdAt` / `updatedAt` 必须是 `Date`，以便安全调用 `.toISOString()`。
- **原理 / 为什么**：`Pick<T, K>` 是 TypeScript 内置工具类型，等价于手写 `{ id: string; title: string; createdAt: Date; updatedAt: Date }`。用 `Pick` 而非完整 `Conversation` 是为了表达「序列化只需这四个字段」，且允许传入 Prisma 查出的对象（可能附带 `messages` 等额外字段）。函数职责是把内存中的 `Date` 转为 API 用的 ISO 字符串，返回 `ConversationJson`。
- **易错点 / 坑**：当前 `types/chat.ts` 里的 `Conversation` 本就四个字段，`Pick` 结果与 `Conversation` 相同，但语义上是「最小依赖」；`& { createdAt: Date; updatedAt: Date }` 在现有类型下基本冗余，主要起文档/约束作用。
- **延伸**：
  - 成对函数：`parseConversationJson` 把 ISO 字符串转回 `Date` 供前端 store 使用 ✅
  - 类似工具类型还有 `Omit<T, K>`（排除字段）、`Partial<T>`（全部可选）✅
  - 🔗 https://www.typescriptlang.org/docs/handbook/utility-types.html#picktype-keys
- **标签**：#typescript #pick #api #serialization
- **状态**：#待复习

### 函数参数名 `conversation` 与类型名 `Conversation` 的区别

- **来源问题**：`Pick` 的前边还有一个 `conversation`，是什么意思？
- **结论**：`conversation` 是**参数名**（变量名），`Pick<Conversation, ...>` 是**参数类型**；二者通过 `:` 分隔，语法为 `参数名: 类型`。
- **原理 / 为什么**：TypeScript 函数参数写法与 `const conversation: string` 相同——名字供函数体内引用（如 `conversation.id`），类型供编译器检查。`Conversation`（大写）是 imported 的类型；`conversation`（小写）是本次入参的标识符，可改为 `conv` 等而不影响类型。
- **易错点 / 坑**：不要把参数名 `conversation` 当成 `Pick` 泛型里的 `Conversation`；大小写不同、职责不同（运行时变量名 vs 编译期类型名）。
- **延伸**：
  - `Pick` 的第一个泛型参数必须是**类型**，不能是参数名 ✅
  - 解构参数同理：`({ id }: { id: string })` 也是「名字 + 类型」分离 ✅
- **标签**：#typescript #function-parameters
- **状态**：#待复习

### POST 请求体解析中的 `as { title?: unknown }`

- **来源问题**：`route.ts` 里 `(await request.json().catch(() => ({}))) as { title?: unknown }` 中 `as` 的作用是什么？
- **结论**：`as` 是 TypeScript 类型断言，告诉编译器将 JSON 解析结果视为「可能有 `title` 字段的对象」；`title?` 表示可选，`unknown` 表示类型未确定，只影响编译期，不做运行时校验。
- **原理 / 为什么**：`request.json()` 返回 Promise，解析结果在 TS 中是宽泛类型。客户端 POST body 可能是 `{ title: "..." }`、`{}` 或非法 JSON（`.catch(() => ({}))` 兜底为空对象）。断言为 `{ title?: unknown }` 后，编译器允许访问 `body.title`，但下一步必须用 `typeof body.title === "string"` 做运行时收窄，比直接断言为 `string` 更安全。
- **易错点 / 坑**：`as` 不会过滤非法数据——若客户端传 `{ title: 123 }`，TS 不报错，需靠 `typeof` 拒绝；JSON 解析失败时 `.catch` 返回 `{}`，会走默认标题逻辑。
- **延伸**：
  - 与 store 里 `(await response.json()) as ConversationJson` 同类：均为 untrusted JSON 补类型 ✅
  - 更严格方案：Zod / type guard 做 schema 校验 ✅
  - 🔗 https://www.typescriptlang.org/docs/handbook/2/everyday-types.html#type-assertions
- **标签**：#typescript #type-assertion #api #request-body
- **状态**：#待复习
- **日期**：2026-07-22

### `typeof` 运行时类型检查与 TypeScript 类型收窄

- **来源问题**：`route.ts` 里 `typeof body.title === "string" && body.title.trim()` 中 `typeof` 的用法和作用是什么？
- **结论**：`typeof` 是 JavaScript 一元运算符，在运行时返回值的类型名字符串；这里用于确认 `body.title` 是字符串且 trim 后非空，否则使用 `DEFAULT_CONVERSATION_TITLE`。
- **原理 / 为什么**：前面 `as { title?: unknown }` 只解决编译期访问问题，不能保证运行时类型。`typeof x === "string"` 是 API 层过滤非法输入的常见手段。在同一表达式内，TypeScript 会将 `body.title` **类型收窄**为 `string`，从而允许调用 `.trim()`。
- **易错点 / 坑**：`typeof null === "object"` 是 JS 历史 quirk；条件里 `&& body.title.trim()` 既检查类型又检查非空（空字符串会走默认值）。不要把 `typeof` 当成 TS 专属——它是 JS 运行时运算符。
- **延伸**：
  - 常见模式：`as` 定大致结构 → `typeof` / type guard 真正校验 → 默认值兜底 ✅
  - 数组检查用 `Array.isArray()`，对象用 `typeof x === "object" && x !== null` ✅
  - 🔗 https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/typeof
- **标签**：#javascript #typescript #type-narrowing #validation
- **状态**：#待复习
- **日期**：2026-07-22

### 前后端 JSON 约定与 `request.json()` / `NextResponse.json()`

- **来源问题**：前后端之间传的 JSON 数据格式有规定吗？`request.json()` 是什么意思？`NextResponse.json()` 的作用又是什么？
- **结论**：项目约定了 `ConversationJson`（时间为 ISO 字符串）、成功时直出业务数据、失败时 `{ error: "..." }`；`request.json()` 把请求体 JSON 文本解析为 JS 对象，`NextResponse.json()` 把 JS 对象序列化为 JSON 响应并设置 `Content-Type: application/json`。
- **原理 / 为什么**：JSON 不支持原生 `Date`，故 API 层用 ISO 字符串（`serializeConversation`），前端 store 用 `parseConversationJson` 转回 `Date`。Route Handler 的 `request` 是 Web 标准 `Request` 对象，`request.json()` 读 body（只能读一次）；`NextResponse.json()` 是 Next.js 封装，等价于 `JSON.stringify` + 正确响应头。二者方向相反：前者「收」、后者「发」。
- **易错点 / 坑**：JSON 线上只能是 string/number/boolean/null/object/array；`Date` 必须在边界转换。`request.json()` 非法 JSON 会抛错，故 POST 用 `.catch(() => ({}))`；`response.json()` 同样只能调用一次。
- **延伸**：
  - 各接口形状：`GET` → `ConversationJson[]`；`POST`/`PATCH` → 单个 `ConversationJson`；`DELETE` → `{ ok: true }`；错误 → `{ error }` + HTTP 4xx/5xx ✅
  - OpenSpec `conversation-api/spec.md` 与 `design.md` 规定了 ISO 日期与字段，未用 envelope 包装 ✅
  - 🔗 https://developer.mozilla.org/en-US/docs/Web/API/Request/json
  - 🔗 https://nextjs.org/docs/app/api-reference/functions/next-response#json
- **标签**：#json #api #nextjs #fetch #serialization
- **状态**：#待复习
- **日期**：2026-07-22
