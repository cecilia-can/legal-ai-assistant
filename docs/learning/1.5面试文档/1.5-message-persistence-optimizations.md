## 1. 背景

Change 1.5 的目标是把 1.4 的内存对话写入 PostgreSQL `Message` 表，并在切换会话时从数据库恢复历史。

初版实现完成后，功能链路已通（消息 API CRUD、游标分页、`loadMessages`、方案 B 落库），但用户联调反馈了若干**体验与数据一致性问题**。这些问题不是「没做持久化」，而是**持久化时机、UI 反馈、数据库延迟**三个层面的细节没对齐真实使用场景。

---

## 2. 现象汇总

| # | 用户观察 | 根因（初判） | 严重程度 |
|---|----------|--------------|----------|
| P1 | 刷新后只剩 user 消息，assistant 不见了 | 落库时机绑在打字机队列 `waitUntilIdle()` 之后；用户提前刷新时 assistant 尚未写入 | 高（数据丢失感） |
| P2 | 删除消息要等很久，弹框一直 loading | 远程 Neon 往返延迟 + 确认弹框 `await DELETE` 成功才关闭 | 中（体感慢） |
| P3 | 找不到删除按钮 | 删除图标 `opacity-0 group-hover:opacity-100`，必须 hover 才可见 | 中（可发现性差） |
| P4 | 删除消息没有确认 | 初版直接调 DELETE，缺少与「删会话」一致的 ConfirmDialog | 低（安全/一致性） |
| P5 | abort 后要不要落库？ | 设计阶段默认方案 A（仅 `done` 落库），与主流 Chat 体验不一致 | 设计决策 |
| P6 | 落库/删除普遍偏慢 | 开发环境连亚太 Neon，网络 RTT 远大于 SQL 本身 | 环境层 |

## 3. 完整数据链路（优化后）

```text
用户发送
    ↓
chatStore.sendMessage
    ├─ 内存插入临时 user + assistant 占位
    ├─ POST /api/chat（SSE 流，不写库）
    │     ↓ token 事件
    │     networkAssistantText += text   ← 网络侧完整文本（与 UI 解耦）
    │     displayQueue.enqueue(text)     ← 打字机展示（仅影响 UI）
    ↓
流结束（done）或 abort（有内容）
    ↓
finalizeRound(userContent, networkAssistantText)   ← 不等打字机排空
    ↓
POST /api/conversations/[id]/messages
    body: { messages: [user, assistant] }           ← 单请求批量 + 事务
    ↓
messageService.createMessages（Prisma $transaction）
    ↓
用服务端 id 替换内存临时 id

切换会话 / 刷新
    ↓
GET /api/conversations/[id]/messages?limit=50
    ↓
chatStore.loadMessages → 渲染 MessageList
```

**关键认知：** 网络 token 流、打字机展示队列、数据库落库是**三条独立时间线**。持久化必须跟「网络已收到什么」对齐，不能跟「UI 已展示多少」对齐。

## 4. 数据库层：决策全景与优化详述

> 本章集中回答：**数据存在哪、什么时候写、怎么读、索引怎么建、开发/部署用什么库**——以及每个分叉点上我考虑过什么、为什么没选别的方案。

### 4.1 起点：有表 ≠ 有持久化

Change 1.1 已定义 `Conversation` / `Message` 模型；Change 1.3 会话 CRUD 已在写 `Conversation`；Change 1.4 聊天消息**只进 `chatStore` 内存**，`Message` 表空着。

| 层 | Change 1.4 状态 | 刷新页面后 |
|----|-----------------|------------|
| `Conversation` | DB 真相源 | 侧栏会话仍在 |
| `Message` | 内存真相源（`chatStore`） | **消息全丢** |

**第一个数据库层决策：** 1.5 不新建表，而是**激活已有 `Message` 模型**，让 DB 成为消息的真相源；内存只做流式展示缓冲 + 已加载页缓存。

**为什么不在 1.4 就写库？** Roadmap 刻意拆分：1.4 验证 SSE 链路，1.5 验证持久化编排。先跑通再落库，避免在流 Handler 里同时调试协议和 SQL。

### 4.2 写路径架构：谁负责 INSERT？

这是本 Change **最核心的架构分叉**——决定消息行什么时候、由哪段代码写入 PostgreSQL。

#### 候选方案

| 方案 | 写库位置 | 触发时机 | 我的评价 |
|------|----------|----------|----------|
| **W1** `/api/chat` 内写库 | SSE Route Handler | 每个 token / done 时 | ❌ 否决 |
| **W2** 客户端编排 + 消息 REST API | `chatStore` → `POST .../messages` | done / abort（方案 B）后 | ✅ 采用 |
| **W3** 服务端异步队列（outbox） | Worker 消费事件 | 流结束后投递任务 | ⏸ 本阶段不做 |

#### W1 为什么否决：流式 Handler 不适合承担 CRUD

```
POST /api/chat（长连接 SSE）
    ├─ 可能 abort  midway
    ├─ 可能网络断开、客户端刷新
    ├─ Vercel function 有 duration 上限
    └─ 若在流内 INSERT：
         · done 前写半截 assistant → 刷新看到残缺行
         · abort 后需 DELETE 或标记作废 → 状态机膨胀
         · token 级 UPDATE → 写放大（1 条回复 = 数百次 UPDATE）
```

**思考要点：** SSE 的生命周期是「不确定何时结束的长任务」；SQL INSERT 的生命周期是「短、原子的 CRUD」。把两者绑在同一 Handler，等于用长连接的状态机管理数据库事务边界——复杂度指数上升。

#### W2 为什么采用：职责分离 + 与交付物对齐

```
/api/chat          → 生成（SSE，无 DB）
/api/.../messages  → 持久化（REST，有 DB）
chatStore          → 编排（何时调哪个 API）
messageService     → 唯一 Prisma 入口
```

- Route Handler 只做校验 + envelope，**复杂查询不堆在 route 里**（与 1.3 `conversationService` 一致）。
- 落库失败时，内存仍有消息，可 `set({ error })` 提示重试——不必在流里做补偿事务。
- **Trade-off 我接受的：** 多一次 HTTP 往返；客户端若漏调 POST，会出现「内存有、DB 无」。本阶段用 spec + 单测路径约束，不做 outbox。

#### W3 为什么暂缓

Outbox（流结束后写事件表，Worker 异步落库）能消除客户端漏调，但需要队列基础设施。Phase 1 目标是「能持久、能恢复」，W2 足够；W3 留给多实例 / 多端同步阶段。

### 4.3 落库边界：方案 A / B / C（数据库视角）

「什么时候往 `Message` 表 INSERT」本质是：**一行（或一对）数据库记录何时成为不可变历史**。

| 方案 | 何时 INSERT user | 何时 INSERT assistant | DB 中可能出现的异常态 |
|------|------------------|----------------------|------------------------|
| **A** 仅 `done` | `done` 后 | 同事务，`done` 后 | 无（要么整轮有，要么整轮无） |
| **B** abort 有内容也落 | `done` 或 abort 有内容 | 同左 | 可能有「半截 assistant」行 |
| **C** 发送即写 user | **send 瞬间** | `done` / abort 后补 | **孤儿 user**（assistant 永远没写入） |

#### 我的决策过程

1. **初稿选 A**：实现最简单——「完整一轮 = 一条 user + 一条 assistant」事务边界清晰，DB 里没有半成品。
2. **联调质疑**：「abort 后刷新，已打出的字没了」——这不是 bug，是 A 的设计结果，但与 ChatGPT 等产品行为不一致。
3. **对比 C**：user 发送瞬间就 INSERT，assistant 后续 UPDATE/INSERT。DB 里会长期存在 `assistant` 缺失的会话轮次；删除/重试/并发都要处理「悬空 user」。**为 1.5 的目标（能恢复历史）上 C 过重。**
4. **最终选 B**：INSERT 时机仍是一次性（整轮结束），只是「结束」的定义从「仅 done」扩到「done 或 abort 且已有内容」。**DB 操作形态与 A 相同（仍是一轮一次 batch INSERT），不引入 C 的中间态。**

```sql
-- 方案 B 下，一次 finalizeRound 对应一次事务，典型写入：
BEGIN;
  INSERT INTO "Message" (..., role='user',     content='...') ;
  INSERT INTO "Message" (..., role='assistant', content='...') ;  -- 可能是半截
  UPDATE "Conversation" SET "updatedAt" = now() WHERE id = ...;
COMMIT;

-- abort 且 assistant 为空：上述 INSERT 不发生（内存占位被丢弃）
-- 流开始前失败：上述 INSERT 不发生
```

**留给后续（1.7）：** 半截 assistant 进入 `Message` 表后，拼进 Prompt 时可能需要长度/完整性过滤——这是**读路径**问题，不在 1.5 改 schema。

### 4.4 原子性演进：从「两次 POST」到「批量事务」

OpenSpec 初稿（`design.md` §4）写的是：`sendMessage` 在落库时**调两次 POST**（先 user，再 assistant）。实现并完成联调后，我改成了**一次 POST + 服务端 `$transaction`**。

#### 为什么初稿是两次 POST？

- API 形状简单：每条 `POST` body 只有 `{ role, content }`。
- 与「单条创建」的 REST 直觉一致。
- 设计文档备注：「若实现中发现竞态再改为 batch」——**这句话后来应验了。**

#### 两次 POST 的数据库风险（联调后认识到的）

```
时间线：
  T1  POST user     → INSERT 成功 ✓
  T2  用户刷新页面   → GET 只有 user，assistant「丢了」
  T3  POST assistant → 可能尚未发出 / 失败

或：
  T1  POST user     → 成功
  T2  POST assistant → 500 / 网络失败
  → DB 中永久存在孤儿 user 行
```

这不是理论问题——**P1（刷新只剩 user）的部分复现路径**，就来自「user 先入库、assistant 还没写」的时间窗（叠加了落库时机绑打字机的 bug）。

#### 最终方案：批量 INSERT + 单事务

```typescript
// messageService.createMessages — 同一 $transaction 内
for (const input of normalized) {
  await tx.message.create({ ... });
}
await tx.conversation.update({ data: { updatedAt: new Date() } });
```

| 维度 | 两次 POST | 批量 POST + 事务 |
|------|-----------|------------------|
| 原子性 | ❌ 可能只写 user | ✅ 全有或全无 |
| HTTP 往返 | 2 × RTT | 1 × RTT |
| API 复杂度 | 低 | 略高（支持 `messages[]`） |
| 与 Neon 延迟关系 | 慢 × 2 | 慢 × 1（仍受 RTT 影响） |

**决策总结：** 初稿优先简单 API；联调暴露一致性风险后，**用一次事务换数据正确性**，API 略复杂可接受。

### 4.5 落库时机与 DB 内容一致性（联调 Bug 修复）

此条表面是前端时序，**本质是「写入 DB 的 assistant.content 以什么为准」**。

| 信号来源 | 含义 | 能否作为 INSERT 的 content？ |
|----------|------|------------------------------|
| `displayQueue` 已 reveal 的文本 | 用户屏幕上看到的 | ❌ 滞后于网络，刷新窗口内偏短 |
| `networkAssistantText` | SSE 已收到的完整拼接 | ✅ 与模型输出一致 |
| 流结束后 store 里的 `message.content` | 取决于上面两者谁更新快 | ❌ 初版常偏短 |

**修复前的 DB 现象：**

```text
SSE done @ T0
waitUntilIdle() 需要 T0 ~ T0+8s（打字机）
用户在 T0+1s 刷新
→ finalizeRound 尚未执行
→ DB：无 assistant 行；或有 user 行（若曾走两次 POST 的第一条）
```

**修复后：**

```text
SSE done @ T0
finalizeRound(user, networkAssistantText) @ T0+ε   ← 立即
waitUntilIdle() 仅服务 UI
→ T0+1s 刷新：DB 中 user + assistant 均已 INSERT
```

**数据库层结论：** INSERT 的 payload 必须来自**网络层累积的完整文本**，不能来自 UI 层。否则「DB 真相源」与「模型实际输出」不一致——这比「DB 比屏幕多几个字」更严重。

### 4.6 读路径：游标分页 + Keyset 查询

#### 聊天场景下的读需求

- **首屏：** 进入会话，看到**最近** N 条（默认 50），时间升序（旧→新）。
- **向上翻：** 加载**更早**的消息，不能漏、不能重。
- **不需要：** 跳到「第 17 页」——那是管理后台模式。

#### 为什么不用 OFFSET？

```sql
-- OFFSET 深分页（会话 1 万条消息时）
SELECT * FROM "Message"
WHERE "conversationId" = $1
ORDER BY "createdAt" ASC
OFFSET 9800 LIMIT 50;
-- Postgres 仍需扫描/跳过前 9800 行 → 越翻越慢
```

聊天「向上无限加载」是典型的深分页场景，OFFSET 成本线性增长。

#### 为什么用 Keyset（游标）？

游标 = 上一页**最早一条**的 `(createdAt, id)`，编码为 base64url JSON：

```typescript
// encodeMessageCursor({ createdAt, id })
// decode → keyset 条件
WHERE conversationId = $1
  AND (
    createdAt < $cursorDate
    OR (createdAt = $cursorDate AND id < $cursorId)
  )
ORDER BY createdAt DESC, id DESC
LIMIT 51   -- 多取 1 条判断 hasMore
```

**为什么 tie-breaker 用 `id`？** 同一毫秒可能 INSERT 多条（batch 事务里 user 和 assistant），仅 `createdAt` 无法全序；`id`（cuid）保证稳定排序。

**首屏实现技巧：** 先 `ORDER BY createdAt DESC LIMIT 51`，再 **reverse** 成升序返回——这样 API 对外始终是「时间线从旧到新」，前端直接渲染。

| 方案 | 适合场景 | 本项目的决定 |
|------|----------|--------------|
| OFFSET | 随机页码、总量小 | ❌ |
| Keyset / Cursor | 时间线 infinite scroll | ✅ |
| 全量加载 | 消息极少 | ❌ 不可扩展 |

### 4.7 索引设计：`(conversationId, createdAt)`

#### Schema 变更

```prisma
model Message {
  // ...
  @@index([conversationId, createdAt])
}
```

Migration：`20260727051317_message_conversation_created_at_index` — **只加索引，不改列、不 reset 数据**。

#### 为什么需要这个索引？

无索引时，列表查询典型路径：

```text
Filter conversationId → Seq Scan 该会话所有行 → Sort by createdAt → Limit
```

会话消息变长后，每次进入会话、每次向上翻页都扫全表——**读放大**。

#### 为什么复合索引，而不是两个单列索引？

| 索引 | 能否高效服务 `WHERE conversationId = ? ORDER BY createdAt` |
|------|-------------------------------------------------------------|
| `(conversationId)` | 能过滤，排序可能仍需额外 sort |
| `(createdAt)` | ❌ 无法先过滤会话 |
| **`(conversationId, createdAt)`** | ✅ 过滤 + 范围扫描 + 顺序读 |

PostgreSQL **最左前缀**：以 `conversationId` 打头，正好匹配「某会话内按时间查」——这是 Message 表 **100% 的主查询模式**。

#### 我刻意没做的（及原因）

| 备选 | 未采用原因 |
|------|------------|
| `(conversationId, createdAt DESC)` 专用索引 | Prisma 升序/降序查询都能用 ASC 索引反向扫描；一条索引够用 |
| 覆盖索引 `(conversationId, createdAt) INCLUDE (content)` | 1.5 消息量小， premature optimization |
| 全文搜索 GIN 索引 | 非目标（spec 明确不做 search） |

#### 与分页的配合

Keyset 条件 `createdAt < ? OR (createdAt = ? AND id < ?)` 在 `(conversationId, createdAt)` 上可走 **Index Range Scan**；`id` tie-break 在索引第二列相同时由 heap 过滤——batch 写入同一毫秒仅 2 行，成本可忽略。

### 4.8 删除语义与级联

| 操作 | DB 行为 | 决策理由 |
|------|---------|----------|
| 删单条消息 | `DELETE FROM Message WHERE id = ?` 硬删除 | 1.5 非目标：软删除、审计 |
| 删会话 | `Conversation` DELETE → Message **ON DELETE CASCADE** | 1.1 已定义，1.5 不逐条删消息 |
| 删消息是否更新 `Conversation.updatedAt` | **否**（当前实现） | 会话「活跃排序」以新消息创建为准；删旧消息不改变「最后聊天时间」语义 |

**为什么不做软删除？** 需要 `deletedAt` 列、所有 SELECT 加 `WHERE deletedAt IS NULL`、UI 要处理「已删除仍占位」。1.5 目标是 CRUD 闭环，硬删除 + 确认弹框足够。

**级联的价值：** 删会话时 O(1) 次 API，DB 自动清理子行——不必 `DELETE FROM Message WHERE conversationId IN (...)` 批量脚本。

### 4.9 开发库 vs 部署库：Neon 与 Docker 本地 Postgres

#### 现象驱动的第二次环境决策

联调 P2/P6：DELETE / POST 体感**数秒**。我第一反应是「接口是不是写错了」——查日志后发现 **SQL 本身 30–60ms 级**，Neon 亚太 RTT + Serverless 冷连接才是主因。

#### 候选环境对比（结合 Roadmap）

| 方案 | 适用阶段 | pgvector（Phase 2） | 延迟 | 我的结论 |
|------|----------|---------------------|------|----------|
| **仅 Neon** | 开发 + 部署 | Neon 支持 | 开发慢 | 初版如此 |
| **Docker 本地 + Neon 部署** | 开发本地 / 部署云端 | 镜像预装 | 开发快 | ✅ 采用 |
| 本地裸 Postgres | 开发 | 需手动装扩展 | 快 | 不如 Docker 可复现 |
| 全面 Docker 自托管 | 部署 | 可控 | 运维成本高 | 留给 `deployment.md` 上线评估 |

#### 为什么选 `pgvector/pgvector:pg17` 镜像？

Roadmap Phase 2 Change 2.1 明确要 **pgvector 向量检索**。若 1.5 用普通 Postgres 镜像，2.1 还要换环境、补扩展——**现在一次选对，迁移风险前置消化**。

Neon 生产同样支持 pgvector → **扩展层面 dev/prod 对齐**；差异只在连接串和网络距离。

#### 切换成本（我评估为「低」）

```text
开发：DATABASE_URL=postgresql://postgres:postgres@localhost:5432/legal_ai_assistant
部署：DATABASE_URL=postgresql://...@neon.tech/...?sslmode=require

Schema 同步：git 中的 prisma/migrations/
  开发：npx prisma migrate dev
  部署：npx prisma migrate deploy
```

**代码零改动**——Prisma `provider = "postgresql"` 是通用的。这是我能接受「开发/部署双库」的前提。

#### 实测延迟分解（本地 warm）

| 操作 | API 总耗时 | DB（application-code） | 结论 |
|------|------------|-------------------------|------|
| POST 批量 2 条 | ~70ms | ~61ms | INSERT×2 + UPDATE conversation |
| GET 列表 | ~42ms | ~30ms | 索引 range scan |
| DELETE 1 条 | ~48ms | ~36ms | 主键删除 |

Neon 联调：同样 SQL，**+数百 ms～数秒 RTT**。优化 SQL 无法解决地理距离——**换本地库是环境决策，不是查询优化**。

#### 我接受的代价

1. **数据隔离：** 切本地库后，Neon 上的旧会话看不到——两套独立 DB，不是 bug。
2. **Docker 依赖：** 需 Docker Desktop 运行；团队 onboarding 多一步 `npm run db:up`。
3. **首次 dev 路由编译 ~5s：** 与 DB 无关，易误判为「数据库慢」。

### 4.10 数据库相关决策演进时间线

```text
1.5 设计阶段
```

## 5. 优化项一：abort 落库策略（方案 A → 方案 B）

> 数据库层视角（INSERT 边界、与方案 C 对比）见 **§4.3**。

### 5.1 现象

设计初稿采用**方案 A**：只有收到 SSE `done` 才落库；abort 一律丢弃本轮 assistant。

用户质疑：「为什么 abort 不落库？误切换会话时，已经打出来的半截回复就丢了。」

### 5.2 方案对比

| 方案 | 落库边界 | 优点 | 缺点 | 实现复杂度 |
|------|----------|------|------|------------|
| **A** 仅 `done` | 完整一轮 | 历史干净；状态机简单 | abort / 误切换丢已生成内容 | 低 |
| **B** `done` 或 abort 有内容 | 有可见 assistant 文本 | 贴近 ChatGPT 等产品；防误丢 | 历史可能含「未完成」轮次 | 中低 |
| **C** 发送即写 user | user 最早稳定 | user 永不丢；利于「重新生成」 | 可能产生孤儿 user；状态机最重 | 中高 |

### 5.3 决策与落地

**选定方案 B**（OpenSpec `design.md` / `chat-state` spec 已同步）：

- `done` 且 assistant 非空 → 落库 user + assistant  
- abort 且 assistant 非空 → 落库 user + **半截** assistant  
- abort 时 assistant 仍为空 / 流开始前失败 → **不落库**

### 5.4 效果

- 用户取消生成或切换会话时，已打出内容刷新后仍在  
- 比方案 C 简单，不必维护「user 已入库、assistant 待补全」的中间态  
- 对 Change 1.7 上下文管理：半截回复进入历史需在 Prompt 阶段再过滤（已留延伸项）

## 6. 优化项二：落库时机（打字机队列 vs 网络完整文本）

> 数据库层视角（INSERT 的 content 以谁为准）见 **§4.5**。

### 6.1 现象（P1）

联调反馈：「落库的难道只有用户的消息吗？AI 助手回复刷新后还在吗？」

复现路径：SSE 流结束后，用户在打字机动画**尚未播完**时刷新页面 → 数据库里只有 user，assistant 缺失。

### 6.2 根因

初版 `sendMessage` 逻辑：

```text
displayQueue.markNetworkDone()
await displayQueue.waitUntilIdle()   // ← 阻塞在这里
await finalizeRound(...)             // ← 落库太晚
```

`finalizeRound` 若从 store 内存读 assistant content，读到的只是**打字机已 reveal 的部分**，不是网络侧完整文本。

这与 Change 1.4 展示队列的设计目标一致（队列管 UX），但 1.5 误把「展示完成」当成了「可以落库」的信号。

### 6.3 方案对比

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **等打字机排空再落库** | `waitUntilIdle()` 后写库 | 库中内容与用户最终看到的一致 | 刷新窗口内丢 assistant；与网络不同步 |
| **网络结束立即落库** | 维护 `networkAssistantText`，done/abort 后立刻 `finalizeRound` | 刷新安全；落库内容与模型输出一致 | 库中可能比当前 UI 多（用户还没看完）——可接受 |
| **边流边写 assistant** | 每个 token PATCH 数据库 | 实时持久 | 写放大、部分失败难回滚；本 Change 明确不做 |

### 6.4 落地改动

`lib/stores/chatStore.ts`：

1. SSE `token` 事件：`networkAssistantText += event.text`（与 `displayQueue.enqueue` 并行）  
2. 流结束 / abort：`await finalizeRound(..., trimmed, networkAssistantText)` — **不** `await waitUntilIdle()`  
3. 打字机：`waitUntilIdle()` 仅用于 UI 收尾，与落库解耦  
4. abort 路径：`displayQueue.flushSync()` 后再 `finalizeRound`，保证 UI 与网络文本一致

### 6.5 效果

- 流结束后任意时刻刷新，user + assistant 均能从 DB 恢复  
- 落库延迟从「打字机时长（可能数秒～数十秒）」降到「一次 POST 往返（本地 ~70ms）」

## 7. 优化项三：批量事务落库（防「只写入 user」）

> 数据库层完整决策见 **§4.4**；本节保留联调视角摘要。

### 7.1 现象

即使修正落库时机，若 user 与 assistant **分两次 POST**，中间失败仍可能出现「只有 user、没有 assistant」。

### 7.2 方案对比

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| 两次 POST | 先 user 再 assistant | API 简单 | 非原子；中间失败产生脏数据 |
| **一次 POST + 服务端事务** | `{ messages: [user, assistant] }` + `$transaction` | 原子；一次往返 | POST body 略复杂 |
| `/api/chat` 内写库 | 流 Handler 直接 insert | 服务端统一 | 与 SSE 耦合；半写入回滚难 |

### 7.3 落地改动

- `messageService.createMessages`：`prisma.$transaction` 内顺序 insert user、assistant，并更新 `Conversation.updatedAt`  
- `postPersistedRound`：单请求 POST `{ messages: [...] }`  
- 成功后用服务端返回的 id **替换**内存临时 cuid

### 7.4 效果

- 一轮对话要么完整入库，要么都不入库（事务失败则 UI 保留临时 id + 错误提示）  
- 减少一次 HTTP 往返

## 8. 优化项四：删除体验（乐观更新 + 弹框）

### 8.1 现象（P2、P4）

- 点删除后消息消失，但确认弹框仍转圈数秒  
- 初版无删除确认，与删会话交互不一致  

### 8.2 方案对比

| 维度 | 悲观更新（等 API 再改 UI） | **乐观更新（先改 UI 再调 API）** |
|------|---------------------------|----------------------------------|
| 体感延迟 | 完全暴露网络 RTT | 即时反馈 |
| 失败处理 | 简单 | 需回滚 + 错误提示 |
| 适用场景 | 强一致、不可撤销操作 | 可回滚的 CRUD（本项目的硬删除） |

弹框关闭时机：

| 方案 | 行为 | 体感 |
|------|------|------|
| 等 DELETE 成功再关 | `await deleteMessage()` 后 `setPendingDeleteMessage(null)` | 弹框长时间 loading |
| **确认后立即关** | 先关弹框，后台 `deleteMessage`；列表已乐观移除 | 与 ChatGPT 类产品一致 |

### 8.3 落地改动

`chatStore.deleteMessage`：

1. 快照 `previous` 与 `targetIndex`  
2. 立刻从 `messagesByConversation` 移除目标消息  
3. `DELETE` 失败 → 按原 index `splice` 回滚 + `set({ error })`

`app/page.tsx`：

- 新增 `ConfirmDialog`（与删会话同款）  
- `handleConfirmDeleteMessage`：先 `setPendingDeleteMessage(null)`，再 `await deleteMessage`

### 8.4 效果

- 删除体感从「数秒」变为「即时」（列表立即更新）  
- Neon 环境下弹框不再长时间转圈  
- DELETE 失败时消息回滚，用户可见错误文案

## 10. 优化项六：本地 Postgres 开发环境

> 数据库层完整决策见 **§4.9**；本节保留联调视角摘要。

### 10.1 现象（P6）

连 Neon 时，落库/删除/加载历史的 API 往返可达**数秒**；SQL 本身很轻，瓶颈在跨区网络 RTT。

### 10.2 方案对比

| 环境 | 延迟（实测量级） | 优点 | 缺点 |
|------|------------------|------|------|
| **Neon 远程** | 数百 ms～数秒 | 零运维；与生产一致 | 开发体感慢；依赖网络 |
| **Docker 本地 Postgres** | DB 30–65ms；API 40–120ms（warm） | 开发快；可离线 | 需 Docker；数据与云端分离 |
| 本地裸装 Postgres | 类似 Docker | 无容器开销 | 无 pgvector 时需额外装扩展 |

### 10.3 决策

**开发用本地 Docker（pgvector 镜像），部署仍用 Neon。**

理由：

- 只改 `DATABASE_URL`，代码与 Prisma schema 不变  
- `pgvector/pgvector:pg17` 镜像预装扩展，Phase 2 向量检索无需换环境  
- 迁移文件走 git，`migrate deploy` 同步到 Neon  

### 10.4 落地内容

- `docker-compose.yml`：`legal-ai-postgres`，5432 端口，数据卷持久化  
- `package.json`：`db:up` / `db:down` / `db:reset`  
- `.env.example`：本地与 Neon 两种 `DATABASE_URL` 示例  

### 10.5 实测效果（warm 路由，本地库）

| 操作 | API 总耗时 | 其中 DB（application-code） |
|------|------------|------------------------------|
| POST 批量 2 条消息 | ~70ms | ~61ms |
| GET 消息列表 | ~42ms | ~30ms |
| DELETE 单条消息 | ~48ms | ~36ms |

对比 Neon 联调时「删一条等数秒」，改善来自**网络 RTT 消除**，不是 SQL 优化。

**注意：**

- 切本地库后，Neon 上的旧会话不会自动出现（两套独立数据）  
- dev 模式**首次**访问某 API 路由可能慢 ~5s（Next.js 编译），与数据库无关

## 13. 面试追问与解答话术

> 使用方式：结论 → 原理 → 结合项目 → trade-off，每题 1～3 分钟。  
> **数据库专项**见 Q1–Q4、Q7–Q8、Q11–Q15。

---

### Q1：你们的聊天消息是怎么持久化的？为什么不让 `/api/chat` 直接写库？

**解答思路：**

1. **结论**：SSE 聊天接口只负责推 token；落库由 `chatStore` 在流结束后调 `POST .../messages`，服务端 `messageService` 写 PostgreSQL。  
2. **原理**：生成（流式、长连接、可能 abort）与 CRUD（短请求、事务）职责分离；避免在流 Handler 里处理半写入、回滚、重试。  
3. **结合项目**：`finalizeRound` → `postPersistedRound` → `createMessages` 事务写入 user + assistant。  
4. **Trade-off**：多一次 HTTP 往返，但边界清晰，符合 roadmap 独立 messages API 的交付物。

**加分项：** 提到 `/api/chat` 不写库 ≠ 消息不进数据库，是客户端编排时机问题；能说出 W1/W2/W3 三个写路径候选。

**减分项：** 说「流式接口里顺便 insert 就行」却提不出 abort/失败怎么处理。

---

### Q11：Message 表 1.1 就有了，为什么 1.5 才写？这算技术债吗？

**解答思路：**

1. **结论**：是 roadmap 刻意拆分，不是遗漏——1.4 验证 SSE，1.5 验证 DB 编排。  
2. **原理**：有 Prisma model ≠ 业务写库；`Conversation` 1.3 已在用 DB，`Message` 1.4 仍走内存。  
3. **结合项目**：1.5 激活已有表 + 索引 + messageService，无破坏性 schema 变更。  
4. **Trade-off**：1.4 刷新丢消息是已知限制；若合并 Change 会把流式调试和 SQL 调试耦合。

**加分项：** 区分「表存在」与「真相源在 DB」。

---

### Q12：复合索引 `(conversationId, createdAt)` 是怎么想出来的？单列不够吗？

**解答思路：**

1. **结论**：Message 表主查询是「某会话内按时间取 N 条」；复合索引同时服务过滤和排序。  
2. **原理**：最左前缀——`(conversationId)` 打头才能高效 `WHERE conversationId = ? ORDER BY createdAt`；单独 `(createdAt)` 无法先过滤会话。  
3. **结合项目**：配合 keyset 分页；migration 只加索引不 reset；batch 写入时 `id` 作 tie-breaker。  
4. **Trade-off**：写入多一条索引维护；聊天读多写少，值得。

**加分项：** 能画 Index Range Scan vs Seq Scan + Sort。

**减分项：** 说「加索引总是越快越好」却不提写入成本。

---

### Q13：游标分页的 cursor 为什么用 `createdAt + id` 编码，而不是 OFFSET？

**解答思路：**

1. **结论**：聊天向上翻历史是深分页；keyset 用上一页边界定位，成本稳定；OFFSET 要跳过 increasingly 多的行。  
2. **原理**：cursor 是 opaque token（base64url JSON），不是页码；同一毫秒 batch INSERT 两条需 `id` 打破平局。  
3. **结合项目**：首屏 `DESC LIMIT 51` 再 reverse 成升序；`nextCursor` 指向本页最早一条。  
4. **Trade-off**：不能随机跳页；聊天不需要。

**加分项：** 区分「消息分页」与「侧栏会话列表」。

---

### Q14：两次 POST 和批量事务，你是什么时候决定改的？

**解答思路：**

1. **结论**：设计初稿两次 POST（简单 REST）；联调发现孤儿 user 风险后改为 `{ messages: [...] }` + `$transaction`。  
2. **原理**：两次 HTTP 非原子——第一次成功、第二次失败 = 脏数据；事务保证 INSERT user + INSERT assistant + UPDATE conversation 同生共死。  
3. **结合项目**：OpenSpec design 写了「若发现竞态再改 batch」——实现后果然改了。  
4. **Trade-off**：API 略复杂，换一致性和少一次 RTT。

**加分项：** 诚实说「先简单后修正」比假装一开始就用事务更可信。

---

### Q15：开发用本地库、部署用 Neon，数据不一致怎么办？迁移怎么做？

**解答思路：**

1. **结论**：**Schema** 用 git migrations 同步（`migrate dev` / `migrate deploy`）；**数据** 开发/生产 intentionally 隔离，不自动同步。  
2. **原理**：只改 `DATABASE_URL`；选 pgvector 镜像是为 Phase 2 扩展对齐，不是为 1.5 性能 alone。  
3. **结合项目**：`docker-compose.yml` + `npm run db:up`；Neon 旧数据切回注释行即可见。  
4. **Trade-off**：本地看不到云端历史是预期；换环境要清楚连哪套库。

**加分项：** 区分 schema migration vs data migration；提到 Neon pooler / 冷连接。

---

### Q16：`createMessages` 里为什么要 UPDATE `Conversation.updatedAt`？

**解答思路：**

1. **结论**：新消息代表会话活跃，侧栏应按最近聊天时间排序。  
2. **原理**：`Message` INSERT 不会自动触发父行 `@updatedAt`（Prisma 只在 Conversation 自身 update 时变）；需显式 `conversation.update`。  
3. **结合项目**：与 `createMessages` 同事务，避免「有消息但会话排序不刷新」。  
4. **Trade-off**：删消息时不 update——删除不改变「最后聊天」语义。

---

### Q2：刷新后 assistant 消息丢了，你会怎么排查？

**解答思路：**

1. **结论**：先区分「没落库」还是「落库了但没加载」——看 Network 里流结束后有没有 POST messages，刷新后 GET messages 返回什么。  
2. **原理**：常见 bug 是把落库绑在 UI 展示完成（打字机队列）而不是网络流完成；内存里的 content 可能少于 `networkAssistantText`。  
3. **结合项目**：初版 `await displayQueue.waitUntilIdle()` 后才 `finalizeRound`，用户提前刷新就只剩 user。修复是维护 `networkAssistantText`，done/abort 后立即落库。  
4. **Trade-off**：库中内容可能略领先于当前 UI（用户还没看完），但刷新安全更重要。

**加分项：** 画三条时间线：网络 / 展示 / 落库。

---

### Q3：abort 时到底要不要保存 assistant？你们怎么选的？

**解答思路：**

1. **结论**：方案 B——abort 时若 assistant 已有非空内容，与 user 一起落库；空占位则不落库。  
2. **原理**：方案 A 历史干净但误操作丢内容；方案 C user 最早入库但状态机重。B 在复杂度与体验间平衡。  
3. **结合项目**：OpenSpec 明确；`finalizeRound` 对 `assistantContent.trim()` 为空直接移除占位不写库。  
4. **Trade-off**：历史可能出现「说到一半」的条目，1.7 上下文阶段可再过滤。

**加分项：** 对比 ChatGPT「Stop generating」仍保留 partial。

---

### Q4：user 和 assistant 为什么用一次 POST 批量写，而不是两次？

**解答思路：**

1. **结论**：一次 POST + Prisma `$transaction`，保证原子性，避免只写入 user。  
2. **原理**：两次请求中间网络/服务失败会产生孤儿 user；事务要么全成功要么全失败。  
3. **结合项目**：`postPersistedRound` body 为 `{ messages: [user, assistant] }`；成功后替换临时 id。  
4. **Trade-off**：API 略复杂，但数据一致性更好，还少一次 RTT。

---

### Q5：删除消息为什么快了很多？你们做了什么优化？

**解答思路：**

1. **结论**：两层——**乐观更新**（先移 UI 再等 API）+ **本地数据库**（消除 Neon RTT）。  
2. **原理**：悲观更新把完整 RTT 暴露给用户；远程 DB 的延迟主要在跨网而非 SQL。  
3. **结合项目**：`deleteMessage` 先 filter 再 DELETE，失败 splice 回滚；确认弹框确认后立即关闭。  
4. **Trade-off**：乐观更新失败需回滚和错误提示；本地与 Neon 数据不共享，开发时注意 `.env` 切换。

**加分项：** 区分「产品层乐观 UI」与「基础设施层本地库」两个独立优化。

---

### Q6：乐观删除失败了怎么办？会不会和数据不一致？

**解答思路：**

1. **结论**：DELETE 失败时按原 index 把消息插回列表，并 `set({ error })` 提示用户。  
2. **原理**：乐观 UI 的前提是**可回滚**；删除是幂等操作，重试安全。  
3. **结合项目**：删除前快照 `target` 与 `targetIndex`；`deletingMessageId` 防并发重复删。  
4. **Trade-off**：极短窗口内 UI 与 DB 不一致（已消失但未删成功），失败即恢复。

---

### Q7：消息列表为什么用游标分页而不是 offset？索引怎么设计的？

**解答思路：**

1. **结论**：游标（`createdAt + id`）做 keyset 分页，首屏取最近 N 条升序展示；`(conversationId, createdAt)` 复合索引加速查询。  
2. **原理**：深分页 `OFFSET` 越扫越慢且插入时易错位；游标是位置令牌，适合「向上加载更早消息」。  
3. **结合项目**：`messageService.listMessages` + Prisma `@@index([conversationId, createdAt])`。  
4. **Trade-off**：不能跳到任意第 N 页；聊天场景不需要。

**加分项：** 区分「消息分页」与「侧栏会话列表」。

---

### Q8：本地库和 Neon 部署怎么切换？迁移麻烦吗？

**解答思路：**

1. **结论**：只改 `DATABASE_URL`；schema 用同一套 Prisma migrations。  
2. **原理**：开发 `migrate dev` 生成迁移；部署 `migrate deploy` 应用到 Neon。  
3. **结合项目**：`docker-compose.yml` + `npm run db:up`；`.env.example` 文档化两种连接串。  
4. **Trade-off**：数据不自动同步；本地 pgvector 镜像与 Neon 扩展应对齐，避免 Phase 2 迁移踩坑。

---

### Q9：打字机展示队列和持久化会不会冲突？

**解答思路：**

1. **结论**：不冲突——队列只管 UI 节奏；持久化跟 `networkAssistantText` 走。  
2. **原理**：1.4 已明确 token、SSE 帧、read chunk、React 帧无 1:1 关系；1.5 不能把「展示完成」当「数据就绪」。  
3. **结合项目**：done 后先 `finalizeRound`，再 `waitUntilIdle()` 做 UI 收尾；abort 先 `flushSync` 再落库。  
4. **Trade-off**：库可能比当前屏幕多几个字，用户刷新后看到完整回复——正确行为。

---

### Q10：如果让你再做一版，还有什么会改进的？

**解答思路（诚实加分）：**

1. 落库失败时在 UI 标记「未保存」并提供重试，而不是仅 toast error。  
2. 长会话配合虚拟列表（1.8）与向上分页加载。  
3. 删消息可考虑软删除 + 审计（当前是硬删除 + cascade）。  
4. 生产环境可选「写库走服务端 BFF 编排」减少客户端漏调 POST 的风险（当前接受客户端编排换实现简单）。
