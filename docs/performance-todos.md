# 性能与上下文管理 TODO

本文记录法律 AI 助手后续可实施的性能与上下文管理事项。优先处理会影响长会话首 Token 延迟、模型输入成本和回答连续性的项目；不在本轮直接实施。

## 1. 会话历史压缩摘要（后续阶段）

**状态：** 计划中，暂不实施。

当早期历史消息占用过多输入预算时，将最早的完整对话轮次压缩为一段可持久化、可追溯的会话摘要；后续请求只携带固定 System Prompt、摘要、最近原始消息和本次问题。

- [ ] 新建 `ConversationMemory`（或等价）数据模型，保存摘要正文、摘要 Token 数、已覆盖到的消息游标和更新时间。
- [ ] 设定摘要触发阈值，例如早期历史超过输入预算的 40%～60%，或未摘要消息达到 10～20 轮。
- [ ] 按完整的 `user + assistant` 对话轮次选择待摘要范围，避免留下缺失提问的孤立 assistant 回答。
- [ ] 使用固定结构生成摘要：当事人、时间线、合同/证据、已讨论结论、不确定事实、待解决问题。
- [ ] 在摘要提示中要求保留日期、金额、主体、条款号、证据名称和不确定性；不得补充对话中不存在的事实。
- [ ] 将摘要作为“历史背景数据”加入模型上下文，不允许摘要内的旧用户指令覆盖 System Prompt。
- [ ] 支持增量更新：`已有摘要 + 新增旧轮次 -> 新摘要`，避免反复总结全部历史。
- [ ] 删除或修改摘要覆盖范围内的消息时，使摘要失效；下一次按需重新生成。
- [ ] 对法律文档原文保留来源标识和可回溯原文；摘要只压缩会话状态，不替代合同条款、法条和证据原文。

**验收标准：** 长会话中，模型上下文由“摘要 + 最近完整轮次”组成；摘要不包含臆造事实；删除被摘要消息后不会继续使用过期摘要。

## 2. Token 计算改为单遍处理

**优先级：** 高。

当前聊天请求会分别计算统计信息和模型消息，并且裁剪时反复对剩余历史分词。应将二者合并为一次计算。

- [ ] 设计 `prepareModelContext`，一次返回 `modelMessages`、完整输入 Token、裁剪后输入 Token 和节省量。
- [ ] 每条消息只执行一次 tokenizer 编码，并缓存本次请求中的消息 Token 成本。
- [ ] 从后向前累计可保留消息，替代“每删除一条就重算全部剩余消息”的循环。
- [ ] 保证 System Prompt、本次最新 user 问题和消息结构开销均参与预算。
- [ ] 为超长单条消息制定明确策略：拒绝、Token 边界截断，或进入文档处理流程。
- [ ] 为完整对话轮次、孤立 assistant 消息、超长最新问题和空历史添加单元测试。

**验收标准：** 同一请求不重复分词同一文本；裁剪后上下文不超过输入预算，或明确返回“单条输入过长”的错误。

## 3. 限制 AI 上下文的数据库读取范围

**优先级：** 高。

当前生成前会读取该会话的全部消息，再在应用层裁剪。应按最新消息倒序分批读取，到达 Token 预算后停止。

- [ ] 查询从最新消息开始分页读取，按 `createdAt + id` 保持稳定排序。
- [ ] 每读取一批即累计 Token；预算满足后停止继续读取。
- [ ] 最终恢复为正序消息，再交给模型。
- [ ] 在实际数据查询中加入会话归属条件，减少独立的所有权校验查询。
- [ ] 评估后续在 `Message` 中持久化 `tokenCount`，避免跨请求重复计算。

**验收标准：** 超长会话不再把全部历史传输到应用层；最终模型输入保持最近上下文优先。

## 4. 统一“输出预留”和模型输出上限

**优先级：** 高。

`CHAT_MAX_OUTPUT_TOKENS` 当前只用于本地输入预算预留，尚未作为上游模型的实际生成上限。

- [ ] 在 Chat Completions 请求中传入 `max_tokens: getMaxOutputTokens()`。
- [ ] 根据当前模型能力验证环境变量上限，避免配置超过模型限制。
- [ ] 识别流式响应最终的 `finish_reason === "length"`。
- [ ] 前端显示“回答因长度限制截断”，并提供继续生成入口。
- [ ] 将实际输出 Token 纳入每日使用额度或明确区分输入/输出配额。

**验收标准：** 本地预算和上游输出上限一致；用户能够识别回答是自然结束还是长度截断。

## 5. 消除首屏会话与消息加载瀑布

**优先级：** 中。

当前客户端先加载会话列表，得到活动会话 ID 后再加载消息。可通过 bootstrap 接口或服务端预取减少串行等待。

- [ ] 记录首页从导航开始到初始消息可见的 p50 / p95。
- [ ] 评估单个 bootstrap 接口：一次返回会话列表与默认会话的最近消息。
- [ ] 或将页面拆为 Server Component 与交互式 `ChatClient`，服务端注入初始状态。
- [ ] 使用 Suspense，避免数据读取阻塞整个页面外壳。

**验收标准：** 初始消息可见时间可量化，并在生产网络条件下得到改善。

## 6. 减少数据库操作的往返次数

**优先级：** 中。

- [ ] 将“先查归属、再更新/删除”改为带归属条件的单次 `updateMany` / `deleteMany`，通过受影响行数判断结果。
- [ ] 将一轮 user + assistant 消息的顺序写入改为批量写入或更少 SQL 语句的事务。
- [ ] 确认生产环境使用 Neon pooler，并为连接池设定符合部署规模的上限。

**验收标准：** 常见消息读写路径的数据库查询数下降，并通过延迟脚本记录前后差异。

当前已完成消息分页加载和顶部 prepend 的滚动位置保持；但消息仍会全量渲染，虚拟列表尚未接入。

- [ ] 完成 `message-virtualization` Change 中的虚拟渲染、动态高度测量和 overscan。
- [ ] 保持 Markdown、代码块、流式增长和 prepend 时的滚动锚点稳定。
- [ ] 将正在流式生成的内容从完整消息数组更新中分离或批量合并，减少长列表复制。
- [ ] 在 100、200、500 条消息及移动端条件下测量滚动帧率和 Long Task。

**验收标准：** 长会话只挂载可视区域附近的消息项，流式输出不会造成明显掉帧。
