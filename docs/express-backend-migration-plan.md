# Express 后端迁移方案

## 1. 背景与目标

当前项目使用 Next.js App Router，同时通过 `app/api/**/route.ts` 提供后端接口。数据库为 PostgreSQL，使用 Prisma 作为数据访问层；认证使用 Auth.js（NextAuth）；聊天接口通过 SSE 返回 AI 流式响应。

本次迁移的目标是将业务 API 从 Next.js API Route 逐步迁移到独立的 Express 服务，同时满足以下要求：

- Next.js 继续负责页面和前端资源。
- PostgreSQL、Prisma Schema 和数据库迁移历史保持不变。
- 保持现有 API 路径、请求参数、状态码和响应结构兼容。
- 保持聊天 SSE 的 `token`、`error`、`done` 事件协议兼容。
- 迁移期间新旧实现可并行验证，并且可以快速回退。
- 为后续 Redis 限流、服务监控、独立扩容和容器化部署提供清晰边界。

Express 本身不是性能问题的直接解决方案。高并发能力仍取决于数据库连接池、AI 上游配额、流式连接数、限流策略、部署实例数和基础设施配置。

## 2. 非目标

第一阶段不包含以下工作：

- 更换 PostgreSQL。
- 更换 Prisma 或重写 ORM。
- 修改现有数据库表结构。
- 重写前端页面和状态管理。
- 一次性替换全部认证实现。
- 在迁移尚未验证前删除 Next.js API Route。
- 将项目立即拆分成多个仓库。

## 3. 当前后端范围

现有后端入口包括：

| 模块 | 当前入口 | 主要职责 |
| --- | --- | --- |
| 认证 | `app/api/auth/[...nextauth]/route.ts` | Auth.js 登录、Session 和 OAuth 回调 |
| 聊天 | `app/api/chat/route.ts` | 加载历史、限流、调用 AI、输出 SSE |
| 会话集合 | `app/api/conversations/route.ts` | 查询和创建会话 |
| 单个会话 | `app/api/conversations/[id]/route.ts` | 修改标题、删除会话 |
| 消息集合 | `app/api/conversations/[id]/messages/route.ts` | 查询和保存消息 |
| 单条消息 | `app/api/conversations/[id]/messages/[messageId]/route.ts` | 删除消息 |

可继续复用的主要模块包括：

- `prisma/schema.prisma` 和 `prisma/migrations/`
- `lib/db.ts`
- `lib/services/messageService.ts`
- `lib/ai/` 下的模型调用、上下文、限流和 token 计算逻辑
- `lib/api/` 下与框架无关的序列化和 SSE 协议逻辑

需要逐步解除的耦合包括：

- `NextResponse` 和 Next.js Route Handler 类型
- `auth()` 与 Next.js 请求上下文
- 登录注册 Server Actions
- Auth.js OAuth 回调路由
- 进程内存限流

## 4. 目标架构

```text
浏览器
   │
   ├── 页面与静态资源 ───────────────▶ Next.js Web
   │
   └── /api 请求 ─────▶ 同源代理 ───▶ Express API
                                           │
                              ┌────────────┼────────────┐
                              ▼            ▼            ▼
                           Service       Prisma       AI Client
                                            │
                                            ▼
                                        PostgreSQL
```

建议迁移初期仍使用单仓库，增加 `server/` 目录：

```text
server/
├── app.ts
├── index.ts
├── config/
├── middleware/
│   ├── auth.ts
│   ├── error-handler.ts
│   ├── request-id.ts
│   └── rate-limit.ts
└── routes/
    ├── conversations.ts
    ├── messages.ts
    └── chat.ts
```

业务逻辑保留在 `lib/services/`，不得依赖 Next.js 或 Express 的 Request/Response 类型。HTTP 层只负责认证、解析参数、调用 Service 和组织响应。

## 5. 核心设计决策

### 5.1 数据库与 Prisma

- PostgreSQL 保持不变。
- Express 继续使用 Prisma，不自行实现数据库访问层。
- Prisma Schema 和 migrations 仍作为唯一数据库结构来源。
- Express 常驻进程必须设置合理的 PostgreSQL 连接池上限、连接等待超时和优雅关闭。
- 应用运行与数据库迁移应使用各自适合的连接地址；生产环境可继续使用 Neon pooler 地址运行应用。

### 5.2 API 兼容性

迁移期间保持现有响应格式：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

错误响应继续使用 HTTP 状态码作为 `code`，例如：

```json
{
  "code": 500,
  "message": "无法加载会话列表，请稍后重试。",
  "data": null
}
```

前端不应依赖 Express 特有的错误页面或默认 HTML 响应。所有 `/api` 错误必须经过统一错误处理中间件并返回约定 JSON；SSE 已开始发送后发生的错误，继续通过 SSE `error` 事件传递。

### 5.3 认证迁移策略

推荐采用两阶段认证迁移：

1. 业务 API 迁移期间保留 Auth.js，由 Next.js 维持当前登录、Session 和 OAuth 行为。
2. 普通 API 与 SSE 稳定后，再单独验证并决定是否将认证完全迁入 Express。

过渡期不得直接相信来自浏览器的 `userId` 请求头。Next.js 与 Express 之间如需传递用户身份，应使用仅服务端可生成、短时有效并带签名的内部凭证，同时限制 Express 内部入口的网络访问范围。

最终认证方案需要覆盖：

- 邮箱密码注册与登录
- 安全 Cookie 或访问令牌
- Session 失效和退出登录
- GitHub、Google OAuth 回调
- OAuth 账号绑定
- CSRF 防护
- 登录防爆破和认证接口限流

### 5.4 同源访问

生产环境推荐由反向代理统一对外提供一个域名：

- `/` 和前端资源转发给 Next.js。
- `/api` 转发给 Express。
- 认证仍在 Next.js 的过渡期，对认证路径设置单独转发规则。

同源访问可以减少 CORS、Cookie、OAuth 回调和浏览器安全策略带来的复杂度。Express 仍需限制允许的来源、请求体大小和凭证策略。

### 5.5 SSE 流式聊天

Express 聊天接口必须保持当前事件协议，并补充以下行为：

- 立即发送正确的 SSE 响应头。
- 禁止反向代理缓冲流式数据。
- 浏览器断开后中止上游 AI 请求。
- 为上游连接设置合理超时。
- 服务关闭时停止接收新请求并妥善结束已有连接。
- 限制单用户并发流数量。
- 不在 SSE 开始后尝试改写 HTTP 状态码。

### 5.6 限流和幂等

- 现有聊天限流使用进程内存 `Map`，只适合单实例开发环境。
- 多实例部署前应迁移为 Redis 或网关级共享限流。
- 至少设置用户、IP 和全局三个维度的限制。
- 保存消息等可重试写操作应增加幂等键，避免响应丢失后重试造成重复数据。
- 429 响应应携带合理的 `Retry-After`。

## 6. 分阶段执行计划

### M0：建立基线与验收标准

任务：

- 记录所有现有 API 的方法、路径、请求体、响应体和状态码。
- 为认证失败、资源不存在、参数错误、数据库错误和 AI 上游错误建立用例。
- 为 SSE 的正常完成、中断、错误和客户端取消建立用例。
- 记录当前本地性能基线：请求延迟、错误率和并发流表现。

验收标准：

- 同一套契约测试可以针对 Next.js API 和后续 Express API 运行。
- 测试不依赖未记录的人工操作。

### M1：抽离框架无关业务层

任务：

- 将会话 CRUD 从 Route Handler 移入 `lib/services/`。
- 将消息请求校验和业务错误统一为明确的领域错误。
- 将聊天历史加载、上下文构建、配额判断和 AI 调用编排拆分为可测试函数。
- 将响应序列化与 HTTP Response 构造分离。
- 保持现有 Next.js API 行为不变。

验收标准：

- Service 不导入 `next/server`、Express 或浏览器 API。
- 当前 Next.js API 测试全部通过。

### M2：建立 Express 基础服务

任务：

- 创建 Express 应用工厂与独立启动入口。
- 增加配置校验、JSON body 上限、请求 ID、结构化日志和统一错误处理。
- 增加 `/health/live` 和 `/health/ready`。
- 接入 Prisma，并实现进程退出时停止接收请求、等待连接结束、关闭数据库连接。
- 增加 Express 单元测试和集成测试基础设施。
- 增加分别启动 Web、API 以及同时启动两者的开发脚本。

验收标准：

- 存活检查不依赖数据库。
- 就绪检查能够反映数据库是否可用。
- 未匹配 API 和未捕获异常均返回约定 JSON，而不是 HTML。

### M3：迁移会话与消息接口

推荐顺序：

1. 查询会话。
2. 创建会话。
3. 更新会话标题。
4. 删除会话。
5. 查询消息。
6. 保存消息。
7. 删除单条消息。

任务：

- Express Router 调用 M1 中的 Service。
- 保持用户数据隔离：每次读取或修改必须同时校验资源 ID 和当前用户 ID。
- 保持分页游标、返回结构和错误文案兼容。
- 对写接口设计和实现幂等策略。
- 让迁移接口在独立前缀或测试域名下并行运行。

验收标准：

- 契约测试在新旧实现上得到一致结果。
- 不存在越权读取、修改或删除其他用户数据的情况。
- 重复提交相同幂等键不会创建重复消息。

### M4：迁移聊天 SSE

任务：

- 将 `/api/chat` 接入 Express。
- 保持现有 SSE 事件格式。
- 处理客户端中止、上游超时、流中错误和半截回复保存。
- 增加单用户并发流限制和共享请求限流。
- 配置开发和生产代理，确保 SSE 不被缓存或缓冲。

验收标准：

- 前端无需改变事件解析即可使用 Express 流。
- 用户停止生成后，上游 AI 请求能够被取消。
- 并发超过限制时返回 429，而不是持续堆积连接。

### M5：前端切换与灰度验证

任务：

- 增加 API 地址或代理配置，但尽量保持前端请求路径不变。
- 在开发环境和测试环境将业务 API 切换到 Express。
- 比较新旧接口的响应、日志、延迟和错误率。
- 保留快速切回 Next.js API 的配置开关。

验收标准：

- 登录、会话 CRUD、消息历史、流式聊天和前端错误提示全部正常。
- 网络失败、401、404、429、500 和非 JSON 响应均有符合预期的处理。

### M6：认证迁移技术验证

任务：

- 明确最终采用 Session Cookie 还是访问令牌。
- 验证 Express 与现有用户、Account 和 OAuthLinkIntent 数据兼容性。
- 验证 GitHub、Google OAuth、密码登录、账号绑定和退出登录。
- 完成 CSRF、Cookie、安全头、密钥轮换和认证限流设计。
- 决定保留 Auth.js，或采用适合 Express 的认证实现。

验收标准：

- 不降低现有认证安全能力。
- 已登录用户迁移时不需要重建业务数据。
- OAuth 失败能够安全回退且不泄露凭证。

### M7：生产化与压测

任务：

- 使用 Redis 或网关实现分布式限流。
- 配置 PostgreSQL 连接池、查询超时和慢查询监控。
- 增加 AI 上游超时、有限重试和熔断。
- 增加结构化日志、指标、链路请求 ID 和错误告警。
- 使用与实际场景相符的普通请求和长连接组合进行压测。
- 完成 Docker、反向代理和 CI/CD 配置。

验收标准：

- 明确系统可承受的普通 API QPS 和并发 SSE 连接数。
- 达到容量边界时系统能快速拒绝请求，不出现无限排队。
- 部署和回滚步骤已经演练。

### M8：全量切换与清理

任务：

- 生产流量全部切换到 Express。
- 保留一个观察和回滚窗口。
- 确认日志、错误率、延迟和数据库连接正常。
- 删除已经没有流量的 Next.js API Route。
- 删除过渡代理和重复适配代码。
- 更新开发、部署和故障处理文档。

验收标准：

- Next.js 仅承担 Web 前端职责，或只保留经明确决策的认证职责。
- Express 成为业务 API 的唯一实现。
- 回滚方案和数据兼容性经过验证。

## 7. 测试策略

至少覆盖以下测试层级：

| 层级 | 重点 |
| --- | --- |
| Service 单元测试 | 校验、权限判断、领域错误、事务行为 |
| API 集成测试 | 路径、状态码、响应结构、认证和异常转换 |
| 数据库集成测试 | Prisma 查询、唯一约束、事务、幂等性 |
| SSE 集成测试 | 事件顺序、中断、错误、超时和完成 |
| 端到端测试 | 登录、创建会话、发送消息、停止生成、重新加载 |
| 性能测试 | 普通 API QPS、并发流、连接池、上游变慢 |

新旧 API 并行期间，应使用相同的契约用例验证二者。涉及写入的对比测试必须使用隔离数据库或独立测试数据，不能直接重复作用于生产数据。

## 8. 部署与回滚

推荐生产拓扑：

```text
反向代理 / 负载均衡
├── /api/*  ─────────▶ Express 实例
└── 其他路径 ────────▶ Next.js 实例
```

迁移期间可以通过路由规则或功能开关，将指定接口切回 Next.js。数据库 Schema 在过渡期必须同时兼容新旧实现；若未来需要 Schema 变更，应遵循先扩展、再迁移数据、后收缩的顺序，避免旧版本无法运行。

回滚触发条件至少包括：

- 5xx 错误率明显高于迁移前基线。
- 登录或用户身份识别异常。
- 出现跨用户数据访问风险。
- 消息重复、丢失或顺序异常。
- SSE 大量中断或上游请求无法取消。
- 数据库连接池持续耗尽。

## 9. 主要风险

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| 认证 Cookie 与 Express 不兼容 | 用户频繁掉线或无法访问 API | 认证最后迁移；保持同源；先做技术验证 |
| OAuth 回调变化 | 第三方登录失败 | 为开发、测试、生产分别验证回调地址 |
| SSE 被代理缓冲或超时 | 回复不流式或中途中断 | 配置禁用缓冲和长连接超时；建立 SSE 测试 |
| 内存限流在多实例失效 | 用户可绕过限制 | 使用 Redis 或网关共享状态 |
| POST 重试产生重复消息 | 数据重复 | 引入幂等键和数据库唯一约束 |
| 新旧实现同时写数据库 | 行为不一致 | 固定契约；共享 Service；灰度期间监控差异 |
| 连接池配置不当 | 数据库连接耗尽 | 设置池上限、等待超时，并通过压测校准 |

## 10. 推荐首个实施范围

第一个可交付变更建议只包含 M0 至 M3：

- 补齐接口契约测试。
- 抽离会话与消息 Service。
- 建立 Express 基础服务。
- 迁移会话与消息 CRUD。
- 保留 NextAuth 和 Next.js 聊天 SSE。
- 保留旧 API Route 作为回退。

该范围能够验证目录结构、Prisma 复用、统一错误处理、身份传递和部署代理，同时避免第一轮就同时承担 OAuth 与 SSE 两个最高风险点。

## 11. 完成定义

只有同时满足以下条件，才认为后端迁移完成：

- 所有业务 API 已由 Express 提供。
- 前端功能和错误提示没有回退。
- API 契约测试、端到端测试和性能测试通过。
- PostgreSQL 与 Prisma 迁移机制保持唯一、清晰。
- 认证边界已经明确且通过安全验证。
- 限流可以在多实例间共享。
- 日志、监控、健康检查、部署和回滚流程可用。
- 旧 Next.js API Route 和过渡代码已安全删除。
