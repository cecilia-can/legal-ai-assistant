# 聊天消息虚拟列表性能优化记录

## 1. 背景

聊天页面需要承载持续增长的历史消息。全量渲染会将每条历史消息及其 Markdown、代码块、表格和操作按钮同时保留在 DOM 中；消息数量增长后，DOM 规模、绘制和浏览器维护成本会持续上升。

为控制列表规模，项目使用 TanStack Virtual 在 `components/chat/MessageList.tsx` 中实现动态高度虚拟列表：仅挂载视口附近的消息，并通过总高度占位层和 `transform: translateY(...)` 保持正确的滚动位置。

本记录的目标是回答两件事：

1. 虚拟化是否降低了长消息列表的资源规模；
2. 在高速滚动时，虚拟列表是否仍能及时显示消息并保持主线程稳定。

## 2. 测试条件与口径

### 数据集

- 场景：真实混合消息（短文本、长文本、Markdown、代码块、表格）；
- 消息数：2,000 条；
- Seed：`20260909`；
- 数据指纹：`fnv1a-1ef7a964`；
- 目的：保证优化前后读取相同内容、顺序和消息 ID。

### 自动滚动基准

`/dev/message-list-bench` 使用真实的 `MessageList`、`TimelineItem`、`MessageBubble` 和 `MessageContent`，仅替换数据来源。

一次自动测量包含两段滚动：

1. 第一段约 5 秒：从列表一端连续滚到另一端，记录 `requestAnimationFrame` 间隔；
2. 第二段约 5 秒：重复滚动并检查可视区域是否存在消息，用于计算“无可见消息帧率”。

Chrome Performance trace 的主要分析口径为第一段 5 秒。该场景模拟持续高速滚动/快速拖动滚动条，是压力测试，不等同于正常阅读速度。

### 解释限制

- 测试页运行在 `next dev`，React 开发模式和编译工具会增加额外开销；最终结论需在 production build 下复测。
- `requestAnimationFrame` 间隔是主线程近似指标，不等于屏幕真实 FPS。
- Chrome trace 中的 `Paint` 事件次数不等于“所有消息被完整重绘的次数”。
- 单次 trace 用于定位热点；优化效果应至少重复 3 次并取中位数。

## 3. 发现的问题

### 3.1 全量渲染的规模问题

在相同 2,000 条混合消息下：

| 实现 | 列表内部 DOM 节点 |
| --- | ---: |
| 全量渲染 | 35,877 |
| 虚拟列表 | 150～238 |

虚拟列表将列表 DOM 节点降低约 **99.3%～99.6%**。这证明虚拟化有效控制了 DOM 规模，避免浏览器维护成本随历史消息数线性增长。

> 说明：早期基准页的“当前挂载消息项”使用了过宽的 `aria-label` 选择器，可能把消息内部动作按钮一并计数，因此不将该指标用于正式对比；DOM 节点数可作为规模对比指标。

### 3.2 虚拟列表的高速滚动问题

首轮虚拟列表 trace（`虚拟列表Trace-20260910T195859.json.gz`）显示：

- 主线程出现 24 个大于等于 50ms 的长任务，合计约 4,247ms；
- `Layout` 27 次、`UpdateLayoutTree` 28 次；
- 自动基准中曾出现约 48%～75% 的“无可见消息帧率”；
- React Profiler 出现 `MessageBubble`、`MessageContent`、`Markdown`、`MarkdownCode`、`CodeBlockPre` 等组件的高耗时 commit。

因此，初始结论不是“虚拟列表滚动更流畅”，而是：虚拟化降低了 DOM/绘制压力，但在极端快速滚动时，虚拟范围变化、新消息挂载、动态高度测量和复杂 Markdown 渲染仍会阻塞主线程。

## 4. 已实施优化

### 4.1 合并动态高度测量更新

在 TanStack Virtual 中启用：

```ts
useAnimationFrameWithResizeObserver: true
```

`ResizeObserver` 产生的一批高度变化被合并到下一动画帧处理，降低连续测量回调触发范围修正的频率。

### 4.2 避免滚动时重复调度按钮状态

滚动事件仍需要判断“回到底部”按钮是否显示，但仅在显示状态真正变化时才调用 `setShowScrollToBottom`。这避免每次 `scroll` 都调度 React 状态更新。

### 4.3 稳定消息项动作回调

删除和重新生成回调通过 ref 与稳定 `useCallback` 包装后传给 `TimelineItem`，降低父层回调引用变化导致已挂载消息行失去 memo 命中机会的风险。

### 4.4 复用 Markdown 渲染配置

将 `remarkGfm`、`rehypeHighlight` 的插件数组及 Markdown 组件映射提升为模块级常量，避免消息挂载时重复创建配置对象。

> `MessageBubble`、`MessageContent` 和 `TimelineItem` 原本已使用 `memo`。本轮重点是稳定其输入条件，而不是重复包裹 memo。

### 4.5 加入滚动诊断标记

开发环境为 `MessageList` 加入 `message-list:scroll-handler` User Timing 标记，用于在 Chrome Performance 中定位应用滚动处理函数本身的耗时。

该项是诊断能力增强，不直接构成性能优化。

## 5. 优化前后 Trace 对比

### 5.1 对比口径

- 优化前：`虚拟列表Trace-20260910T195859.json.gz`；
- 优化后：`虚拟列表Trace-20260910T215135.json.gz`；
- 均为 2,000 条混合消息、约 5 秒连续快速滚动；
- 统计 Chrome renderer 主线程第一轮滚动窗口中的 trace 事件。

| 指标 | 优化前 | 优化后 | 结果 |
| --- | ---: | ---: | --- |
| 长任务（>= 50ms） | 24 个 / 4,247ms | 26 个 / 4,551ms | 未改善 |
| 最长主线程任务 | 305ms | 262ms | 改善约 14% |
| `FunctionCall` 总耗时 | 4,552ms | 4,683ms | 未改善 |
| `Layout` | 27 次 / 201ms | 26 次 / 228ms | 基本持平 |
| `UpdateLayoutTree` | 28 次 / 151ms | 27 次 / 149ms | 基本持平 |
| `Paint` | 172 次 / 44.75ms | 100 次 / 16.75ms | 总耗时下降约 63% |
| `Commit` | 252ms | 187ms | 下降约 26% |
| Minor GC | 21 次 / 90ms | 7 次 / 55ms | 总耗时下降约 39% |

### 5.2 滚动处理函数的结论

优化后的 trace 中，第一轮 5 秒有 28 次 `message-list:scroll-handler` 调用：

| 指标 | 数值 |
| --- | ---: |
| p50 | 0.076ms |
| p95 | 0.137ms |
| 最大值 | 0.223ms |

因此 `MessageList` 自身的 React `onScroll` 处理函数不是长任务来源。长任务主要表现为 React 调度函数 `performWorkUntilDeadline`，发生在滚动位置变化之后，说明主要开销仍在虚拟范围更新后的消息挂载与复杂内容渲染链路。

## 6. 结果与结论

### 已验证的收益

- DOM 节点规模由 35,877 降至约 150～238，降低约 99.5%；
- 最新一轮高速压力 trace 中，绘制耗时、合成提交耗时和 Minor GC 耗时下降；
- 已排除 `MessageList` 的应用层 `onScroll` 函数本身是主要瓶颈的可能。

### 尚未验证或未达成的目标

- 尚不能声称高速滚动的流畅度或 FPS 已提升；
- 长任务数量和总时长没有下降，主线程 React 工作仍是主要瓶颈；
- 未实现跨卸载的 Markdown/代码高亮解析结果缓存；
- 未实现按滚动速度动态调整 overscan；
- 未在高速滚动阶段使用轻量内容预览；
- 尚未在 production build、相同设备和多次重复运行下取得中位数结果。

## 7. 下一步建议

1. 为复杂 assistant 消息实现高速滚动时的轻量文本预览，停止/减速后再渲染完整 Markdown、代码块与表格；
2. 研究可安全复用的 Markdown/代码高亮解析结果缓存，避免消息重新进入窗口后重复执行完整解析；
3. 引入分档动态 overscan，例如普通速度 `4`、较快速度 `12`、极快速度 `24`，并以“无可见消息帧率”和长任务变化验证取舍；
4. 在 production build 下以相同 seed、相同窗口尺寸运行至少 3 次，记录 p50/p95、长任务、DOM 节点和无可见消息帧率的中位数；
5. 将相同 Mock 数据注入真实聊天页面复测，验证输入框、工具时间线、流式消息和历史分页不会引入额外回归。

## 8. 可用于项目介绍的量化表述

> 实现支持动态高度的聊天消息虚拟列表，并建立可复现的 2,000 条混合消息滚动基准；将列表 DOM 节点从 35,877 降至约 150～238（约 99.5%）。在 5 秒高速滚动压力测试中，绘制耗时降低约 63%、合成 Commit 耗时降低约 26%、Minor GC 耗时降低约 39%。

该表述应限定为“2,000 条混合消息、开发环境压力测试”的结果；不应表述为 FPS 或整体滚动流畅度已提升。

## 9. 面试问答与技术解释

### Q1：什么是 Chrome trace 中的 `Commit`？为什么它的耗时会降低？

浏览器渲染大致包含以下阶段：

```text
JavaScript / React 更新
→ Style / Layout（计算样式、尺寸和位置）
→ Paint（将文字、背景、边框等绘制为绘制记录或像素）
→ Commit / Composite（提交更新并由合成器组合图层显示）
```

Chrome trace 中的 `Commit` 可理解为渲染结果提交给合成器/后续显示流程的一部分；它不等于一次完整屏幕刷新，也不应简单等同于 GPU 耗时。

本次 5 秒压力 trace 中，`Commit` 总耗时从约 252ms 降至约 187ms。合理解释是：高度测量更新被安排到动画帧、无效的“回到底部”状态调度减少后，列表的局部位置、可见行和绘制结果变化次数减少，因而需要提交的更新也减少。

不过，这是一组优化前后 trace 的相关结果，而非针对单一改动的隔离实验。不能表述为“某一行代码直接使 Commit 降低 26%”。要严格证明因果，需要把改动分组、每组重复至少 3 次并比较中位数。

### Q2：为什么 `Paint` 绘制耗时会降低？

`Paint` 指浏览器把元素的文本、背景、边框、阴影等转换为可显示内容的过程。它不等于重新绘制全部消息；滚动时新进入区域、位置变化的虚拟行或发生视觉变化的局部区域都可能产生 Paint。

本次 trace 中，`Paint` 总耗时从约 44.75ms 降至约 16.75ms，事件数从 172 降至 100。可能原因包括：

- 高度更新由更分散的即时处理转为动画帧阶段处理，减少连续位置修正；
- “回到底部”按钮状态不再在每个 scroll 事件中都尝试更新，减少局部 UI 改动；
- 稳定回调与 memo 命中减少已挂载消息行的无效更新；
- Markdown 配置对象复用减少了部分无关对象创建。

其中前两项更可能影响绘制路径；Markdown 配置复用主要影响 JavaScript 对象分配，不能单独解释 Paint 降低。

### Q3：为什么 `ResizeObserver` 会一次产生多条高度变化？

虚拟列表通过 `measureElement` 观察当前已挂载的消息行。消息行的实际高度可能在以下情况下变化：

- 一批新虚拟行同时挂载；
- Markdown 解析完成后形成标题、列表、表格或代码块；
- 字体、图片或异步内容加载完成；
- 容器宽度变化导致文本重新换行；
- 流式消息内容增长。

浏览器会将同一轮布局中发生尺寸变化的多个元素，以多个 `ResizeObserverEntry` 的形式交给观察回调。因此一次回调中可能包含多条消息，而不是只包含一条消息。

### Q4：`ResizeObserver` 更新“合并到下一动画帧”具体做了什么？

启用 `useAnimationFrameWithResizeObserver: true` 后，TanStack Virtual 不会在收到观察回调的当前时机立刻处理高度缓存更新，而是用 `requestAnimationFrame` 将处理安排到下一帧。

```text
多条消息尺寸变化
→ 浏览器交付 ResizeObserver entries
→ TanStack Virtual 安排 requestAnimationFrame
→ 下一帧统一读取 entries、更新高度缓存和虚拟范围
→ 浏览器执行后续布局、绘制与合成
```

作用是让同一渲染周期内的尺寸变化更集中地处理，降低“测量一条 → 修正范围 → 又测量一条 → 再修正”的连续反馈风险。代价是高度修正最多可能延后一帧。

需要准确表述的是：浏览器本身会批量交付同一次观察回调中的 entries；该选项将 TanStack Virtual 对这些 entries 的处理移至动画帧。它并不保证把任意时间发生的全部变化无限制地合并为一次更新。

### Q5：什么是模块级常量？为什么要把 Markdown 配置放到模块级？

模块级常量是定义在组件函数外、文件顶层的常量：

```ts
const markdownRemarkPlugins = [remarkGfm];
const markdownRehypePlugins = [rehypeHighlight];

export const MessageContent = memo(function MessageContent() {
  // 每次组件 render 或 mount 时复用上方常量
});
```

浏览器加载该 JavaScript 模块时会初始化这些常量；同一模块实例中的每个 `MessageContent` 挂载和渲染都会复用同一数组与组件映射对象。

相对地，若在组件函数中编写 `remarkPlugins={[remarkGfm]}` 或每次创建新的组件映射对象，每次组件执行都会得到新的数组/对象引用。模块级复用可减少少量对象分配，也让依赖引用稳定。

这项优化不会缓存 Markdown 的解析结果，也不会消除消息重新挂载时的 Markdown 解析；它只是减少配置对象创建。

### Q6：为什么当前还不能声称高速滚动 FPS 已提升？

虽然 Paint、Commit 与 Minor GC 下降，但最新 trace 的长任务从 24 个增加到 26 个，长任务总时长从约 4,247ms 增至约 4,551ms。高耗时工作仍集中在 React 的 `performWorkUntilDeadline` 调度路径。

这意味着浏览器绘制路径变轻了一些，但滚动位置变化后，React 挂载新虚拟行、渲染 Markdown/代码块以及处理相关更新的耗时仍然很高。只要单次主线程任务经常超过 16.67ms（60Hz 的单帧预算），就不能证明 FPS 或高速滚动流畅度已经改善。

### Q7：下一步怎样提高高速滚动时的流畅度和 FPS？

优先级建议如下：

1. **降低新进入虚拟窗口的渲染成本**：高速滚动时先显示简化纯文本预览或稳定高度的轻量内容，停止/减速后再渲染完整 Markdown、代码高亮和表格。这样用户快速定位时不会因复杂内容解析而长时间空白。
2. **缓存或延后复杂解析**：研究缓存 Markdown AST/代码高亮结果，或将重解析移出主线程；不要缓存 React 元素本身，因为卸载后复用 React 元素并不能可靠避免组件重新挂载和内部状态问题。
3. **动态 overscan**：正常速度保持较小值（如 4）；快速滚动时提高到 12 或 24，让即将进入视口的消息提前挂载，降低空白帧。需要同时观察长任务，因为 overscan 过大也会一次挂载过多复杂消息。
4. **减少动态高度修正**：为不同消息类型提供更准确的预估高度，缓存已测量高度，避免无必要的全量测量或高度缓存重置。
5. **用生产构建验证**：在相同设备、相同窗口尺寸、相同 seed 下，分别进行至少 3 次优化前后录制，记录 p50/p95、长任务、无可见消息帧率和 DOM 节点数的中位数。
