# Express 后端迁移阶段

## 目标

以 `docs/express-backend-migration-plan.md` 为迁移总纲，以当前仓库、Git 状态、测试结果和已有 OpenSpec 产物为事实来源，为 M0-M8 中的一个阶段建立明确边界并推动其安全落地。每次调用只处理一个阶段，不因总方案包含后续工作而扩大当前任务。

## 首次行动

1. 完整读取 `docs/express-backend-migration-plan.md`。
2. 检查当前分支、工作区改动和最近提交，保留用户已有改动。
3. 检查已有 OpenSpec Change 及其状态，避免重复创建或实施。
4. 根据用户指定的阶段，或根据代码和验收证据推断“下一阶段”。说明推断依据；证据不足时不得宣称前置阶段已完成。
5. 阅读该阶段涉及的真实代码、测试、配置和项目指令。修改 Next.js 代码前，遵守 `AGENTS.md` 并读取 `node_modules/next/dist/docs/` 中相关指南。
6. 阅读 [阶段规则](references/stage-rules.md) 中当前阶段对应的小节。

## 阶段门禁

### 门禁一：阶段任务书

任何实现开始前，必须按照 [阶段任务书模板](references/stage-brief-template.md) 输出任务书，至少包含：阶段目标、现状证据、前置条件、范围、排除项、影响面、文件计划、任务依赖、风险、测试、验收、回滚和待确认事项。

输出任务书后停止，不修改应用代码、不创建数据库迁移、不切换流量，等待用户明确确认。只读检查和生成任务书不代表实施授权。

### 门禁二：设计与任务确认

用户确认任务书后：

1. 如果用户要求 OpenSpec，或本阶段已有对应 Change，则按 [OpenSpec 映射](references/openspec-mapping.md) 创建或更新产物。
2. 展示最终任务列表和未解决的设计选择。
3. 认证、数据库结构、生产切流、删除旧路由等高风险阶段必须再次确认后才能实施。
4. 普通低风险阶段，如果用户已明确要求确认后直接实现，可在第一次确认后实施，不机械增加确认。

## 实施原则

- PostgreSQL、Prisma Schema 和迁移历史默认保持不变；Express 继续使用 Prisma。
- API 路径、状态码、`{ code, message, data }` 和 SSE 事件协议默认保持兼容。
- Service 不得依赖 Next.js、Express 或浏览器 Request/Response 类型。
- 新旧入口优先复用同一业务层，不复制业务实现。
- 新接口验证和回滚窗口结束前，不删除对应 Next.js API Route。
- 过渡期不得相信浏览器直接提供的 `userId` 或内部身份头。
- 写接口自动重试前必须评估幂等性，不用重试掩盖未知根因。
- 不顺带重构无关模块，不擅自更换认证库、数据库或部署平台。
- 工作区存在重叠修改且无法安全绕开时停止并说明冲突。
- 不自动提交、推送、合并、归档 Change 或删除旧实现，除非用户明确授权。

## 验证与验收

根据阶段读取 [验收清单](references/acceptance-checklists.md) 的相关部分。至少验证受影响测试、类型或构建检查、API 契约、认证和用户隔离（如涉及）、错误路径与回滚可行性。

不得把“代码已写完”等同于阶段完成。只有任务和验收条件都有证据时才能报告完成。

## 阶段结束报告

报告已完成与未完成任务、实际修改文件、行为变化、测试结果、计划偏差、已知风险、回滚方法，以及下一阶段前置条件是否满足。被阻塞时说明已验证事实和继续所需的最小用户决定。
