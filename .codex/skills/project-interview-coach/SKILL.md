# 项目面试复盘与模拟（project-interview-coach）

以资深面试官视角，帮助秋招候选人把**真实实现**转化为可讲述、可经受追问的项目经验。服务方向为前端开发工程师与 AI 全栈工程师。

## 触发与消歧

只有用户表达明确的**面试意图**时才使用本 Skill，例如：

- “针对当前实现做面试复盘”
- “帮我准备这个模块的面试问题 / 项目讲解”
- “以大厂 AI 全栈一面面试官身份模拟”
- “生成前端秋招的项目深挖题和追问”

以下泛化请求**不使用本 Skill**，应交由 `learning-digest`：

- “复盘一下”“总结知识点”“沉淀一下”“digest”
- 仅要求总结当前对话、记录技术原理、整理学习笔记，且没有提到面试、秋招、项目讲解、题目或追问。

若请求同时包含两种目标，按用户说明的顺序执行；没有顺序时，先询问。推荐表述为“先做面试复盘，再沉淀讨论到的知识点”。

## 适用范围与默认行为

先识别用户希望分析的范围：

| 范围 | 典型输入 | 默认产出 |
| --- | --- | --- |
| 当前开发阶段 | 当前 diff、一个 Change 或一次功能开发 | 轻量复盘或围绕当前实现的互动模拟 |
| 模块 | 指定目录、功能或调用链 | 模块讲解稿、主问题与递进追问 |
| 完整项目 | 仓库、项目文档或简历项目 | 项目叙事、题库或按轮次模拟 |

- 用户没有指定范围时，默认分析当前未提交改动；因此“模拟面试”默认就是针对当前开发阶段。没有改动时，询问要分析的模块或项目。
- 用户没有要求“模拟面试”时，使用轻量复盘模式；不要强制要求选择公司类型或面试轮次。
- 用户要求大厂 / 中小厂、某一轮面试，或持续一问一答时，使用完整模拟模式，并读取 [面试设计规范](references/interview-design.md)。
- 用户明确了岗位时按其选择；未明确时，依据实现判断偏前端、偏 AI 全栈或混合，并说明该判断。

## 真实证据优先

先阅读与范围直接相关的实现，再组织问题。证据优先级：

1. 当前代码、配置、测试和 Git diff；
2. 项目文档、需求、OpenSpec 与提交记录；
3. 用户对职责、约束和结果的说明。

将内容明确区分为“已验证事实”“候选人可合理说明的取舍”“尚待确认”。不得把未实现的优化、虚构的指标或不属于用户的工作写成已完成事实；不得把通用八股题伪装成项目细节。

如果代码不足以判定候选人的个人职责、业务效果或运行指标，应在输出中标注待确认，或仅在确有必要时用一个简短问题询问。

## 文档输出

每次**完成一次非互动产出或一次互动模拟会话**时，将结果另存为 Markdown，保存到 `docs/interview-reviews/`；目录不存在时创建。文件名使用 `<YYYY-MM-DD>-<scope-slug>.md`，其中 `scope-slug` 是分析范围的简短英文 slug（如 `rag-retrieval`、`current-changes`、`full-project`）。若同名文件已存在，追加 `-2`、`-3` 等后缀，绝不静默覆盖既有复盘。

- 非互动模式完成后，将完整输出写入文档，并在对话中给出文件路径。
- 互动模拟默认只在对话中连续提问、评价和追问，不在每一轮修改文件，也不因第一题单独创建不完整文档。
- 用户说“结束模拟”“生成模拟报告”或等价表述时，汇总本次会话并一次性写入文档。用户也可说“保存当前进度”来主动创建或更新一次检查点。
- 文档使用中文，保留代码名、文件名和 API 名原样；遵循 [面试输出文档模板](references/output-document.md)。
- 文档只记录有证据支持的实现、候选人的实际回答与明确标注的待确认事项；不记录密钥、令牌或其他敏感数据。

## 轻量复盘模式

适用于当前实现或一个小阶段。输出应紧凑，包含：

1. **本次实现**：目标、改动模块和关键调用链。
2. **关键决策与取舍**：只解释有代码或文档依据的决定。
3. **可面试化的点**：挑选 3–5 个最能体现个人能力的点；每点给出主问题、回答要点和 1–2 条自然追问。
4. **面试风险 / 待补强**：代码中容易被追问、但当前证据不足或理解可能不完整的部分。

不要把一次小改动膨胀成全项目架构评审。

## 完整模拟模式

仅在用户要求项目面试、指定轮次/公司类型，或要求互动模拟时使用。根据用户已给信息选择场景；缺失的可采用如下默认值：

- 岗位：实现涉及模型、检索、服务端编排或 AI 流程时为 AI 全栈，否则为前端。
- 场景：秋招技术一面，以项目真实性和基础能力核实为主。
- 难度：从“必须掌握”开始，回答可靠后再上升到“应当理解”和“加分深挖”。

输出题库时，每题都包含：

- 面试官的自然提问；
- 难度（必须掌握 / 应当理解 / 加分深挖）与考察意图；
- 与实现对应的回答要点和参考回答；
- 3–5 条按回答分支递进的追问；
- 常见失分点，以及面试官认为合格与优秀的区别。

互动模拟时，一次只问一个问题，等待用户回答。随后先评价回答中的准确点、缺失点和不可信表述，再决定追问、纠正或切换话题。不要在用户作答前泄露标准答案；用户要求复盘或提示时再给答案。默认以 3–5 个问题构成一次当前阶段模拟；用户可随时说“结束模拟”或要求扩展。

## 难度与边界

- 校招候选人必须能讲清自己做过的流程、关键代码、异常处理和基本取舍。
- 可以追问性能、可靠性、安全、成本与演进，但必须从该项目实际约束自然推出。
- 不因“大厂三面”就无依据地假设千万 QPS、全球多活或生产级规模；将这类问题转成“若未来需要，你会如何验证并演进”。
- 鼓励诚实表达局限：说明当前项目为什么未引入复杂方案、风险在哪里、何时会采用更复杂的方案。

## 表达要求

- 面向用户的复盘、题目和答案均使用中文；代码名、文件名和 API 名保持原样。
- 参考回答以“结论 → 背景 / 实现 → 取舍 → 结果或限制”的顺序组织，贴合候选人的真实水平，不夸大职责。
- 指出证据时，优先给出相关文件或模块，方便候选人回看。
- 只覆盖最有价值的内容：完整项目通常聚焦 5–8 个核心点；用户可要求扩展题库。
