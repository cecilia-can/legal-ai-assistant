# 面试设计规范

本参考仅用于完整模拟模式、模块深挖或用户明确要求题库时。

## 1. 场景路由

| 场景 | 面试官重点 | 题目比例建议 |
| --- | --- | --- |
| 中小厂技术面 | 独立交付、代码质量、实际排错、协作 | 项目实现 60%，岗位基础 25%，工程意识 15% |
| 大厂一面 | 基础扎实度、项目真实性、核心模块细节 | 项目实现 50%，岗位基础 40%，扩展 10% |
| 大厂二面 | 方案取舍、模块边界、复杂问题定位 | 项目实现与设计 60%，基础追问 25%，演进 15% |
| 大厂三面 | 技术判断、复盘能力、项目价值与成长性 | 项目叙事 35%，取舍与演进 40%，协作与学习 25% |
| 项目深挖 | 对一个模块的端到端掌握 | 流程、代码、异常、取舍、改进，依回答递进 |

比例是选题指导，不要为了凑比例加入与项目无关的问题。

## 2. 岗位能力地图

### 前端开发工程师

围绕实际项目选择：

- JavaScript / TypeScript：异步、类型设计、状态与数据转换；
- 框架与组件：组件边界、状态管理、渲染和副作用；
- 浏览器与网络：请求、缓存、渲染、跨域或流式通信；
- 体验与质量：加载态、错误态、可访问性、性能；
- 工程化：测试、构建、配置、调试、接口协作。

### AI 全栈工程师

先确认项目是否真的涉及下列环节，再从实际链路出题：

- 前端交互与服务端 API 的边界；
- 模型调用、提示词、结构化输出与流式传输；
- 检索、RAG、工具调用或 Agent 编排；
- 上下文、数据、权限与敏感信息处理；
- 超时、失败、降级、重试、限流；
- 质量评估、日志、延迟和成本。

不能只用“AI”标签代替对端到端实现的考察，也不能要求候选人掌握其项目未使用的模型训练或分布式推理细节。

## 3. 递进式追问

每个主问题从以下路径中选择与实现相关的 3–5 条，形成分支而非平铺清单：

```text
实现了什么
→ 具体怎样实现
→ 为什么选择当前方案
→ 异常或边界如何处理
→ 如何验证效果
→ 如果需求增长，如何演进
```

- 回答不清楚实现：回到流程、数据流、职责边界，不直接跳难题。
- 回答准确：追问替代方案和真实取舍。
- 能解释取舍：追问验证方法、风险和演进条件。
- 对未做内容：接受“未实施 + 原因 + 会如何验证”的诚实回答；不逼迫虚构经验。

## 4. 回答评价标尺

| 级别 | 信号 |
| --- | --- |
| 有风险 | 只背概念；无法对应自己的实现；将计划说成已完成；关键流程前后矛盾 |
| 合格 | 讲清职责、主流程和基本取舍；能承认边界；面对提示能补全异常路径 |
| 优秀 | 能用真实证据解释设计；主动识别限制；提出与当前约束匹配的验证和演进方案 |

评价应具体指出“哪一句不够可信”“漏掉了什么流程”以及“下一次如何回答”，避免泛泛地称赞或否定。

## 5. 题目卡片模板

```markdown
### <问题标题>

- **面试官提问**：<自然口语化的问题>
- **适用场景**：<岗位、公司类型、面试轮次>
- **难度 / 考察意图**：<层级>；<想核实的能力>
- **实现证据**：<文件、模块、流程，或待确认事项>
- **回答要点**：
  1. <结论>
  2. <实现与约束>
  3. <取舍、结果或限制>
- **参考回答**：<符合校招生真实经历的 1–3 段回答>
- **追问路径**：
  1. <追问 1>
  2. <追问 2>
  3. <追问 3>
- **评价与失分点**：<合格 / 优秀差别；避免的表述>
```
